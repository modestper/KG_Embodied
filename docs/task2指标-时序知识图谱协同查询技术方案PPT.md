# Task2 指标：时序知识图谱协同查询技术方案 PPT 稿

> 适用场景：项目评审 / 中期检查 / 技术路线汇报  
> 对齐指标：支持不少于 100 个智能体节点的时序知识图谱协同查询；在百万规模图数据及对应向量、时序数据下，端侧具身智能设备查询延迟低于 500ms。

---

## 第 1 页：汇报标题

**标题：面向百智能体协同的时序知识图谱查询技术方案**

**页面要点**

- 面向无人机配送多智能体仿真与端侧具身智能场景
- 构建“图数据 + 时序事件 + 向量语义”的统一知识底座
- 支持 100+ 智能体并发协同查询
- 目标：百万规模图数据下端侧查询延迟低于 500ms

**汇报讲法**

本方案围绕 Task2 指标中的“时序知识图谱协同查询”展开，目标是在现有 LaDe 多无人机仿真和 Neo4j 知识图谱基础上，形成可测试、可扩展、可迁移到端侧设备的协同查询技术路线。

## 第 2 页：指标理解与验收口径

**页面要点**

| 指标项 | 技术含义 | 验收关注点 |
|---|---|---|
| 100+ 智能体节点 | 多无人机 / 多 agent 并发运行和查询 | 并发请求、状态同步、协同查询吞吐 |
| 时序知识图谱 | 图谱实体随时间演化，事件按 step/run 记录 | Event、Step、Run、时间窗口查询 |
| 百万规模图数据 | 图节点、关系、事件、向量和时序数据达到百万级 | 数据生成、索引、分区、查询优化 |
| 端侧延迟 <500ms | 在具身智能设备上完成复杂查询响应 | 平均响应时间、P95、稳定性 |
| 第三方测试 | 标准数据集 + 自动化测试工具 | 多轮重复测试、性能报告 |

**汇报讲法**

指标不是单纯要求存储百万节点，而是要求在百万级图、向量、时序混合数据下，仍能支撑 100 个以上智能体稳定并发查询，并在端侧设备上把查询平均延迟控制在 500ms 以内。

## 第 3 页：现有项目基础

**页面要点**

当前 LaDe viewer 已具备以下基础：

- 多无人机配送仿真环境
  - local 后端：单进程顺序推进
  - Ray 后端：每个 drone 对应一个 Ray actor
- 无人机状态建模
  - 电池续航、低电返航、depot 充电
  - `queue_capacity=6`、`cargo_capacity=3`
  - `waiting / assigned / picked_up / completed` 任务状态
- Neo4j 知识图谱接入
  - `Run` 隔离不同实验
  - `Drone / Task / Region / Event / Step` 节点
  - `ASSIGNED / COMPLETED / CARRYING / IN_RUN` 等关系
- 前端动态展示
  - Agent 状态、电量、载货、KG 最近事件

**汇报讲法**

现有系统已经不是静态演示页面，而是具备多 agent 仿真、状态事件写入和 Neo4j 图谱记录的原型系统。后续工作重点是把它从“功能可用”提升到“百万级数据和端侧性能达标”。

## 第 4 页：总体技术架构

**页面要点**

```text
多智能体仿真层
  ├─ Local Simulation
  └─ Ray Actor Simulation（100+ agents）

事件与状态采集层
  ├─ task_assigned / task_picked_up / task_completed
  ├─ drone_low_battery / drone_returning_to_charge / drone_charged
  └─ Step 运行摘要

时序知识图谱层
  ├─ Neo4j 属性图
  ├─ Run 实验隔离
  ├─ 时间窗口索引
  └─ 图分区 / 热点子图缓存

跨模态查询层
  ├─ Cypher 模板查询
  ├─ 向量召回
  ├─ 时序窗口聚合
  └─ 多 agent 协同查询合并

端侧加速层
  ├─ 本地子图缓存
  ├─ 预聚合 Step 指标
  ├─ 查询计划裁剪
  └─ 异步批处理
```

**汇报讲法**

整体架构分为五层：仿真层产生智能体行为，事件采集层把行为结构化，知识图谱层沉淀实体关系和时序事件，查询层完成图、向量、时序联合检索，端侧加速层保证在资源受限设备上的 500ms 响应目标。

## 第 5 页：知识图谱数据模型设计

**页面要点**

**核心节点**

- `Run`：一次实验运行
- `Drone`：智能体节点
- `Task`：配送任务
- `Region`：空间区域 / depot 所属区域
- `Event`：离散时序事件
- `Step`：每轮仿真的状态摘要
- `EmbeddingChunk`：语义向量单元，面向任务、事件、区域描述扩展

**核心关系**

- `(Drone)-[:ASSIGNED]->(Task)`
- `(Drone)-[:CARRYING]->(Task)`
- `(Drone)-[:COMPLETED]->(Task)`
- `(Event)-[:ABOUT_DRONE]->(Drone)`
- `(Event)-[:ABOUT_TASK]->(Task)`
- `(Step)-[:IN_RUN]->(Run)`
- `(Task)-[:BELONGS_TO]->(Region)`
- `(Drone)-[:CURRENTLY_IN]->(Region)`

**汇报讲法**

数据模型把“实体状态”和“时序事件”分开建模。`Event` 记录发生了什么，`Step` 记录每轮整体态势，`Run` 确保不同实验不混淆，后续向量节点用于承接语义检索能力。

---

## 第 6 页：时序协同查询机制

**页面要点**

**典型查询场景**

- 查询某个区域最近 30 分钟低电无人机和未完成任务
- 查询 100 个无人机当前任务队列、电量和载货状态
- 查询某个 run 下任务完成率、延迟率和低电返航次数
- 查询与某类异常事件语义相似的历史片段
- 查询某个智能体在时序窗口内的派单、取货、完成链路

**技术路线**

- 以 `Run + time_minute + region_id` 作为主过滤条件
- 高频查询走参数化 Cypher 模板
- `Step` 节点承接聚合类查询，避免实时扫全量事件
- 智能体查询按 region 分区并行执行，再合并结果
- 向量查询先召回候选，再回表图谱做关系验证

**汇报讲法**

协同查询的核心不是让 100 个 agent 同时扫全图，而是让每个 agent 的查询被限制在 run、region 和时间窗口内；聚合指标优先读 Step，复杂语义问题才走向量召回和图谱验证。

---

## 第 7 页：百万级图数据支撑方案

**页面要点**

**数据规模构造**

- 基于标准测试数据集构建百万级：
  - 智能体节点
  - 任务节点
  - 区域节点
  - 事件节点
  - Step 节点
  - 向量数据
  - 时序数据

**性能优化策略**

- 图谱侧：
  - `Run.id` 索引
  - `(Drone.run_id, Drone.id)` 组合索引
  - `(Task.run_id, Task.id)` 组合索引
  - `Event.run_id + time_minute + region_id` 查询路径优化
  - `Step.run_id + step_index` 顺序查询
- 查询侧：
  - 模板化 Cypher
  - 时间窗口裁剪
  - 子图缓存
  - 热点 region 预聚合
- 数据侧：
  - 按 run 和 region 分区
  - 冷热数据分层
  - 历史事件压缩为 Step 摘要

**汇报讲法**

百万级数据下，性能瓶颈主要来自无约束图遍历和全量事件扫描。因此方案中所有查询都必须有 run、region、时间窗口或 step 范围，避免开放式遍历。

## 第 8 页：100+ 智能体并发协同方案

**页面要点**

**智能体执行**

- 使用 Ray actor 表示 drone agent
- 每个 agent 独立维护局部状态：
  - 坐标
  - 电量
  - 队列
  - 载货
  - 当前任务
- 调度器按 region 进行任务分配和状态协调

**协同查询**

- Agent 查询按 region 分组
- 同一区域内共享 KG 上下文
- 对同类查询做批处理合并
- 高频状态查询优先读取 Step / cache
- 写入采用事件追加，避免智能体间互相锁等待

**汇报讲法**

100 个以上智能体并发时，系统不应让每个 agent 各自发起重复复杂查询。更合理的方式是按 region 汇聚查询需求，共享上下文，减少重复读取和图数据库压力。

## 第 9 页：端侧 500ms 延迟保障方案

**页面要点**

**端侧挑战**

- CPU / 内存资源有限
- 图数据库完整实例可能较重
- 网络访问云端图谱会引入不稳定延迟
- 多智能体并发查询容易产生抖动

**端侧优化**

- 端侧保留当前 run 的热点子图
- 按 region 下发局部图谱和最近 Step 摘要
- 向量索引用轻量化本地索引承接初筛
- 聚合查询优先读预计算 Step
- 复杂跨 run 查询回退云端
- 请求队列限流 + 批处理

**500ms 目标拆解**

| 阶段 | 目标耗时 |
|---|---:|
| 查询解析与模板匹配 | <30ms |
| 子图 / Step 读取 | <150ms |
| 向量候选召回 | <120ms |
| 图谱关系验证 | <120ms |
| 结果组装返回 | <80ms |

**汇报讲法**

端侧不追求保存全部百万级冷数据，而是保存和当前任务相关的热点子图、Step 摘要和轻量向量索引。这样可以把大多数实时协同查询控制在 500ms 内，复杂历史分析再交给云端。

## 第 10 页：测试与验收方案

**页面要点**

**测试对象**

- 云端单节点
- 100+ 智能体并发场景
- 端侧具身智能设备

**测试内容**

- 百万级图数据加载
- 向量数据加载
- 时序事件数据加载
- 跨模态复杂查询
- 并发吞吐量
- 平均响应时间
- P95 / P99 延迟
- 连续稳定运行情况

**测试方法**

- 每种环境不少于 3 轮重复测试
- 自动化记录：
  - 平均响应时间
  - QPS / TPS
  - 错误率
  - 内存占用
  - CPU 占用
  - 延迟波动
- 输出性能测试报告

**汇报讲法**

验收不只看一次查询是否小于 500ms，而要看多轮重复测试下的平均延迟、并发吞吐和稳定性。方案会把测试脚本、日志和报告生成纳入交付内容。

## 第 13 页：风险与保障措施

**页面要点**

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 百万级全图遍历导致延迟超标 | 查询超过 500ms | 强制 run、region、时间窗口过滤 |
| 100+ agent 重复查询压垮图数据库 | 吞吐下降 | 查询批处理、上下文共享、缓存 |
| 端侧资源不足 | 无法部署完整图谱 | 热点子图 + Step 摘要 + 云端回退 |
| 向量召回结果不稳定 | 跨模态查询误差 | 向量召回后图谱关系验证 |
| 不同实验数据混淆 | 测试结果不可复现 | `KG_RUN_ID` / `Run` 隔离 |
| 性能报告缺少证据链 | 第三方验收困难 | 自动化日志、原始数据、重复测试 |

**汇报讲法**

本指标最大的风险不是功能做不出来，而是在百万规模和端侧条件下延迟不稳定。因此方案从数据建模、查询约束、缓存预聚合和测试报告四个层面保证可验收。

# 附：一页版技术路线摘要

**目标**

面向 100+ 智能体节点，实现百万级图、向量、时序数据下的时序知识图谱协同查询，并在端侧具身智能设备上将平均查询延迟控制在 500ms 以内。

**路线**

1. 以 LaDe 多无人机仿真为智能体行为来源。
2. 以 Neo4j 构建 `Run / Drone / Task / Region / Event / Step` 时序知识图谱。
3. 以 `Run + Region + Time Window` 约束查询范围。
4. 以 Step 预聚合支撑高频统计查询。
5. 以向量召回 + 图谱验证支撑跨模态复杂查询。
6. 以 Ray 支撑 100+ 智能体并发仿真与查询压力。
7. 以端侧热点子图缓存和轻量索引保障 500ms 延迟目标。

**验证**

通过统一标准测试数据集，在云端单节点、100+ 智能体并发、端侧设备三类环境中分别开展不少于 3 轮测试，记录平均延迟、吞吐、稳定性和异常情况，形成性能测试报告。
