### 任务背景

用户希望统计项目有哪些查询脚本，以及各脚本的作用。按当前工作区代码统计，主要范围为 Neo4j 查询和查询压测的命令行入口；另列模板、网页查询模块及辅助脚本。仅阅读代码和导入查询目录统计，未连接数据库、启动 Ray、执行压测或修改程序。

### 关键结论

- `scripts/` 中共有 **9 个主要查询入口文件**，其中 **5 个为 LLM 上下文查询系列**，其余 **4 个为图谱概览、查询计时及性能压测工具**。
- LLM 上下文系列共享或加载同一套 **56 条查询（i0–i55）**，目标是为 LLM 整理无人机决策信息；脚本本身不调用 LLM。
- `lade_cypher_benchmark.py` 使用另一套 **56 条查询（q0–q55）**，用于覆盖不同 Cypher 查询结构和业务场景的性能测试，不能与 i 系列视为同一套目录。
- `lade_llm_context_queries_single.py` 与 `lade_llm_context_queries.py` 当前内容完全一致，仍使用线程池；9 个入口中包含这份重复实现。
- 基础版、stages、多进程和 Ray 版的上下文内部均逐条顺序执行查询；并发主要发生在不同上下文之间。Cypher benchmark 则按单条查询任务提交线程池。
- 另外有 **2 个模板模块、2 个网页查询模块、1 个计时命令包装脚本**，不并入 9 个主要入口。数据库备份、复制、造数工具也不并入该数字。

#### 主要查询入口：9 个

以下文件均位于 `scripts/`。

| 脚本 | 查询范围／数量 | 主要作用 | 执行方式与输出 |
| --- | --- | --- | --- |
| `query_neo4j.py` | 7 处固定查询；无 run_id 时执行其中 5 处 | 检查数据库有什么数据：总节点数、总关系数、节点标签分布、关系类型分布、Run 列表，以及指定 Run 的节点统计和最近事件 | 顺序执行，直接在终端打印概览；适合确认入库结果和数据规模 |
| `timed_neo4j_query.py` | 7 个预设，也支持自定义 Cypher／文件 | 对选定查询计时，打印返回行和行数；预设覆盖节点／关系数量、类型分布、Run 列表、Run 概览及最近事件 | 顺序执行；`overview` 组合调用前 5 个预设，支持 JSONL 日志 |
| `concurrent_neo4j_query.py` | 6 个预设，也支持自定义查询 | 模拟多个 agent 重复执行选定查询，测数据库并发吞吐与延迟；预设包括无人机当前状态、事件、邻接节点、全局最近事件、Run 节点统计、Step 摘要 | 线程池按单条查询提交任务；输出查询日志及成功率、QPS、P50/P95/P99 等统计 |
| `lade_cypher_benchmark.py` | 56 个模板，q0–q55 | 系统测试点查、时间窗口、星形展开、聚合、排序、关联、多跳遍历、反连接，以及任务、电量、区域和协作场景的查询性能 | 线程池按单条查询提交任务；支持多模板、多 agent、多轮测试、自定义模板及分类汇总 |
| `lade_llm_context_queries.py` | 56 个模板，i0–i55 | 为每架无人机构造 LLM 决策前所需的上下文，覆盖自身状态、任务、历史、附近资源、电量、区域态势和数据准备情况 | 不同 context 通过线程池并发；每个 context 内查询顺序执行；输出上下文 JSONL、逐查询日志和汇总 JSON |
| `lade_llm_context_queries_single.py` | 同上，56 个模板 | 当前与基础版完全相同，具有相同的上下文生成与计时功能 | 当前仍使用线程池；文件名不表示强制单线程，设 `--max-workers 1` 才将 context 并发数限制为 1 |
| `lade_llm_context_queries_stages.py` | 复用基础版目录，56 个模板 | 定位上下文查询时间花在哪里，拆分参数构造、线程排队、Session 创建／关闭、结果头返回、记录拉取、字典转换和日志构造等时间 | context 之间线程并发；额外记录 Neo4j 服务端可观测计时和客户端组合估算；估算项不是精确的网络耗时 |
| `lade_llm_context_queries_process.py` | 复用基础版目录，56 个模板 | 用独立 Python 进程执行上下文查询，供多进程并发测试及与线程版对比 | 使用 spawn 的 ProcessPoolExecutor；每个子进程创建自己的 Neo4j driver，父进程统一落盘；context 内仍顺序查询 |
| `lade_llm_context_queries_ray.py` | 复用基础版目录，56 个模板 | 使用本机 Ray Actor 多进程执行上下文查询，并控制 worker 的 CPU 绑定 | 默认 100 个 Actor，每个 Actor 使用不同物理核心上的一个逻辑 CPU；每个 Actor 单独创建 driver，主进程分发任务并落盘；汇总包含启动、查询和关闭阶段 |

#### LLM 系列的 56 条查询在查什么

下表按代码中的 category 精确计数，合计 56 条。

| 类别 | 数量 | 用途 |
| --- | ---: | --- |
| `self` | 2 | 无人机当前属性、目标 step 之前的最新快照 |
| `history` | 1 | 最近自身轨迹和状态序列 |
| `task` | 2 | 自身有效任务、区域已知的临期未完成任务 |
| `event` | 2 | 自身近期事件和任务完成情况摘要 |
| `region` | 2 | 所在区域的无人机状态分布及近期事件 |
| `coordination` | 1 | 同区域其他无人机的队列、电量和状态 |
| `global` | 2 | 全局 Step 摘要和区域负载瓶颈 |
| `capability` | 1 | 队列、载货容量、速度和电量配置 |
| `readiness` | 4 | 快照新鲜度、记忆窗口覆盖、当前属性与历史快照差异、决策信息缺口 |
| `memory` | 3 | 历史状态变化、状态样本分布和停滞证据 |
| `recovery` | 2 | 自身返航／充电状态、附近低电无人机信息 |
| `task_detail` | 5 | 有效任务摘要、取件点、投递点、候选动作和任务事件 |
| `task_risk` | 5 | 临期／逾期任务、直达完成时间下界、待取件及载货时间 |
| `task_history` | 5 | 历史分配、取件、完成事件、事件类型汇总和服务区域 |
| `peer` | 5 | 附近／跨区域无人机候选、单任务路线估算、返航同伴和队列比较 |
| `energy` | 6 | 返航余量、可达 depot、单任务航程、电量变化及充电历史 |
| `local_context` | 5 | 区域任务压力、队列容量、服务质量、任务流量和附近紧急任务 |
| `feedback` | 3 | 分配到取件、释放到完成、取件到投递的历史耗时反馈 |

上述查询提供图谱已知的信息和部分估算，不自动执行调度、派单、求助或 LLM 推理。
