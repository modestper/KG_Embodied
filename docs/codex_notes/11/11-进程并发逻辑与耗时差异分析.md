### 任务背景

用户希望理解新增进程版查询测试的执行逻辑，并解释为什么观察到的查询时间比线程版低很多。本次审查代码、当前 Python 环境及已有历史分阶段结果，不修改查询代码，不运行数据库压测。

### 关键结论

- 两版执行同一个 `execute_context()`，复用相同查询模板和单查询计时逻辑；进程版没有将包内查询改为并行，也没有省略结果读取。
- 线程版由多个线程共享一个 Python 解释器、Driver 和连接池；进程版每个工作进程拥有独立解释器、Driver 和连接池，每次处理一个上下文任务。数据库仍为所有客户端请求提供查询服务。
- 当前 `lade` 环境为 Python 3.13.13，GIL 已启用，Neo4j Python Driver 为 6.2.0。进程版有机会降低 Python 字节码执行、Driver 结果处理及父进程日志 JSON 编码之间的 GIL 竞争，但本轮尚无 CPU 剖析，不能认定这是加速的全部原因。
- `elapsed_ms` 和 `total_elapsed_ms` 不计进程启动、任务排队及返回结果的进程通信。`wall_ms` 才包含进程池启动至关闭的整轮开销，单查询更快不必然意味着整轮更快。
- 同样设置 `--max-workers 100` 不保证同样的实际查询并发。进程启动、进程通信、父进程收集结果和写日志均可能改变请求到达节奏，减轻服务器排队，并使单查询延迟下降。
- `--max-connection-pool-size` 在线程版是共享 Driver 的连接池上限，在进程版是每个 Driver 各自的上限。不能直接把相同的参数值视为相同的总连接限制。
- 当前尚未找到用户此次进程实验的结果文件，已询问两次运行命令和输出路径；本文给出代码证据、可能机制及核对方法，不宣称已经定位本轮加速原因。

#### 进程版怎样执行

以 100 个 drone、每个重复 20 次、选择 i0-i11 为例：

1. 父进程生成 2,000 个上下文任务，每个任务包含一个 drone ID 和独立的 `context_index`。
2. `ProcessPoolExecutor` 使用 `spawn` 创建至多 100 个工作进程。
3. 每个进程初始化一次自己的 Driver，并在后续任务中复用。默认连接池上限是每进程 1。
4. 空闲工作进程取一个任务，创建自己的 Session，依次执行 i0、i1……i11，每条查询都完整消费结果后再执行下一条。
5. 整包结果通过进程通信返回父进程，父进程写入上下文和查询日志。
6. 工作进程继续取下一包任务；正常退出时关闭自己的 Driver。

因此，100 个工作进程代表最多 100 包上下文任务同时处理，而不是包内 12 条全部同时执行、形成 1,200 条同时查询。工作进程不与某个 drone 永久绑定；重复任务沿用原线程版的提交方式。

线程版也能让多条网络请求同时等待。共享 Driver 不等于共享一个物理连接；Driver 可以从连接池为多个 Session 分配多个连接，也不意味着所有查询被一把锁串行执行。[Neo4j 官方 Driver 文档](https://neo4j.com/docs/api/python-driver/current/api.html)说明 Driver 可供多线程使用，但不能跨进程共享。

#### 为什么进程版可能显著降低客户端查询延迟

**机制一：减少同一解释器里的 Python 执行竞争。**

查询包含网络等待，也包含 Driver 协议处理、结果解码、Record 迭代、字典构造等客户端工作。传统 CPython 的多个线程在执行 Python 字节码时竞争同一把 GIL；独立进程各有解释器，允许这些阶段分散到多个 CPU 核执行。网络 I/O 等待可以释放 GIL，所以不能把线程版说成所有查询只能逐条发送。[Python 官方线程文档](https://docs.python.org/3.12/library/threading.html)同时说明了 GIL 限制和线程适合 I/O 并发的条件。

原线程版的父线程还会把完整上下文编码为 JSON 并写入日志，这部分 Python 工作与查询线程处于同一解释器。进程版的父进程编码日志时不会竞争工作进程的 GIL。不过进程版增加了结果 pickle、进程队列传输和反序列化，仍可能竞争宿主机 CPU 或内存带宽；不能据此预言净收益。

**机制二：连接池结构变化。**

线程版的连接池包含同步协调，已安装的 Driver 源码中 `_acquire()` 可见 `with self.lock` 和连接池满时的条件等待。进程版每个池只服务当前进程的顺序任务，减少多个工作线程在同一池的协调。但池内有锁本身不证明它是主要瓶颈，需要测量才能量化。

例如，仅讨论直连一个 Neo4j 地址时，线程版若设置 `--max-connection-pool-size 1`，100 个线程仍共享这个小池；进程版 100 个工作进程各设 1，则可能维持约 100 条工作连接。此时实验同时改变了连接容量。反过来，在每个进程只执行一个顺序任务的当前实现中，把每进程池上限设成 100 也不代表每个进程一定创建 100 条连接。

**机制三：实际请求重叠程度变化。**

当前代码没有统一起跑的 Barrier，`spawn` 启动并非同时完成；先就绪的进程可以提前处理任务。任务结果的传输和父进程收集也会影响后续流转。如果实际同时运行的查询减少，数据库排队就可能减少，单条查询看起来会很快，但整轮未必更快。

汇总中的 `observed_worker_count` 仅表示有结果返回的不同 PID 数量，不代表这些进程同时在查数据库。即使最终记录了 100 个 PID，也不能直接称为整个测量期间都维持 100 查询并发。

#### 时间字段到底包含什么

单条查询的核心代码由两版共同执行：

```python
query_start = clock()
rows = [row_to_dict(row) for row in session.run(query.cypher, **params)]
elapsed_ms = round((clock() - query_start) * 1000, 3)
```

该值包含调用内发生的连接获取、必要时建连、请求发送、服务端处理、网络往返、Driver 解码、结果转换，以及这段期间的线程或进程调度等待。它不是 Neo4j 纯执行耗时。

| 指标 | 统计范围 | 本次比较时应注意 |
|---|---|---|
| `query_avg_ms`、`query_p95_ms` | 成功查询的 `elapsed_ms` | 不含启动进程、任务在池中排队、返回整包的进程通信 |
| `context_avg_ms` | 工作进程或线程内的整包执行 | 不含该任务启动前的排队、返回整包的通信 |
| `wall_ms` | 进程池或线程池创建前至关闭后 | 包含启动、执行、结果收集、主进程日志写入及关闭；不含预先解析 Step 时间 |
| `throughput_qps` | 所有查询记录数除以整轮秒数 | 当前实现包含失败查询，比较时还需核对失败数与成功吞吐 |

如果单条均值大幅降低，而 `wall_ms` 和成功查询吞吐没有改善，应优先检查启动、通信和实际请求密度，不能只凭查询均值认定系统整体加速。

#### 历史结果提供什么线索

项目已有的 `test_stage/index_summary.json` 显示，历史带索引实验客户端查询平均为 **123.144 ms**，服务端计时估算为 **11.914 ms**，非服务端组合残差为 **111.230 ms**。这说明该历史负载中，客户端与通信链路有明显优化空间。

但残差不能单独解释为 GIL 时间，也包含连接池、网络、Driver 和调度等因素；这份历史结果不是用户本次线程与进程对照实验，不能用于计算本轮加速倍数。此外，这批历史结果的 i2 全部失败，而当前模板已经没有旧的 BETWEEN 语法错误；若拿历史线程结果对比当前进程结果，查询版本和成功率也发生了变化。

### 后续建议

1. 取得两次实际运行命令及 summary/query JSONL，核对 URI、数据库、run、查询文本和目录版本、step、窗口、drone、repeat、limit、自定义参数，以及是否空结果或失败。
2. 固定工作线程/进程数和可比的总连接容量，比较实际请求重叠程度。对默认每进程单连接的 100 进程配置，线程版可使用 100 工作线程与共享池上限 100 作对照。
3. 同时比较成功查询均值和 p95、`wall_ms`、成功吞吐；每条查询还需核对返回行数。查询均值仅统计成功请求，不能混淆成功率差异。
4. 固定数据与参数、分别预热，交替运行线程版和进程版多轮；不要让两组争抢同一台数据库资源。
5. 如需确定原因，再做有针对性的 CPU/GIL、服务端处理时间和实际并发观测。只有分离出客户端改善、服务器负载变化和启动/通信成本后，才能量化本轮为什么更快。
