# 知识图谱查询窗口字段与耗时说明

### 任务背景

用户希望理解前端知识图谱查询窗口的结果字段，尤其是五项耗时的含义和计时范围。本轮对照当前代码解释，不修改功能或运行数据库查询。

### 关键结论

- 五项耗时均以毫秒展示，各项存在包含关系，不能全部相加。
- 数据库报告耗时来自 Neo4j summary 的两个字段之和，是数据库报告口径，不是纯 CPU 时间，也不包含前置 EXPLAIN 校验。
- 后端查询耗时由 Python 测量，包含实际查询、数据库通信、结果读取和部分结果转换。
- 准备与只读校验包含参数校验、连接和事务准备以及一次 EXPLAIN；首次查询可能额外包含 driver 初始化、连接和认证开销。
- 后端处理总耗时包含准备、实际查询和事务清理，但不包含最终 HTTP 响应 JSON 序列化及发送。
- 网页请求总耗时从浏览器发请求前到响应 JSON 解析完毕，不包括结果表格渲染，也不是鼠标点击到屏幕绘制完成的时间。
- 最多展示行数限制的是返回给页面的记录量，不能替代 Cypher 中的 LIMIT；实时写入负载和缓存状态都会影响耗时比较。

#### 五项耗时

| 页面字段 | 导出 JSON 字段 | 实际范围 |
| --- | --- | --- |
| 数据库报告耗时 | `timing.server_reported_ms` | `summary.result_available_after + summary.result_consumed_after`；当前 driver 从服务器元数据 `t_first`、`t_last` 取得，分别描述服务器使结果可用和消费结果的耗时。不是 HTTP 请求时间或纯 CPU 时间。 |
| 后端查询耗时 | `timing.query_client_ms` | 正式 `tx.run(query)` 前开始，到 `result.consume()` 完成。包含数据库执行及通信、读取结果、将展示记录转换成可返回的值、为限制结果大小进行的 JSON 编码，以及获取执行摘要。事务回滚不在这一段。 |
| 准备与只读校验 | `timing.validation_ms` | 从后端 `execute()` 入口到 EXPLAIN 完成并确认 `query_type == 'r'`。包含语句检查、参数和限制检查、必要的 driver/连接准备、创建只读 session 和事务，以及 EXPLAIN 请求和消费摘要。不是只测一次字符串判断。 |
| 后端处理总耗时 | `timing.backend_total_ms` | 从 `execute()` 入口到返回结果对象前，包含以上准备和正式执行，以及回滚事务、退出事务和 session、整理数据库通知等开销。不含 HTTP handler 读取并解析请求体，也不含 handler 最终对响应执行 JSON 序列化和发送。 |
| 网页请求总耗时 | `timing.browser_request_ms` | 浏览器准备发起 fetch 前开始，到 `response.json()` 完成。包含浏览器请求序列化、HTTP 通信、后端处理、响应序列化及浏览器 JSON 解析；不包含发请求前的本地输入校验、清空旧表格、后续填表及绘制。 |

数据库报告值不包含 EXPLAIN 的计时，而 EXPLAIN 已计入准备阶段。EXPLAIN 会规划语句但不会实际读取并返回正式查询结果，可能影响随后的计划缓存状态。

各阶段的关系可以近似写为：

```text
后端处理总耗时 ≈ 准备与只读校验 + 后端查询耗时 + 清理及整理开销
网页请求总耗时 ≈ 后端处理总耗时 + HTTP请求处理、序列化、传输及浏览器解析等开销
```

数据库报告值描述正式查询中的服务器侧计时，不能再作为额外阶段加到后端查询耗时上。不同来源、精度和结果拉取方式也意味着不应强行要求这些数值严格形成一个等式。

示例（仅用于说明，不是实测）：准备 20 ms、后端查询 10 ms、后端总计 32 ms、网页请求 38 ms、数据库报告 6 ms。可以理解为后端除准备和查询外另花约 2 ms，浏览器这一层还包含约 6 ms 的其他开销；不能把五项加起来作为本次总时间，也不能把两个差值都认定为纯网络延迟。

`0.000 ms` 表示上报或测量精度下显示为零，不能解释为数据库完全没有工作；`—` 表示当前没有可用数值，例如还未查询，或 summary 缺少某项时间。代码要求两个服务器时间都存在才计算数据库报告总和。

#### 查询窗口的其他字段

- **Cypher 查询**：实际提交执行的只读语句。结果表的列名由 `RETURN` 的表达式或 `AS` 别名决定，不是页面预设。例如 `RETURN d.id AS drone_id` 的 `drone_id` 就是结果列。
- **JSON 参数**：为语句中的 `$参数名` 提供值，例如 `{"limit":20}` 对应 `LIMIT $limit`。页面不会因为这里出现 `run_id` 就自动过滤，必须在 Cypher 里引用它。
- **最多展示行数**：默认 100、当前最多 200。超过显示行数或结果体积限制时标记截断；后端仍调用 `consume()` 获取正式摘要，不应把这个输入当作数据库工作量上限。
- **事务超时**：默认 5 秒、最多 15 秒，传给 Neo4j 的事务超时设置。EXPLAIN 与正式查询位于同一事务内，不能理解为完整网页请求必定在该时间内结束。浏览器另有 30 秒停止等待的逻辑，停止等待不等于数据库立即取消。
- **查询目标、数据库、环境 Run ID**：目标连接的显示标识、实际数据库及环境配置中的运行标识。环境 Run ID 只是展示信息，不会自动注入查询条件。
- **已展示 N 行**：本次实际返回页面的行数，即导出的 `row_count`。不是图中节点总数、匹配对象总数，也不是数据库扫描的总行数。
- **结果已截断**：`truncated == true`，表示结果受到展示行数或体积限制。单个表格值超过 2000 字符时也会缩短显示，完整值可在导出中查看；这与整批记录被截断不同。
- **数据库查询提示**：Neo4j 返回的通知，包含严重程度、代码和描述。通知不一定表示查询失败，应与错误提示区分。
- **最近 20 次成功查询**：当前页面内存中的历史，包含查询、耗时和展示行数；刷新后清空，失败请求不加入成功历史。
- **导出结果与耗时 JSON**：包含本次 `request`、结果 `columns/rows`、`row_count`、`truncated`、`notifications`、`timing` 和当时的成功查询历史。`executed_at` 是后端整理结果时生成的 UTC 时间，并非严格的点击时刻或事务开始时刻。

#### 选择哪项指标

观察用户需要等多久，优先看网页请求总耗时；观察后端查询调用及取回结果的成本，优先看后端查询耗时；研究数据库自身报告的执行表现，再记录数据库报告耗时，并保留其两个原始字段。

若准备阶段显著偏大，可以进一步区分首次连接与后续查询、EXPLAIN 规划和网络往返；现有单个准备指标不能直接确定是哪一项最慢。若后端查询较大但数据库报告较小，可进一步检查结果数量、取回和转换开销，不能仅凭差值认定一定是网络问题。
