### 任务背景

用户追问：100 个工作进程独立查询 Neo4j，是否增加数据库压力、是否会让数据库查询变慢，以及这些进程是否分别独占 CPU。

本次结合已分析的 `test50` / `th_test50` 结果、当前脚本和本机 CPU 信息解释，未修改压测程序或重新运行数据库查询。

### 关键结论

- **会增加单位时间的查询负载，也可能让服务端查询变慢。** 独立进程只隔离客户端解释器、Driver 和连接池，不隔离同一个 Neo4j 的 CPU、缓存、磁盘和查询执行资源。
- 原线程版也能通过多个连接并发请求数据库。100 个进程不等于把原来的单条串行数据库请求突然变成 100 条；本轮两组主体阶段都已有接近 100 包上下文处于执行区间。
- 进程版客户端完成查询速率由约 980 提高到 5,085 次/秒，同一份工作在更短时间内完成，单位时间处理负载确实增加。这个倍数不是数据库 CPU 使用率的实测倍数。
- 已确认的是客户端平均延迟和整轮耗时降低，**尚未确认 Neo4j 服务端单查询处理时间是否降低**。服务端即便略微变慢，只要客户端等待与处理开销减少得更多，客户端总体时间仍会降低。
- 当前脚本没有把每个进程绑定到特定 CPU。工作进程由操作系统调度；可运行时占用 CPU，等待网络响应时通常阻塞，让 CPU 执行其他线程或进程。
- 当前主机可见 2 个 CPU 插槽、128 个物理核、256 个逻辑 CPU；当前执行环境允许使用 256 个逻辑 CPU。此结果不代表每个 worker 预留一个物理核，也不证明实验期间的 CPU 使用率。
- 多进程不是越多越好。达到数据库或主机资源上限后，增加进程会造成排队、调度与内存等开销，可能同时降低吞吐并增加尾延迟。

### 修改内容

#### 一、独立进程为什么仍然影响数据库

所有进程连接的是同一个 Neo4j。每个进程独立的对象主要是 Python 解释器、Driver、Session 和客户端连接池。它们发出的查询仍由 Neo4j 服务端处理，共享其执行线程、图数据缓存、内存、CPU 与磁盘。

“客户端彼此隔离”不代表“服务端资源彼此隔离”。如果客户端与 Neo4j 还运行在同一台物理机上，二者还可能直接竞争同一批 CPU 核、内存容量及带宽。当前未重新核查数据库部署及其 CPU affinity，不假设它与压测端有硬件资源隔离。

线程版本来就可以同时发出多个网络请求。GIL 限制的是同一解释器中 Python 字节码的并行执行，不会把所有正在等待 Neo4j 的网络请求强制合并成一个。共享 Driver 也可以维护多个连接。

因此，从线程改为进程后，主要发生变化的是客户端执行效率、协调方式和请求到达节奏。两组约 100 包任务同时处理并不代表 Neo4j 恰好同时计算 100 条查询；一包处于执行期间，还会经过客户端解码、参数构造和网络等待等阶段。

#### 二、压力增加为什么客户端时间还能下降

本次 `elapsed_ms` 测量的是从 `session.run()` 前开始，直到结果完整读取和转换完成的一段时间，包含多种成本：

- 获取连接，必要时建连和认证。
- 请求发送、网络往返、Neo4j 排队及服务端处理。
- 结果拉取、Driver 解码、Python 对象构造。
- 该区间内的线程或进程调度等待。

这些因素会相互影响，不能把该字段当成 Neo4j 内部纯执行时间。进程版可以减少一部分客户端竞争，即便服务端因为更高请求密度略微变慢，总体仍有可能更快。

下面仅用简化数字说明这种可能性，不是本次测得的分阶段数据：

| 简化成本 | 线程版示例 | 进程版示例 |
|---|---:|---:|
| 数据库相关时间 | 5 ms | 10 ms |
| 其他客户端与链路开销 | 95 ms | 8 ms |
| 客户端观测总时间 | 100 ms | 18 ms |

这个例子中数据库部分反而变慢，但客户端观测的总时间仍显著下降。本次实验没有服务端分阶段计时，不能判断服务端究竟是变快、不变还是变慢。

数据库压力增加也不会必然立即带来显著延迟上升。如果原先瓶颈位于客户端，数据库尚有余量，更快的客户端可能让数据库提高利用率、完成更多工作。只有接近或达到服务能力上限时，额外请求通常才会明显积累排队；具体拐点还取决于查询组合、缓存、数据访问和硬件。

#### 三、进程是否各占一个 CPU

脚本使用 `ProcessPoolExecutor(..., mp_context=multiprocessing.get_context("spawn"))`，创建独立操作系统进程。每个 worker 有自己的 PID、地址空间和 Python 解释器，由其主执行线程运行查询任务。

操作系统真正调度的是线程。每个可运行的执行线程在某一时刻被放到一个逻辑 CPU 上执行，随后可能迁移；脚本没有为某个 worker 固定核心。对于当前普通同步查询循环，可以把一个 worker 理解为：

1. 有 Python/Driver 工作要处理时，被调度到可用 CPU 上运行。
2. socket 读取需要等待数据库时，通常阻塞，让出 CPU。
3. 响应到达后重新变为可运行状态，等待调度，再解码结果。

所以 100 个 worker 不意味着 100 个物理核持续满载。进程可能大量时间在等网络或等调度；主机也同时运行父进程、数据库及其他服务。

若只有 8 个可用逻辑 CPU，100 个主要执行线程就需要在这些 CPU 上轮流运行；网络等待仍可重叠。如果增加进程超过适合该负载的数量，切换开销与资源争用会增加。反之，当前主机可见 256 个逻辑 CPU，具备把多个客户端执行线程分散运行的条件，但不意味着这些 CPU 都空闲或归压测独占。256 个逻辑 CPU 对应 128 个物理核，不能视为 256 个完全独立的物理核。

Neo4j 实际执行 Cypher 的计算发生在服务端。客户端 worker 使用某个 CPU 发送请求、处理结果，并不意味着这条 Cypher 的服务端计算被迁移到该客户端 CPU。

#### 四、本次结果应该如何表述

可以确认：同样的 112,000 条查询和相同结果，进程版客户端吞吐约提高 5.19 倍、平均观测延迟由 100.303 ms 降到 17.734 ms，整轮由 114.310 秒降到 22.024 秒。

合理解释：多进程缓解了客户端 Python/GIL/Driver 竞争，同时改变了数据库收到请求的节奏。数据库处理更多单位时间工作，与客户端整体完成更快并不矛盾。

当前不能确认：服务端单查询耗时下降了多少、数据库 CPU 使用率提高了多少、每个 worker 运行在哪个核心、GIL 对改善贡献了多少。上述问题需要服务端计时及实验期间的资源监控，不能由现有客户端耗时倒推。

### 后续建议

- 若继续做性能归因，同时记录客户端各核 CPU、Neo4j CPU/I/O、服务端处理时间、连接数和客户端整轮吞吐，保持相同查询组合和数据版本。
- 分别测试适度递增的 worker 数，例如 10、25、50、100，观察吞吐与 p95 的拐点，再决定合适进程数；本次没有自动启动这些压测。
- 比较实验时记录实际可用 CPU 和数据库资源限制，避免把增加客户端计算资源的收益误写成查询语句本身优化的收益。
