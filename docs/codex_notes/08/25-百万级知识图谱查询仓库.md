### 任务背景

用户希望在 GitHub 上查找关于加速百万级规模知识图谱查询的仓库，或者与这方面相关的开源仓库，作为项目技术路线、选型和性能测试参考。

### 关键结论

- 如果数据是 RDF/三元组并使用 SPARQL，优先看 QLever、gStore、Virtuoso、Blazegraph、qEndpoint、MillenniumDB、Jena/Fuseki/TDB2、Oxigraph。
- 如果数据是属性图并使用 Cypher/Gremlin，优先看 NebulaGraph、TuGraph、GraphScope、Memgraph、FalkorDB。
- 如果目标是端侧或单机压缩查询，可重点看 HDT/qEndpoint/HDT-rs 这类基于压缩 RDF 的路线。
- 如果目标是证明“百万级图查询低延迟”，需要配套 benchmark，建议参考 LDBC SNB、LSQB、QLever benchmark、MillenniumDB Wikidata benchmark。
- 对当前项目来说，最值得优先试的是 QLever、NebulaGraph/TuGraph、GraphScope、FalkorDB/Memgraph，以及 LDBC/LSQB benchmark。

### 执行过的操作

- 使用 Web/GitHub 搜索 RDF/SPARQL 高性能查询引擎：`QLever`、`gStore`、`Virtuoso`、`Blazegraph`、`Oxigraph`、`MillenniumDB`。
- 使用 Web/GitHub 搜索分布式或高性能属性图数据库：`NebulaGraph`、`TuGraph`、`GraphScope`、`Memgraph`、`FalkorDB`、`Kuzu`。
- 使用 Web/GitHub 搜索压缩 RDF/HDT 查询路线：`qEndpoint`、`rdfhdt`、`hdt-rs`。
- 使用 Web/GitHub 搜索图数据库与 SPARQL benchmark：`LDBC SNB`、`LSQB`、`MillenniumDB/benchmark`、`QLever benchmarks`、`Wikidata Scaling Benchmarking`。

### 后续建议

- 如果当前 LaDe 项目继续使用 Neo4j/Cypher，可先用 LDBC/LSQB 的查询模式构造百万级测试集，再对比 Neo4j、NebulaGraph、TuGraph、FalkorDB、Memgraph。
- 如果要转向 RDF/SPARQL 技术路线，优先用 QLever 和 gStore 做本地原型，验证导入耗时、索引大小、查询 p50/p95/p99。
- 如果目标强调端侧设备或低资源部署，重点调研 HDT/qEndpoint 的压缩查询能力。
- 选型时不要只看节点或三元组数量，应按查询类型拆分测试：点查、1-2 跳邻域、多跳路径、聚合、复杂 join、时序过滤。
