### 任务背景

用户询问在百万级规模知识图谱查询加速目标下，推荐自己做查询优化，还是使用已有优化过的图数据库/查询引擎仓库来提升查询速度。

### 关键结论

- 推荐主路线：优先使用已有优化过的图数据库或查询引擎，不建议从零自研完整查询优化器。
- 当前 LaDe 项目已有 Neo4j/Cypher 基础，应先把查询模板、索引、时序分区、Step 汇总和缓存做好，优先达成 500ms 级指标。
- 自研部分建议限制在“业务层查询优化”：查询模板改写、深度限制、预计算、缓存、物化视图、冷热分层，而不是实现完整 CBO。
- 如果要做技术对比或论文支撑，可以引入 QLever、TuGraph、NebulaGraph、GraphScope、Memgraph/FalkorDB 做横向 baseline。
- 如果未来转 RDF/SPARQL，可以重点试 QLever；官方文档说明其面向非常大规模 RDF/SPARQL 数据集，并提供 benchmark 和公开 demo。
- 查询优化器学习可参考 Apache Calcite，但 Calcite 更适合学习 planner/rule/cost model，不适合作为当前项目短期直接替换 Neo4j 的方案。

### 执行过的操作

- 查阅 Apache Calcite 官方页面与 GitHub，确认其定位是动态数据管理框架，包含 SQL parser、validator、可插拔规则和代价函数的 optimizer。
- 查阅 Neo4j Cypher query tuning 文档，确认 Neo4j 已内置查询 planner、execution plan、索引、统计信息和 `EXPLAIN`/`PROFILE` 调优机制。
- 查阅 QLever 文档与仓库信息，确认其是面向 RDF/SPARQL 的高效图数据库/查询引擎，支持非常大规模 triples 查询。
- 查阅 LDBC SNB 官方说明，确认其适合图数据库 benchmark，包括交互式邻域查询和复杂 BI 查询。

### 后续建议

- 先在 Neo4j 上定义 5-10 个验收查询模板，覆盖 agent 状态、task 事件链、run/step 汇总、异常事件、1-2 跳邻域。
- 对这些查询逐个用 `EXPLAIN`/`PROFILE` 看执行计划，补齐索引和查询改写。
- 做百万级数据压测时同时记录 p50、p95、p99、结果集大小、冷启动/热缓存差异。
- 如果 Neo4j 在目标查询上无法稳定低于 500ms，再选择 1-2 个成熟引擎做迁移或双写对比，不要一开始就全量替换。
- 自研优化可以作为项目亮点，但应做在业务查询层：缓存、预计算、分区、限深、物化视图和查询路由。
