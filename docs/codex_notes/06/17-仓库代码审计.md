## 详细审计结果

### 问题 1：DOM XSS 风险，数据字段被直接拼接进 `innerHTML`

- 最危险的问题：
  前端把数据文件、trace、SSE 返回值中的字段直接插入 `innerHTML`，没有 HTML 转义或 DOM API 构建。
- 可能导致的后果：
  只要 `data/summary.json`、`data/traces.json`、动态 `/events` payload 或上游 CSV/trace 被污染，攻击者可以注入 `<img onerror=...>`、`<script>` 等内容，在浏览器中执行任意脚本。动态页面还可能把 LLM/KG/任务字段展示到页面，风险面会随数据来源扩展而扩大。
- 具体出问题的位置：
  - `src/dynamic_app.mjs:445` 到 `src/dynamic_app.mjs:458`
  - `src/dynamic_app.mjs:469` 到 `src/dynamic_app.mjs:486`
  - `src/dynamic_app.mjs:513` 到 `src/dynamic_app.mjs:522`
  - `src/app.mjs:41` 到 `src/app.mjs:43`
  - `src/app.mjs:81` 到 `src/app.mjs:87`
  - `src/app.mjs:91` 到 `src/app.mjs:105`
  - `src/simulation_app.mjs:51` 到 `src/simulation_app.mjs:53`
  - `src/simulation_app.mjs:195` 到 `src/simulation_app.mjs:208`
- 推荐修改方式：
  不要把不可信字段拼接成 HTML。优先使用 `document.createElement()` 和 `textContent`，或至少提供统一的 `escapeHtml()` 并强制所有插值字段走转义。`option.value` 也应通过 DOM property 设置，而不是字符串拼接。
- 修改后的代码示例：

```js
function replaceRows(tbody, rows) {
  tbody.replaceChildren(...rows);
}

function cell(value) {
  const td = document.createElement("td");
  td.textContent = value == null ? "-" : String(value);
```

### 问题 2：SSE 缓冲区无上限，暂停或慢速播放会造成浏览器内存膨胀

- 最危险的问题：
  `frame` 事件持续 `push` 到 `state.frameBuffer`，没有容量上限、背压或丢帧策略。
- 可能导致的后果：
  用户暂停播放、选择较慢播放速度，或服务端按 `max_steps=100000` 持续推送时，浏览器会持续保存完整 frame payload。每帧包含 drones、task_states、kg_events、llm_events，任务量上限又可到 10000，内存和渲染延迟会迅速恶化，最终页面卡死。
- 具体出问题的位置：
  - `src/dynamic_app.mjs:132` 到 `src/dynamic_app.mjs:135`
  - 服务端允许 `max_steps` 到 100000：`scripts/run_dynamic_sim.py:382`
- 推荐修改方式：
  给缓冲区设置上限；如果是实时可视化，超过上限时丢弃旧帧或强制追到最新帧。服务端也应限制每次 frame 的体积，避免把全量 `task_states` 在每帧重复发送。
- 修改后的代码示例：

```js
const maxBufferedFrames = 500;

source.addEventListener("frame", (event) => {
  const payload = JSON.parse(event.data);
  state.frameBuffer.push(payload);
  if (state.frameBuffer.length > maxBufferedFrames) {
    state.frameBuffer.splice(0, state.frameBuffer.length - maxBufferedFrames);
    state.frameIndex = state.frameBuffer[0]?.frame_index ?? state.frameIndex;
  }
  if (state.playing && state.frameBuffer.length === 1) consumeFrame();
});
```

### 问题 3：`/events` 异常处理不完整，真实错误不会反馈给前端

- 最危险的问题：
  `handle_events()` 发送 200 和 SSE headers 后才构建 runtime；除断连外其他异常没有捕获并写出 `error` 事件。
- 可能导致的后果：
  数据文件缺失、Neo4j 连接失败、Ray 初始化失败、LLM 配置错误、CSV 读取异常都会导致连接中断或服务端 traceback。前端只显示 reconnecting，用户无法知道真正失败原因，排查困难；反复重连还可能不断触发昂贵初始化。
- 具体出问题的位置：
  - `scripts/run_dynamic_sim.py:320` 到 `scripts/run_dynamic_sim.py:341`
  - 前端错误事件只设置 reconnecting：`src/dynamic_app.mjs:149` 到 `src/dynamic_app.mjs:150`
- 推荐修改方式：
  捕获普通异常，写出结构化 `error` SSE，并记录服务端日志。前端监听自定义 `error` 或 `fatal` 事件展示明确错误。注意不要把密钥、完整内部路径或敏感 payload 直接暴露给前端。
- 修改后的代码示例：

```python
import traceback

def public_error(exc):
    return {"message": str(exc.__class__.__name__), "detail": str(exc)[:300]}

def handle_events(self):
    runtime_args = args_from_request(self.runtime_args, self.path)
    self.send_response(200)
    self.send_header("Content-Type", "text/event-stream; charset=utf-8")
    self.send_header("Cache-Control", "no-cache")
    self.send_header("Connection", "keep-alive")
    self.end_headers()

    env = None
    try:
        self.replace_active_env(None)
        initialize_ray_if_needed(runtime_args)
        env, config, depots = build_runtime(runtime_args)
        self.replace_active_env(env)
        for event in stream_simulation(env, config, depots, runtime_args.max_steps, runtime_args.frame_stride):
            self.wfile.write(event.encode("utf-8"))
            self.wfile.flush()
            time.sleep(runtime_args.wall_interval)
    except (BrokenPipeError, ConnectionResetError):
        return
    except Exception as exc:
        print(traceback.format_exc(), file=sys.stderr)
        self.wfile.write(format_sse("fatal", public_error(exc)).encode("utf-8"))
        self.wfile.flush()
    finally:
        self.clear_active_env(env)
```

### 问题 4：LLM 日志记录完整 request/response，存在数据泄露风险

- 最危险的问题：
  `record_llm_event()` 将完整 request、response、decisions、error 写入 `data/llm_logs/*.jsonl`。
- 可能导致的后果：
  日志会包含任务 ID、区域、坐标、KG recent events、模型响应和错误信息。当前没有硬编码密钥，但日志仍可能泄露业务数据和位置信息；如果后续 prompt 中加入用户输入、客户信息或系统上下文，泄露风险会更高。
- 具体出问题的位置：
  - `simulation/planner.py:246` 到 `simulation/planner.py:269`
  - 日志路径由动态服务生成：`scripts/run_dynamic_sim.py:216` 到 `scripts/run_dynamic_sim.py:230`
- 推荐修改方式：
  默认只记录摘要；提供显式 `LLM_LOG_FULL=1` 才写完整 payload。日志写入前应脱敏、截断字段，并避免记录原始错误中的敏感连接串。
- 修改后的代码示例：

```python
def compact_llm_event(event):
    request = event.get("request") or {}
    return {
        "time": event.get("time"),
        "region_id": event.get("region_id"),
        "model": event.get("model"),
        "max_tokens": event.get("max_tokens"),
        "elapsed_ms": event.get("elapsed_ms"),
        "used_fallback": event.get("used_fallback"),
        "error": (event.get("error") or "")[:300] or None,
        "request_meta": {
            "message_count": len(request.get("messages", [])),
            "model": request.get("model"),
        },
        "decision_count": len(event.get("decisions") or []),
    }

def write_llm_log(self, event):
    if self.log_path is None:
        return
    self.log_path.parent.mkdir(parents=True, exist_ok=True)
    payload = event if os.environ.get("LLM_LOG_FULL") == "1" else compact_llm_event(event)
    with self.log_path.open("a", encoding="utf-8") as handle:
        handle.write(json.dumps({"event": "llm_call", **payload}, ensure_ascii=False) + "\n")
```

### 问题 5：动态接口允许前端触发高成本本地/Ray/LLM 运行，缺少请求级资源预算

- 最危险的问题：
  `/events` 是 GET 接口，任何能访问服务的人都能传参触发仿真、Ray 初始化和 LLM 请求。虽然有部分上限，但仍可请求 `task_limit=10000`、`drone_count=1000`、`max_steps=100000`、`wall_interval=0`。
- 可能导致的后果：
  在非 localhost 或被代理暴露时，可被用作本机资源消耗入口。开启 LLM 后会触发外部/本地模型请求，造成 GPU/CPU/费用消耗。Ray 模式还可能重启本地 Ray runtime。
- 具体出问题的位置：
  - `scripts/run_dynamic_sim.py:350` 到 `scripts/run_dynamic_sim.py:386`
  - `scripts/run_dynamic_sim.py:405` 到 `scripts/run_dynamic_sim.py:421`
- 推荐修改方式：
  默认只绑定 `127.0.0.1` 是正确的，但仍建议加入请求级预算：限制 `max_steps * task_limit`、限制 `wall_interval` 最小值、LLM 模式需要服务端显式允许，Ray 模式不能由前端随意切换。
- 修改后的代码示例：

```python
MAX_WORK_UNITS = 2_000_000

def validate_budget(values):
    work_units = values["task_limit"] * values["max_steps"]
    if work_units > MAX_WORK_UNITS:
        values["max_steps"] = max(1, MAX_WORK_UNITS // values["task_limit"])
    values["wall_interval"] = max(values["wall_interval"], 0.02)
    if values["use_llm"] and os.environ.get("ALLOW_BROWSER_LLM") != "1":
        values["use_llm"] = False
    if values["backend"] == "ray" and os.environ.get("ALLOW_BROWSER_RAY") != "1":
        values["backend"] = "local"
    return values
```

### 问题 6：调度接口边界不清晰，状态修改和事件记录分离

- 最危险的问题：
  `AuctionCoordinator.assign()` 和 `RegionLLMCoordinator.apply_assignments()` 会直接调用 `drone.assign(task)` 修改状态；`SimulationEnv.release_and_assign()` 再根据返回的 assignments 补记 KG 事件。
- 可能导致的后果：
  新增 coordinator 时，如果它修改了状态但没有返回完整 assignments，KG 会漏记；如果返回了 assignments 但内部没有修改状态，外层也不会真正派单；如果同一个任务被重复返回，状态和事件可能不一致。这个设计未来扩展会踩坑。
- 具体出问题的位置：
  - `simulation/delivery_sim.py:102` 到 `simulation/delivery_sim.py:115`
  - `simulation/delivery_sim.py:151` 到 `simulation/delivery_sim.py:164`
  - `simulation/planner.py:271` 到 `simulation/planner.py:282`
- 推荐修改方式：
  coordinator 只负责计算计划，不直接修改实体；由 `SimulationEnv` 统一验证、应用状态变更、记录事件。接口名也应从 `assign` 改成 `plan_assignments` 或明确约定。
- 修改后的代码示例：

```python
class AuctionCoordinator:
    def plan_assignments(self, tasks, drones, now_minute):
        plans = []
        for task in tasks:
            candidates = [drone for drone in drones if drone.can_accept() and drone.region_id == task.region_id]
            candidates = candidates or [drone for drone in drones if drone.can_accept()]
            if not candidates:
                break
            winner = min(candidates, key=lambda drone: drone.estimate_cost(task, now_minute))
            plans.append((task.task_id, winner.drone_id))
        return plans

def release_and_assign(self):
    available = [task for task in self.tasks if task.status == "waiting" and task.release_minute <= self.now_minute]
    plans = self.coordinator.plan_assignments(available, self.drones, self.now_minute)
    drone_by_id = {drone.drone_id: drone for drone in self.drones}
    task_by_id = {task.task_id: task for task in available}
    for task_id, drone_id in plans:
        task = task_by_id.get(task_id)
        drone = drone_by_id.get(drone_id)
        if task is None or drone is None or task.status != "waiting" or not drone.can_accept():
            continue
        drone.assign(task)
        self.knowledge_store.record_assignment(self.now_minute, task, drone)
```

### 问题 7：前端 trace 文件名来自 URL，虽有编码但没有白名单校验

- 最危险的问题：
  `trace` query 参数会覆盖默认 trace 文件，并直接 fetch `./data/${encodeURIComponent(state.traceFile)}`。
- 可能导致的后果：
  `encodeURIComponent` 阻止了常规路径穿越，但没有保证请求的文件一定来自 `data/traces.json` 白名单。攻击者可以诱导用户加载任意同目录下可访问的数据文件名；如果静态服务器存在特殊解码行为或未来迁移服务器，风险会变复杂。
- 具体出问题的位置：
  - `src/simulation_app.mjs:49` 到 `src/simulation_app.mjs:60`
- 推荐修改方式：
  URL 参数只能从 `state.traces` 白名单中选择；不在白名单则回退默认值。
- 修改后的代码示例：

```js
const requested = new URLSearchParams(window.location.search).get("trace");
const allowed = new Set(state.traces.map((trace) => trace.file));
state.traceFile = requested && allowed.has(requested)
  ? requested
  : state.traces[0]?.file || "delivery_sim_current.json";
```
