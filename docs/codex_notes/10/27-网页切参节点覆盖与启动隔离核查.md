### 关键结论

- 不能把当前实现理解为“替换整个旧仿真”。普通 `Drone` 按 `(run_id, id)` 执行 `MERGE`，再更新属性；相同身份复用节点，不删除重建，不自动清理旧关系。
- `s8010` 将第一个参数固定为 `KG_RUN_ID`。同一服务内网页切参不会自动更换这个运行 ID；重新启动时若继续使用同一个运行 ID，也会复用对应普通实体。
- 无人机数量从 5 减为 3 时，后续更新涉及的节点会更新，旧的另外两个节点不会自动删除。旧 Task/Event/Step/AgentState 和关系也不能视为已清理，因此同一 run 下可能混入历史残留。
- 启用新代码的 `KG_STATE_SOURCE=neo4j` 后，主进程读取的是新增 `DroneRuntimeState`。它按 `(run_id, execution_id, drone_id)` 隔离，每次新建环境生成新的执行 ID，查询还检查本次无人机列表与版本；旧视图不会被当成本次有效状态。
- 新读取视图隔离不等于整个图谱已具备完整重启隔离；普通实体和历史查询仍按原 run ID 匹配。独立实验使用新的运行 ID可避免复用旧实体，但网页切参自动生成新 run ID 尚未实现。
- 当前磁盘上的 `s8010` 将第二个参数赋给 `KG_WRITE_MODE`，会覆盖前置同名环境变量。当前正确用法为 `KG_STATE_SOURCE=neo4j s8010 <新运行ID> ray`，或将末尾改为 `process`。
