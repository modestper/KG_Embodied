### 任务背景

用户希望明确主进程查询知识图谱后能拿到哪些信息。本次按当前代码核查 `KG_STATE_SOURCE=neo4j` 的自动调度状态读取，以及区域 LLM 可选的历史查询，列出实际返回内容。

### 关键结论

- 实时状态查询读取本次 `DroneRuntimeState`，一次批量读取全部本次无人机；实际 Cypher 返回无人机 ID、执行 ID、操作版本、格式版本和完整 JSON。
- JSON 中包含 `snapshot` 和 `task_updates`：前者为无人机完整运行快照，后者为本次发布包含的任务更新。
- 无人机快照覆盖位置、区域、运行状态、电量、容量、队列、载货、当前目标、速度、depot、故障、互助和完成统计。
- 队列和载货任务包含完整 DeliveryTask 字段；任务更新包含当前队列/载货任务，以及本次操作需要保留的派单、释放、完成等任务数据，不等于重新读取所有历史任务。
- 初始任务目录和尚未派单任务仍保留在主进程 CSV 加载后的内存中；实时状态查询没有遍历全部 Task、Event、Step 或 AgentState 历史。
- 启用区域 LLM 时，还可按 run 和区域额外查询默认最近 30 分钟的派单数、完成数、超时完成数及最多 20 条近期事件；这条历史查询不按 execution_id 隔离。
- 主进程基于读回的数据计算派单成本、候选无人机和互助方案，查询本身没有返回已经算好的最优派单结果。

### 修改内容

新增本说明文档，未修改执行代码。

实际状态查询直接返回以下五列：

| 返回列 | 含义 |
|---|---|
| `drone_id` | 无人机身份 |
| `execution_id` | 当前执行身份 |
| `version` | 最近一次状态变更对应的全局操作序号，用于预期版本校验 |
| `schema_version` | 状态 JSON 格式版本 |
| `payload_json` | 含 `snapshot`、`task_updates` 的完整 JSON |

`run_id` 是查询过滤条件。节点虽然另有 `step_index`、`time_minute`、`updated_at` 属性，当前查询接口并未返回它们；仿真当前时间仍由主进程维护。

`snapshot` 字段分组：

| 信息类别 | 实际字段 |
|---|---|
| 身份、位置、状态 | `id`、`drone_id`、`x`、`y`、`status`、`region_id` |
| 队列 | `queue`（任务 ID 顺序）、`queue_payload`（完整任务）、`queue_capacity` |
| 载货 | `onboard`（任务 ID）、`onboard_tasks`（完整任务）、`onboard_count`、`cargo_capacity` |
| 能力与移动 | `capacity`、`speed_m_per_minute`、`distance_m` |
| 电量 | `battery_range_m`、`battery_capacity_m`、`battery_remaining_m`、`battery_consumed_m`、`low_battery_threshold_m`、`safety_buffer_m` |
| 当前目标 | `target`，为空或描述当前任务/返航目标，包括相应坐标与阶段 |
| depot | `home_depot`、`depots`、`target_depot` |
| 故障与互助 | `failure_mode`、`takeover_mode` |
| 完成统计 | `completed`（数量）、`completed_ids`（任务 ID 列表） |

完整任务字段：

| 信息类别 | 实际字段 |
|---|---|
| 身份和区域 | `task_id`、`city`、`aoi_id`、`region_id` |
| 地点 | `pickup_x`、`pickup_y`、`x`、`y`（送达位置） |
| 时限 | `release_minute`、`deadline_minute` |
| 执行进度 | `status`、`picked_up`、`assigned_to`、`pickup_time`、`completed_at`、`onboard_drone_id` |
| 互助请求 | `assistance_reason`、`assistance_requested_at`、`assistance_source_drone_id` |
| 交接 | `handover_from_drone_id`、`handover_to_drone_id`、`handover_x`、`handover_y`、`handover_completed_at` |
| 接管历史 | `takeover_count`、`previous_assignees` |

这些任务字段通过 `queue_payload`、`onboard_tasks` 或 `task_updates` 返回。已完成任务的完整详情只在相应操作更新中携带；完成 ID 列表本身不是完整任务历史。

区域 LLM 的历史信息来自 Event：

- `recent_agent_performance`：每架无人机在时间窗口内的 `assigned`、`completed`、`late`。
- `recent_events`：窗口内按时间选取的最近事件节点属性，可能含事件类型、发生时间、无人机、任务、区域及该类事件的额外属性。
- `urgent_tasks` 和 `candidate_drones` 是在主进程中根据已传入的任务和无人机对象整理的上下文，并不是该历史接口另外从数据库读取了完整任务目录。

### 后续建议

1. 若只需了解调度输入，优先关注位置、电量、容量、队列、任务进度与故障/互助信息。
2. 若要检查“最近任务完成率”等历史指标，需要启用相应历史查询，不能仅使用最新快照中的完成 ID 列表推断。
3. 若复用同一 run ID 重启，实时状态以 execution_id 隔离，历史 Event 查询仍可能包含其他执行的记录；独立实验继续使用不同 run ID。
