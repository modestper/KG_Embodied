# 知识图谱节点与属性梳理

### 任务背景

用户希望了解当前 drone 配送仿真在 Neo4j 知识图谱中会存放哪些节点，每类节点有哪些属性、何时创建和更新。本文以 `simulation/knowledge.py` 当前工作区实现为准，不仅依赖 README 的概要描述。

### 关键结论

- 主仿真 Neo4j 写入链路共使用 7 种节点：`Run`、`Region`、`Drone`、`Task`、`Event`、`Step`、`AgentState`。
- `Run`是一次实验，`Region/Drone/Task` 是业务实体，`Event` 是离散事件，`Step` 是全局步级摘要，`AgentState` 是单架 drone 在单个 step 的历史快照。
- `Step` 每一个仿真 step 都会写；`AgentState` 只有在 `KG_RECORD_AGENT_STATE=1` 时才写。headless 入口当前默认开启 AgentState，普通动态服务则取决于环境变量。
- `Drone` 和 `Task` 节点保存的是随最新事件不断覆盖的“当前态”；要查历史 drone 位置和状态，应查 `AgentState`，不能把 `Drone` 节点当作历史快照。
- 等待中任务不会因为 step 写入而自动建 `Task` 节点；通常在首次派单事件时才创建。`Region` 也通常在某个任务事件首次涉及该区域时创建。
- Neo4j 不存储 `null` 属性；下文标为“可选”的字段在 Python 值为 `None` 时，节点上通常是没有该 property，而不是存一个可见的 null。
- 仓库还有一个独立的百万级基准数据导入器，它会额外建 `Courier` 节点；这不属于主仿真运行时 schema，需要与 drone 仿真分开理解。

#### 1. `Run`：一次仿真实验

| 属性 | 含义 |
|---|---|
| `id` | run 的唯一识别字符串，来自 `KG_RUN_ID`；未指定时生成 `run-<uuid>` |

主仿真目前没有把 city、day、seed、drone_count、task_limit 等运行配置写到 `Run` 节点，因此仅查 `Run` 无法完整还原实验参数。

#### 2. `Region`：任务区域及其 depot

| 属性 | 含义 |
|---|---|
| `id` | 来自任务的 `region_id` |
| `run_id` | 所属仿真 run |
| `city` | 城市名 |
| `depot_x`, `depot_y` | 该任务区域在当次仿真中的合成 depot 平面坐标 |

逻辑身份是 `(id, run_id)`，同一 region ID 在不同 run 中是不同节点。

#### 3. `Drone`：无人机最新当前态

| 属性组 | 属性 | 含义 |
|---|---|---|
| 身份 | `id`, `run_id` | drone ID 及所属 run；逻辑身份为两者组合 |
| 区域 | `region_id` | drone 初始化时确定的固定归属区域，不是根据坐标实时重算 |
| 位置 | `x`, `y` | 最近一次写入时的平面坐标 |
| 状态 | `status` | `idle`、`queued`、`delivering`、`returning`、`charging`、`failed` 等 |
| 队列/载货 | `capacity`, `queue_capacity`, `cargo_capacity`, `queue_len`, `onboard_count` | 历史兼容 capacity、任务队列上限、载货上限、当前队列长度和已取货数 |
| 配送统计 | `completed_count`, `total_distance_m` | 已完成任务数和累计飞行距离 |
| 性能 | `speed_m_per_minute`, `battery_range_m` | 速度及遗留的航程参数 |
| 电池 | `battery_capacity_m`, `battery_remaining_m`, `battery_consumed_m`, `low_battery_threshold_m`, `safety_buffer_m` | 电池总量、剩余量、已消耗量、低电基准阈值和接单安全余量 |
| 故障/互助 | `failure_mode`, `takeover_mode` | 故障类型及互助状态，无值时属性可能不存在 |
| 更新时间 | `updated_at` | 最近一次事件写入的仿真分钟 |

`battery_range_m` 是历史兼容字段；当前真正递减和判定接单的主要是 `battery_remaining_m`。

`Drone` 会在任务事件、低电/返航/充电事件时用 `SET +=` 更新。启用 `AgentState` 后，每个 step 还会用快照中的 `region_id/x/y/status/battery_remaining_m/queue_len/onboard_count/total_distance_m` 刷新 `Drone`，但 step 刷新不会更新 `updated_at`、`failure_mode` 和 `takeover_mode`。

#### 4. `Task`：订单任务最新当前态

| 属性组 | 属性 | 含义 |
|---|---|---|
| 身份 | `id`, `run_id` | task ID 及所属 run |
| 基本归属 | `city`, `region_id`, `aoi_id` | 城市、原始 region 和 AOI |
| 时间 | `release_minute`, `deadline_minute` | 任务可派时间和 deadline |
| 路线 | `pickup_x`, `pickup_y`, `dropoff_x`, `dropoff_y` | 区域 depot 取货点和订单送达点 |
| 主状态 | `status` | `waiting`、`assigned`、`picked_up`、`completed` |
| 分配 | `assigned_to` | 当前被分配的 drone ID，可选 |
| 取货 | `picked_up`, `pickup_time`, `onboard_drone_id` | 是否已取货、取货时间、当前载货 drone；后两者可选 |
| 完成 | `completed_at`, `late` | 完成时间及是否晚于 deadline |
| 互助请求 | `assistance_reason`, `assistance_requested_at`, `assistance_source_drone_id` | 原因、请求时间和求助 drone，可选 |
| 交接 | `handover_from_drone_id`, `handover_to_drone_id`, `handover_x`, `handover_y`, `handover_completed_at` | 交接双方、交接点及完成时间，可选 |
| 接管历史 | `takeover_count`, `previous_assignees` | 接管次数和曾经分配过的 drone ID 列表 |

`Task` 不会每 step 写快照，而是在派单、取货、完成和互助事件时用最新任务状态覆盖更新。

#### 5. `Event`：不可变的离散业务事件

所有 Event 的公共属性：

| 属性 | 含义 |
|---|---|
| `id` | 确定性 ID：`run_id:type:time_minute:drone_id:task_id`；无 task 时最后一段是 `-` |
| `run_id` | 所属 run |
| `type` | 事件类型 |
| `time_minute`, `time` | 仿真分钟和格式化时间 |
| `region_id` | 任务区域或 drone 归属区域 |
| `task_id` | 相关 task；纯 drone 事件时没有该属性 |
| `drone_id` | 事件主要 actor |

按事件类型附加的属性：

| Event `type` | 额外属性 |
|---|---|
| `task_assigned` | `queue_len` |
| `task_picked_up` | `onboard_count` |
| `task_completed` | `late` |
| `drone_low_battery` | `status`, `battery_remaining_m`, `battery_consumed_m` |
| `drone_returning_to_charge` | `status`, `battery_remaining_m`, `battery_consumed_m` |
| `drone_charged` | `status`, `battery_remaining_m`, `battery_consumed_m` |
| `task_assistance_requested` | `source_drone_id`, `reason`, `handover_x`, `handover_y`, `takeover_count`；没有 helper 时 `helper_drone_id` 不存在 |
| `assist_dispatched` | `source_drone_id`, `helper_drone_id`, `reason`, `handover_x`, `handover_y`, `takeover_count` |
| `task_handover_completed` | 同上 |
| `task_taken_over` | 同上 |

Event ID 使同一 run 中同时间、同类型、同 drone、同 task 的 Ray 重放写入具有幂等性。

任务相关 Event 会连到 Drone、Task、Region 和 Run。纯 drone 事件当前只连到 Drone 和 Run，虽然自身有 `region_id` property，但没有创建 `IN_REGION` 关系。

#### 6. `Step`：每轮全局摘要

| 属性 | 含义 |
|---|---|
| `id` | `<run_id>-<step_index>` |
| `run_id` | 所属 run |
| `step_index` | step 序号 |
| `time_minute`, `time` | 当前仿真时间 |
| `completed_tasks` | **本 step** 完成的任务数，不是累计完成数 |
| `unfinished_tasks` | 当前仍未完成的全部任务数 |
| `idle_drones` | `status == idle` 的 drone 数 |
| `delivering_drones` | `status == delivering` 的 drone 数 |
| `returning_drones` | `status == returning` 的 drone 数 |
| `charging_drones` | `status == charging` 的 drone 数；由于当前充电瞬时完成，通常难以在 step 快照中看到非 0 |
| `assisting_drones` | `takeover_mode` 为 `assisting` 或 `requesting_help` 的 drone 数 |
| `low_battery_drones` | 根据 drone 当前动态低电判定统计的数量 |
| `total_distance_m` | 所有 drone 累计飞行距离之和 |

`Step` 不依赖 `KG_RECORD_AGENT_STATE`：只要使用 Neo4j KG，每 step 都会建一个 Step 节点。

#### 7. `AgentState`：每架 drone 的 step 级历史快照

| 属性 | 含义 |
|---|---|
| `id` | `<run_id>-<step_index>-<drone_id>` |
| `run_id` | 所属 run |
| `step_index`, `time_minute` | 快照对应的 step 和仿真时间 |
| `drone_id` | 对应 drone |
| `region_id` | drone 固定归属区域 |
| `x`, `y` | 该 step 下的位置 |
| `status` | 该 step 下的状态 |
| `battery_remaining_m` | 该 step 下的剩余电量 |
| `queue_len` | 待完成队列长度 |
| `onboard_count` | 已取货但未送达的载货数 |
| `total_distance_m` | 截至该 step 的累计飞行距离 |
| `failure_mode`, `takeover_mode` | 当时的故障和互助状态，可选 |

唯一性逻辑使用 `(run_id, drone_id, step_index)`。该节点只在 `KG_RECORD_AGENT_STATE=1` 时批量写入；100 架 drone 运行 10,000 step，理论上会产生约 1,000,000 个 AgentState 节点。

为支持查询，代码可自动维护三个 RANGE 复合索引：

- `(run_id, drone_id, step_index)`
- `(run_id, region_id, step_index)`
- `(run_id, step_index)`

#### 节点之间的主要关系

虽然本次重点是节点属性，为了便于理解 schema，当前主要关系如下：

```text
Region/Drone/Task/Event/Step/AgentState -[:IN_RUN]-> Run
Drone -[:HOME_REGION|CURRENTLY_IN]-> Region
Task -[:BELONGS_TO]-> Region
Event -[:ABOUT_DRONE]-> Drone
Event -[:ABOUT_TASK]-> Task
Event -[:IN_REGION]-> Region
Event -[:ABOUT_SOURCE_DRONE|ABOUT_HELPER_DRONE]-> Drone
Drone -[:ASSIGNED|CARRYING|COMPLETED|TAKES_OVER]-> Task
helper Drone -[:ASSISTS]-> source Drone
source Drone -[:HANDOVER_TO]-> helper Drone
AgentState -[:IN_STEP]-> Step
AgentState -[:OF_DRONE]-> Drone
```

其中 `ASSIGNED`、`CARRYING`、`COMPLETED`、`ASSISTS`、`HANDOVER_TO`、`TAKES_OVER` 关系自身还有时间、`active`、`reason`、`late` 等关系属性，不属于节点 property。

#### 独立的规模基准导入 schema

`scripts/build_neo4j_scale_dataset.py` 是用来构造百万级查询数据的离线工具，不走上述 drone 仿真事件链路。它使用 `Run`、`Region`、`Task`、`Event` 并额外引入 `Courier`：

- `Run`：`id`, `kind='scale_benchmark'`, `source`。
- `Region`：`id`, `run_id`, `city`。
- `Courier`：`id`, `run_id`, `city`。
- `Task`：`id`, `run_id`, `order_id`, `city`, `region_id`, `courier_id`, `aoi_id`, `aoi_type`, `accept_time`, `delivery_time`, `accept_minute`, `delivery_minute`, `pickup_lng`, `pickup_lat`, `dropoff_lng`, `dropoff_lat`, `ds`, `status='completed'`。
- `Event`：`id`, `run_id`, `type`, `time_minute`, `time`, `task_id`, `courier_id`, `region_id`, `city`, `ds`；每个 Task 生成 `task_accepted` 和 `task_delivered` 两个 Event。

因此，若查的是同时装载了基准数据的 Neo4j 库，`CALL db.labels()` 可能看到 `Courier`；这并不表示实时 drone 仿真会创建 Courier。

### 后续建议

- 建议将 city、day、seed、task_limit、drone_count、depot_mode、backend 等实验配置写入 `Run`，使图谱本身可复现实验。
- 如果需要追溯 Task 的每 step 状态，应新增 `TaskState` 快照或从 Event 严格重建；当前 `Task` 只是最新态。
- 建议对 `Run.id`、`(Task.id, Task.run_id)`、`(Drone.id, Drone.run_id)`、`(Region.id, Region.run_id)`、`Event.id` 配置正式唯一约束，不要只依赖 `MERGE`。
- 建议明确是否要让纯 drone Event 也建 `IN_REGION` 关系，否则按关系查询区域事件时会漏掉低电、返航和充电事件。
