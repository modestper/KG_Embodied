### 任务背景

用户希望基于 `scripts/lade_llm_context_queries.py` 另写一个脚本，统计尽量接近 Neo4j 实际处理 Cypher 的时间，排除连接池等待、TCP/Bolt 建连与认证、网络往返和 Python 结果转换。本轮只做可行性与实现方案分析，不修改查询脚本。

### 关键结论

- 现有脚本在 `session.run()` 之前打点，在全部结果迭代并转为 Python `dict` 后停止，因此 `elapsed_ms` 是客户端端到端时间。
- 当前 Neo4j Python Driver 版本是 6.2.0，当前 Neo4j 服务端是 2026.05.0，协商的 Bolt 版本是 6.0。
- 服务端已实测返回 Bolt `t_first` 和 `t_last`，Driver 将其暴露为 `ResultSummary.result_available_after` 和 `ResultSummary.result_consumed_after` 实例属性。
- `t_first` 表示 DBMS 准备好流式输出首条记录前的毫秒数；`t_last` 表示结果流剩余部分被服务端消费完成的毫秒数。建议以二者之和作为 `server_query_ms` 的最佳可用近似。
- `server_query_ms` 能排除客户端连接池等待、新建 TCP/Bolt 连接和认证、网络往返、Driver 解码、`row_to_dict` 及日志写入时间。
- 它仍不是纯 CPU 时间：服务端内的语句解析、计划生成/计划缓存查找、内部调度与资源等待、执行算子、页缓存/I/O 等都可能在其中。只用客户端脚本无法从这两个字段中再分离纯执行 CPU 时间。
- 两个字段是整数毫秒；对 i0、i3 等快查询，可能大量出现 `0 ms`，统计分辨率低于当前 `perf_counter()` 端到端计时。

建议的单查询执行形式：

```python
result = session.run(query.cypher, **params)
rows = [row_to_dict(row) for row in result]
summary = result.consume()

server_available_ms = summary.result_available_after
server_consumed_ms = summary.result_consumed_after
server_query_ms = server_available_ms + server_consumed_ms
```

建议的日志字段：

- `server_available_ms`：服务端准备好首条结果的时间。
- `server_consumed_ms`：服务端完成剩余结果流处理的时间。
- `server_query_ms`：上述两段之和，作为新脚本的主查询耗时。
- `timing_supported`：服务端是否返回完整计时，避免把缺失值当作 0。
- `row_count`、`success`、`error`：保留现有校验字段。

新 summary 应使用 `server_query_ms` 计算 avg/p50/p95/p99，不应继续把这些字段命名为含糊的 `query_avg_ms`。建议使用 `server_query_avg_ms`、`server_query_p95_ms` 等显式名称。`wall_ms` 和 `throughput_qps` 可以保留作为整体负载参考，但不应被解释成服务端查询时间。
