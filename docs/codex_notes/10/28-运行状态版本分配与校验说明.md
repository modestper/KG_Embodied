### 任务背景

用户希望了解 Neo4j 调度状态的版本由谁统一、如何写入，以及主进程如何确认数据属于本次所需状态。本次核查当前版本分配、发布确认和读回校验逻辑，不修改运行代码。

### 关键结论

- 版本由主进程统一分配。每次执行维护一个全局递增的 `_state_sequence`，actor 和写入副程序不自行编号。
- 主进程另维护 `_expected_versions`，记录每架无人机最近一次操作应发布的版本。所谓统一是“统一编号和校验规则”，不要求所有无人机一直持有相同数字。
- 初始化版本为 0；单架无人机派单、互助释放/接单/回滚等命令使用新的操作序号，并只更新该机的预期版本；一次全体 step 使用同一个新序号，更新全部无人机的预期版本。
- 主进程把版本与 execution_id、step_index、time_minute 一起传入 actor 操作。写入方按该上下文发布运行快照，提交确认后主进程查询并逐架要求版本精确相等。版本更小或更大都不能作为当前预期状态使用。
- 新建环境或检查点恢复时生成新 execution_id，操作序号重置为 0；查询同时限定 run_id 和 execution_id，避免把重置后的序号与上次执行混淆。schema_version 是格式版本，目前为 1，与操作版本不是同一含义。
- 当前一致性依赖主进程编排、actor 串行操作、写入确认、全体 step 等待和严格读回校验，不是跨全部 actor 的单一原子数据库事务，也不是任意并发写入下的强一致协议。

### 修改内容

仅新增本说明文件。

主进程的核心数据结构相当于：

```python
execution_id = "本次执行的 UUID"
state_sequence = 0
expected_versions = {"A": 0, "B": 0}
```

版本变化示例：

| 操作 | 本次分配的序号 | A 的预期版本 | B 的预期版本 |
|---|---:|---:|---:|
| 发布初始状态 | 0 | 0 | 0 |
| 给 A 派单 | 1 | 1 | 0 |
| 给 B 派单 | 2 | 1 | 2 |
| A、B 并行执行一轮 step | 3 | 3 | 3 |
| 从 A 释放一个互助任务 | 4 | 4 | 3 |
| B 接受互助任务 | 5 | 4 | 5 |

因此，读到 A=4、B=5，在预期表正好也是该组合时属于有效结果；无需强行把 A 也更新成 5。全体执行同一轮 step 时，则统一使用该批操作的序号。

`_next_state_context` 在发出命令前就更新预期表。这是“命令完成后应该看到什么”的记录，不代表数据库已经提交。之后流程为：

```text
主进程递增序号并登记目标无人机的预期版本
→ 携带上下文调用 actor
→ actor 执行操作并生成结果状态
→ 写入方把状态与同一版本写入 Neo4j
→ 主进程等待操作返回、必要的写入队列排空
→ 查询本次 execution 的状态
→ 逐架比较实际版本和预期表
→ 所有必需状态通过检查后用于规划
```

写入方式差别：

- `ray`：无人机 actor 在方法返回前完成自身运行状态写入，使用主进程提供的版本。
- `process`：actor 结果中的状态由主进程转交独立写入进程，使用同一个操作上下文；主进程确认提交后读取。
- `main`：主进程收到结果后使用该上下文自行写入，再读取。

数据库写入语句包含 `s.version IS NULL OR s.version <= $version` 条件，以避免普通顺序调用中的旧版本回写覆盖新版本。同一版本允许再次发布。这个条件本身不能被理解为对所有任意并发写入均有效的 compare-and-swap 协议；当前保证还依赖单一编排者和上述操作顺序。

读回检查相当于：

```python
assert row.execution_id == current_execution_id
assert row.version == expected_versions[row.drone_id]
assert row.schema_version == SCHEMA_VERSION
```

另检查缺失/重复/非本次无人机、JSON 格式、必需字段和队列载货一致性。未通过时抛出 `KnowledgeStateError`；没有“选最大的数据库版本凑合使用”或“取已有部分状态继续”的逻辑。

这里的操作序号不是仿真步数：同一个 step 内可发生多次派单与互助，产生多个序号；拒绝接单等命令也可以发布新版本，表示该命令处理后的快照已确认。`schema_version` 则仅表示 JSON 格式，不能用它判断状态新旧。

### 后续建议

1. 调试状态不匹配时，同时记录 run_id、execution_id、drone_id、实际版本和预期版本，先确认查询范围与写入确认。
2. 如需改为异步流水线或多主进程调度，应重新设计命令顺序、预留/冲突检查和提交协议，不能仅沿用递增编号就宣称一致性。
3. 继续保留现有的精确版本及完整性校验；性能优化优先合并重复读取，不以放宽版本校验代替。
