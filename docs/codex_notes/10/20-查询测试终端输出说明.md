### 任务背景

用户希望确认 `scripts/lade_llm_context_queries.py` 是否把实际查询结果输出到终端，以及此前没有看到结果的原因。本次仅检查现有实现，不启动压测、不修改查询代码。

### 关键结论

- 原命令默认打印连接信息、日志路径、进度和结束后的统计，不打印查询返回的具体数据。
- 原命令未传 `--print-context`，所以不会将包含查询返回行的上下文 JSON 打印到终端。数据仍保存到 `--context-jsonl` 指定的文件。
- 添加 `--print-context` 可以打印实际返回数据；打印发生在一个 context 的全部查询完成之后，不是每条查询完成后立即打印。
- `--progress-every` 默认是 20，计数单位是完成的 context。设为 1 可每完成一个 context 打印一次进度。
- 查询明细日志记录耗时、成功状态、返回行数和错误等信息，不包含完整返回行；完整结果位于 context JSONL。
- 如果此前是连连接信息、进度、结束统计都没有，需要结合实际运行状态、输出重定向和缓冲进一步判断，不能仅凭缺少 `--print-context` 解释。

### 默认输出与结果保存位置

| 内容 | 默认终端输出 | 原命令中的文件 |
| --- | --- | --- |
| 连接信息、日志路径 | 是，时间参数解析成功后打印 | 不适用 |
| 进度 | 每完成 20 个 context 打印一次 | 不适用 |
| 总查询数、成功数、失败数、耗时、吞吐、分查询统计 | 全部完成后打印 | `test/index_summary.json` |
| 查询耗时、状态、返回行数、错误、参数 | 不逐条打印 | `test/index_query_logs.jsonl` |
| 每个 drone 的各查询实际返回行 | 需要 `--print-context` | `test/index_contexts.jsonl` |

上下文中的 `queries` 字段按查询名称保存返回行，`query_metrics` 保存各查询的指标。空数组可能是合法的无匹配结果，也可能伴随查询失败，需要查看对应指标的 `success` 和 `error`。

### 如何在终端看到实际结果

将原命令的结尾改为：

```bash
  --summary-json test/index_summary.json \
  --print-context \
  --progress-every 1
```

以上是原命令结尾的替换片段，不是独立命令。前面的 URI、run、drone、step 等参数保持原样。

两个参数互不替代：`--print-context` 显示具体结果，`--progress-every 1` 显示更频繁的进度。文件保存仍然保留，并非改成只输出到终端。

对于 `--queries all`，每个 context 内会顺序执行 56 条查询，全部完成后才写入该 context 的日志并按需打印。100 个 drone × 20 次重复会打印 2000 份上下文，大量输出会影响整体耗时，因此建议只在小规模功能检查中开启实际结果打印，正式性能压测维持默认行为。

### 如果终端完全没有输出

- 当前程序会先运行 `resolve_time_args`，之后才打印连接信息。原命令未显式指定 `--time-minute`，通常需要先查询数据库解析时间；在该步骤等待时，初始提示也尚未打印。
- 默认进度要等 20 个完整 context 完成，而不是 20 条查询完成；长查询期间可能暂时没有进度更新。
- 如果通过管道、重定向或后台运行，stdout 可能写入其他位置或采用缓冲。可以把原命令中的 `python scripts/lade_llm_context_queries.py` 改为 `python -u scripts/lade_llm_context_queries.py`，关闭 Python stdout/stderr 缓冲；这不会新增查询结果打印，也不能消除数据库等待。
- 若执行中断或提前失败，结束统计不会正常生成。需要查看当时的 stderr、进程状态和启动方式。本次未取得此前运行日志，因此不对这些情况作确定诊断。

`run_in_lade.sh` 只激活环境并 `exec` 原命令，没有主动屏蔽或重定向输出。
