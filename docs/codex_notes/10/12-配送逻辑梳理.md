# 配送逻辑梳理

### 任务背景

用户希望查清当前 LaDe 多 drone 配送仿真中，订单从哪里起送、送到哪里、任务如何派给 drone，以及区域如何划分、drone 的归属区域如何确定。本次以当前工作区代码为准，同时核对了最新留存的 `hangzhou-0621-headless-002` checkpoint。

### 关键结论

- 系统模拟的是“区域仓/depot 取货 → 订单地点送达”，不是沿用原始配送员的实际轨迹。
- 送达点取 CSV 的 `lng/lat`，转成 Web Mercator 平面坐标；系统没有用 `delivery_gps_lng/lat` 作为送达点。
- 取货点不取 CSV 的 `accept_gps_lng/lat`。代码把本次仿真中同一 `region_id` 的所有订单送达点取平均，合成该区域的 depot，并作为该区域全部订单的取货点。
- 任务的区域编号直接读自 LaDe CSV 的 `region_id`；当前代码不根据经纬度重新聚类或判定任务属于哪个区域。
- 默认 `region` depot 模式下，drone 被按“区域 ID 字符串排序 → seed 打乱 → 轮询分配”确定固定归属，并从所属区域 depot 出生。它不会因为跨区配送而改变 `region_id`。
- 默认规则拍卖优先使用同区域且队列、电量合格的 drone；如果本区无合格 drone，会放宽到全城候选，所以区域是优先约束，不是绝对边界。
- 页面上的区域边界是可视化层：预生成文件用各区域中心做 Voronoi 分割；边界不参与任务归属、drone 归属或派单决策。

#### 1. 订单字段如何变成仿真任务

| 仿真含义 | 数据来源/算法 |
|---|---|
| 任务 ID | `order_id` |
| 任务区域 | CSV 原始 `region_id` |
| 任务下发时间 | `accept_time` 的时、分 |
| deadline | `delivery_time` 的时、分；本质上是历史订单送达时间，在仿真中被当作截止时间 |
| 送达点 | `lng/lat` 经 Web Mercator 投影后的 `(x, y)` |
| 取货点 | 本次任务集中，同 `region_id` 所有送达点 `(x, y)` 的算术平均 |
| 原始 courier | `courier_id` 在当前 drone 仿真加载中未使用 |
| 原始取/送 GPS | `accept_gps_*` 和 `delivery_gps_*` 在当前任务加载中未使用 |

任务会先按 city/day 过滤，再按 `task_limit` 和 `seed` 做 reservoir sampling。因此 depot 不是一个固定现实仓库：修改 day、`task_limit` 或 seed，进入仿真的订单会变，区域平均点也可能随之移动。

#### 2. 一个任务的完整配送链路

```text
CSV 订单
  → 到 accept_time 后成为 waiting 可派任务
  → 调度器先找同 region 的合格 drone
  → 选中 drone，任务变为 assigned，进入 queue
  → drone 从当前位置直线飞往任务的 region depot
  → 到 depot 后取货，任务变为 picked_up
  → drone 直线飞往订单 lng/lat 对应的送达点
  → 到达后任务变为 completed
```

空间运动是 Web Mercator 平面上的欧氏直线，不使用道路网、飞行禁区或实际路由。默认速度是 `1200 m/min`。

drone 的队列上限默认为 6，同时载货上限为 3。到达某个 depot 后，会把队列中位于该坐标的任务批量取货，直到载货上限。已载货任务优先按 deadline 从早到晚送达；没有载货时，再按 queue 中的先后顺序去下一个取货点。完成后 drone 留在送达点，不会例行返仓；只有低电且未载货时才返回 `home_depot` 充电。

#### 3. 派单是怎么判定的

默认为 `AuctionCoordinator + RuleBasedPlanner`：

1. 只处理 `status == waiting` 且 `release_minute <= now` 的任务。
2. 优先筛选 `drone.region_id == task.region_id` 的 drone；若一个合格的都没有，再改用所有区域的合格 drone。
3. 合格 drone 必须：未故障、不在返航/充电、queue 未满，且剩余电量足以覆盖“当前位置 → 取货点 → 送达点 → 最近 depot + 5000m 安全余量”。
4. 在候选者中选 cost 最低者。规则 cost 主要由飞行距离、每个已排队任务 `1500` 的队列惩罚、预计超时惩罚，以及跨区 `25000` 惩罚组成。

电池容量默认 `50000m`，低电阈值 `12000m`。低电时实际返航目标是固定 `home_depot`，但接单前的回程电量检查使用“所有 depot 中距送达点最近的一个”。这两个口径并不完全一致，是当前实现中值得注意的一点。

若启用 `USE_LLM=1`，会改用 `RegionLLMCoordinator`：先按 `region_id` 把任务分组，只向 LLM 提供同区域 drone，由 LLM 返回 task-drone 对。LLM 请求失败时回退到规则拍卖；某区根本没有本区 drone 时，该轮 LLM 分支不会主动跨区派单。

#### 4. 故障、低电和超时风险时的互助

每轮新任务派单前，系统先检查已排队任务是否存在三种情况：原 drone 故障、剩余电量不足以完成载货任务并返仓、预计无法在 deadline 前完成。援助 drone 可以跨区，但排序时优先同任务区域。

- 任务尚未取货：直接重派，取货点仍是区域 depot。
- 任务已取货：原 drone 的当前位置被设为临时交接点，援助 drone 先飞往该点取得货物，再去原送达点。

#### 5. 区域边界究竟怎么来的

需要区分两层概念：

- **业务归属**：完全由 CSV 原始 `region_id` 决定，这是派单和 drone 归属使用的字段。
- **地图边界**：`scripts/build_region_boundaries.py` 读取某城市全部日期的订单，求每个原始 region 的订单点中心，再用这些中心生成 Voronoi 多边形，裁到城市点集的外接矩形中并简化。这些多边形存在 `data/region_boundaries.json`，只供前端画线。

如果预生成边界不存在，前端可按本次任务点生成“凸包 + padding”备用轮廓，仍然只影响显示。因为预生成边界用全城全日期数据，而运行时 depot 只用本次抽样任务，页面上的区域视觉中心与当次 depot 不一定完全重合。

#### 6. 每个 drone 属于哪个区域

`region` 模式的初始化算法是：

```text
active_region_ids = sorted(本次任务中出现的 region_id)  # 字符串排序
shuffle(active_region_ids, seed)
drone-i.region_id = active_region_ids[(i - 1) % region_count]
drone-i.position = 该 region 的 depot
```

这是按区域数量均匀轮询，不会按每个区的任务量配置 drone。若 drone 少于活跃区域，会有区域无初始 drone；若 drone 多于区域，则循环分配，每区数量最多相差 1。同一个 region set + seed + drone count 会得到确定性结果，但任务抽样改变了 active region set 后，整个映射也可能变。

默认动态页面参数 `Jilin/0925, 20 tasks, 3 drones, seed=13` 下，共抽到 4 个区域，映射是 `drone-1→R53`、`drone-2→R129`、`drone-3→R165`；R31 有 7 个任务但没有初始 drone，需要规则拍卖跨区兜底。

### 后续建议

- 若希望更接近真实配送，首先明确取货点应使用 `accept_gps_*`、固定仓网，还是当前的合成 region depot。
- 建议将 drone 数量按区域任务量/时段负载加权分配，而不是只按区域数量均分。
- 建议统一“接单时假设的返航 depot”和“真正低电时返回的 depot”，避免电量可行性估算与实际执行不一致。
- 若需要严格区域隔离，需取消 `AuctionCoordinator` 的跨区兜底；若需要全局调度，则应明确将 region 定义为“优先级”而非“服务边界”。
