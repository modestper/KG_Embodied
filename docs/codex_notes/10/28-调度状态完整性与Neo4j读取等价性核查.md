### 任务背景

用户希望确认：集中查询得到的数据能否满足当前任务分配，以及这些数据与之前主进程内存中的状态在有效性上是否等价。本次核对当前规则派单、互助的实际字段依赖、状态编码/还原及版本校验，并运行现有状态测试。未修改执行逻辑。

### 关键结论

- 对当前调度算法，“Neo4j 读回的无人机状态与任务更新 + 主进程已有的待派任务目录、仿真时间、规划器配置”覆盖任务分配所需输入。不能把这理解为所有调度输入都由这一条数据库查询提供。
- 与原 Ray 快照路径相比，正常写入链路中同一执行、同一预期版本的数据在业务含义上应等价：两条路径共同使用 `drone_snapshot` 生成状态，并由 `proxy_from_snapshot` 还原为同一类规划代理；Neo4j 路径增加 JSON 序列化和数据库往返。
- 有效性等价有前提：匹配本次 run/执行、写入已提交、读取完整预期版本、任务进度已同步、配置和仿真时间一致。它不是“任何时刻从数据库随意读一份状态，都等价于当前内存”。
- 当前实现通过执行 ID 过滤、每架无人机版本检查、数据完整性检查及同步时间步维护上述条件；不符合要求时报错，不自动采用旧快照或部分无人机继续规划。版本检查不是对所有字段内容与 Ray 内存逐项比较的证明。
- 当前状态测试 11 项通过；普通配送与故障交接场景在三种写入方式下的页面帧、任务完成和事件与原 Ray 快照路径一致。该测试使用数据库/Ray 替身，不替代真实 Neo4j 落库及并发可见性验证。
- 切换状态来源不会增加额外知识推理信息，也不自动减少耗时。若未来改为无人机持续运行、主进程同时查询和规划，必须重新定义状态滞后和派单确认规则，不能沿用当前同步条件直接宣称实时等价。

### 修改内容

任务分配输入与来源：

| 决策用途 | 所需信息 | 当前来源 |
|---|---|---|
| 筛选可接单无人机 | 运行状态、故障、队列长度和队列容量 | Neo4j 快照还原的代理 |
| 区域候选选择 | 无人机区域、任务区域 | 快照 + 主进程任务目录 |
| 距离与时效评分 | 无人机位置、速度、队列、任务取送货位置与 deadline、当前时间 | 快照 + 任务目录 + 仿真时钟 |
| 电量风险 | 剩余电量、充电站、返程距离、安全余量 | 快照及既有计算逻辑 |
| 故障/电量/时效互助 | 故障、载货、队列顺序、任务状态/时限、接管历史、位置与电量 | 快照及图中读回的任务更新 + 当前时间 |
| 筛选待派任务 | 任务释放时间、等待/已分配/完成进度 | CSV 加载的目录与主进程同步维护的任务对象 |
| 规划器选择及参数 | 规则/LLM 配置、成本规则 | 主进程配置和规划器 |

两种读取路径：

```text
Ray 路径：
actor 真实状态 → drone_snapshot → Ray 返回
→ proxy_from_snapshot → 主进程内存中的规划对象

Neo4j 路径：
actor 真实状态 → drone_snapshot → 发布状态 JSON → Neo4j
→ 主进程读回并校验 → proxy_from_snapshot → 主进程内存中的规划对象
```

初始化时，初始状态由仿真配置发布；恢复时由检查点发布，两条路径最终仍还原到相同代理结构。正常运行中图里的完整快照不是根据不完整的普通 Drone 属性重新推测出来的。

关于等价范围：

- 原 Ray 路径的坐标与累计距离快照本来就会舍入；Neo4j 复用相同编码，因此没有额外引入这一精度差异。如果比较的是 local 后端直接操作的原始 DroneAgent 对象，不能宣称所有数值与序列化快照逐位相同。
- 同样的规则规划器、相同任务/时间/状态输入，应具有相同业务判断依据。LLM 等外部服务即使输入相同，也不能据此保证每次输出完全相同。
- 原始无人机状态仍保存在 Ray actor 内存中。Neo4j 中保存的是按当前协议发布的调度快照；预期版本用于确认本轮所需发布已可见，不是数据库与 Ray 内存之间任意时刻的强一致证明。
- 历史 Event 查询仍按 run ID 与区域/时间窗口过滤，不包含本次 execution_id 的隔离。不要把实时快照的执行隔离保证泛化到全部历史查询。

### 后续建议

1. 当前可以将 Neo4j 读取结果作为原 Ray 快照的替代输入，但继续保留版本、完整性和操作确认检查。
2. 在隔离 Neo4j 测试库运行已有真实落库集成，再测量状态提交、查询和规划耗时；不要仅凭字段齐全就宣称整体性能更好。
3. 若未来采用异步流水线，另行设计允许滞后、任务预留、重复派单防护及 actor 二次确认，再验证信息有效性。
