# 知识图谱关系梳理

### 任务背景

用户希望在已了解 `Run`、`Region`、`Drone`、`Task`、`Event`、`Step`、`AgentState` 节点的基础上，进一步梳理当前 drone 配送仿真会写入 Neo4j 的所有关系，包括方向、关系属性、创建时机、有效性变化及实际语义限制。

### 关键结论

- 主仿真运行时共有 17 种关系：`IN_RUN`、`IN_STEP`、`OF_DRONE`、`HOME_REGION`、`CURRENTLY_IN`、`BELONGS_TO`、`ABOUT_DRONE`、`ABOUT_TASK`、`IN_REGION`、`ABOUT_SOURCE_DRONE`、`ABOUT_HELPER_DRONE`、`ASSIGNED`、`CARRYING`、`COMPLETED`、`ASSISTS`、`HANDOVER_TO`、`TAKES_OVER`。
- 结构/归属关系主要是 `IN_RUN`、`IN_STEP`、`OF_DRONE`、`BELONGS_TO`；业务生命周期关系主要是 `ASSIGNED`、`CARRYING`、`COMPLETED`。
- `ASSIGNED`、`CARRYING`、`TAKES_OVER`、`ASSISTS`、`HANDOVER_TO` 会通过 `active=true/false` 表示当前有效性，关系失效后不会删除。查“当前任务”时不能只看边是否存在。
- 正常流程中，取货会新增 `CARRYING`，但不会立刻关闭 `ASSIGNED`；任务完成时才将该 drone 的 `ASSIGNED/CARRYING/TAKES_OVER` 设为 `active=false`，并新增 `COMPLETED`。
- `HOME_REGION` 和 `CURRENTLY_IN` 当前都是在任务事件中连向 `task.region_id`，不是根据 `drone.region_id` 或 drone 坐标严格计算。跨区派单后可能对同一 drone 累积多条区域关系。
- 纯 drone 事件（低电、返航、充电）只建 `ABOUT_DRONE` 和 `IN_RUN`；即使 Event 有 `region_id` 属性，也没有 `IN_REGION` 关系。
- 独立的规模基准导入器还会使用 `DELIVERED`、`WORKS_IN`、`ABOUT_COURIER` 三种关系；它们不属于主 drone 仿真运行时链路。

#### 主仿真关系全景

```text
Region --------IN_RUN--------> Run
Drone ---------IN_RUN--------> Run
Task ----------IN_RUN--------> Run
Event ---------IN_RUN--------> Run
Step ----------IN_RUN--------> Run
AgentState ----IN_RUN--------> Run

AgentState ----IN_STEP-------> Step
AgentState ----OF_DRONE------> Drone

Drone ---------HOME_REGION---> Region
Drone ---------CURRENTLY_IN--> Region
Task ----------BELONGS_TO----> Region

Event ---------ABOUT_DRONE---------> Drone
Event ---------ABOUT_SOURCE_DRONE--> Drone
Event ---------ABOUT_HELPER_DRONE--> Drone
Event ---------ABOUT_TASK----------> Task
Event ---------IN_REGION-----------> Region

Drone ---------ASSIGNED------> Task
Drone ---------CARRYING------> Task
Drone ---------COMPLETED-----> Task
helper Drone --TAKES_OVER----> Task
helper Drone --ASSISTS-------> source Drone
source Drone --HANDOVER_TO---> helper Drone
```

箭头表示代码实际写入方向；Cypher 查询仍然可以反向匹配。

#### 1. run 和 step 归属关系

| 关系 | 方向 | 属性 | 作用/写入时机 |
|---|---|---|---|
| `IN_RUN` | `Region/Drone/Task/Event/Step/AgentState → Run` | 无 | 将节点隔离到某次 run；任务事件、drone 事件、step 及 AgentState 写入时分别 `MERGE` |
| `IN_STEP` | `AgentState → Step` | 无 | 表示这条 drone 快照属于哪个 step；仅 `KG_RECORD_AGENT_STATE=1` 时写入 |
| `OF_DRONE` | `AgentState → Drone` | 无 | 表示这条快照属于哪架 drone；仅 AgentState 开启时写入 |

`IN_RUN` 和节点上的 `run_id` 属性是两套同时存在的归属表示。Neo4j 不会自动保证两者一致，一致性来自当前写入代码。

#### 2. 区域归属关系

| 关系 | 方向 | 属性 | 当前实际语义 |
|---|---|---|---|
| `BELONGS_TO` | `Task → Region` | 无 | 任务属于其 CSV `region_id`，这是稳定的任务区域归属 |
| `HOME_REGION` | `Drone → Region` | 无 | 名字表示归属区，但当前实现在每次任务事件中连向“任务区域” |
| `CURRENTLY_IN` | `Drone → Region` | 无 | 名字表示当前所在区，但当前实现仍连向“任务区域”，没有按 `(x,y)` 判定 |

当前 Cypher 是：

```cypher
MERGE (r:Region {id: task.region_id, run_id: run_id})
MERGE (d)-[:HOME_REGION]->(r)
MERGE (d)-[:CURRENTLY_IN]->(r)
```

没有删除 drone 原先指向其他 Region 的边。因此在当前数据中，这两种边更接近“该 drone 曾经处理过该区域任务”，不宜直接解释为唯一归属区或实时所在区。真正的固定归属字段是 `Drone.region_id`/`AgentState.region_id`。

#### 3. Event 指向业务实体的关系

| 关系 | 方向 | 属性 | 用途 |
|---|---|---|---|
| `ABOUT_DRONE` | `Event → Drone` | 无 | 指向事件的主要 actor |
| `ABOUT_TASK` | `Event → Task` | 无 | 指向事件所涉及的任务 |
| `IN_REGION` | `Event → Region` | 无 | 指向任务所属区域 |
| `ABOUT_SOURCE_DRONE` | `Event → Drone` | 无 | 互助事件中的原/求助 drone |
| `ABOUT_HELPER_DRONE` | `Event → Drone` | 无 | 互助事件中的援助 drone；找到 helper 后才存在 |

普通派单、取货、完成事件会有 `ABOUT_DRONE + ABOUT_TASK + IN_REGION + IN_RUN`。

互助事件中：

- 没有 helper 的求助事件：`ABOUT_DRONE` 和 `ABOUT_SOURCE_DRONE` 都指向 source。
- 已有 helper 的事件：`ABOUT_DRONE` 指向 helper，同时 `ABOUT_SOURCE_DRONE` 指向 source，`ABOUT_HELPER_DRONE` 再指向 helper。

低电、返航、充电等纯 drone Event 只建：

```text
Event -[:ABOUT_DRONE]-> Drone
Event -[:IN_RUN]-> Run
```

这些 Event 没有 `ABOUT_TASK` 和 `IN_REGION`。因此使用 `(e)-[:IN_REGION]->(r)` 查询区域近期事件时，会漏掉纯 drone 事件。

#### 4. 任务生命周期关系

##### `ASSIGNED`

```text
Drone -[:ASSIGNED]-> Task
```

| 属性 | 含义 |
|---|---|
| `time_minute`, `time` | 最近一次该 drone-task 派单时间 |
| `active` | 派单是否仍有效 |
| `handover_time_minute` | 因交接/重派失效的时间，可选 |
| `completed_time_minute`, `completed_time` | 任务完成后关闭该关系的时间，可选 |

派单时 `active=true`。取货时不关闭，所以一个正在配送的任务可同时有 `ASSIGNED(active=true)` 和 `CARRYING(active=true)`。交接或完成时设为 `false`。

`MERGE (drone)-[:ASSIGNED]->(task)` 会将同一 drone-task 的多次派单压在同一条边上，`time*` 会被最新一次派单覆盖。完整派单历史应以 Event 为准。

##### `CARRYING`

```text
Drone -[:CARRYING]-> Task
```

| 属性 | 含义 |
|---|---|
| `active` | 该 drone 当前是否仍携带该任务货物 |
| `pickup_time_minute`, `pickup_time` | 取货时间 |
| `handover_time_minute` | 货物交给其他 drone 的时间，可选 |
| `completed_time_minute`, `completed_time` | 送达后关闭载货关系的时间，可选 |

取货时建立并设为 `active=true`；交接或完成时保留关系，但改为 `active=false`。

##### `COMPLETED`

```text
Drone -[:COMPLETED]-> Task
```

| 属性 | 含义 |
|---|---|
| `time_minute`, `time` | 完成时间 |
| `late` | 是否晚于 task deadline |

这是历史事实关系，没有 `active`；一旦任务送达就保留。

#### 5. drone 互助与交接关系

##### `ASSISTS`

```text
helper Drone -[:ASSISTS]-> source Drone
```

| 属性 | 含义 |
|---|---|
| `task_id` | 这次援助对应的任务，也参与 `MERGE` 区分关系 |
| `active` | 援助/交接流程是否仍在进行 |
| `reason` | `failure`、`low_battery`、`deadline_risk` 等 |
| `updated_at` | 最近互助事件时间 |

在 `assist_dispatched` 时设为 `active=true`，后续 `task_handover_completed` 或 `task_taken_over` 写入时设为 `false`。

##### `HANDOVER_TO`

```text
source Drone -[:HANDOVER_TO]-> helper Drone
```

属性与 `ASSISTS` 相同：`task_id`、`active`、`reason`、`updated_at`。`ASSISTS` 表达“谁援助谁”，`HANDOVER_TO` 表达“谁将货物/任务交给谁”，两者方向相反。

##### `TAKES_OVER`

```text
helper Drone -[:TAKES_OVER]-> Task
```

| 属性 | 含义 |
|---|---|
| `active` | helper 的接管是否仍有效 |
| `reason` | 接管原因 |
| `time_minute` | 首次创建该 helper-task 接管边的时间；通过 `coalesce` 保留首次值 |
| `handover_time_minute` | 后续再交给其他 drone 的时间，可选 |
| `completed_time_minute`, `completed_time` | 完成任务后关闭接管的时间，可选 |

当前在 `assist_dispatched` 阶段就建立 `TAKES_OVER(active=true)`，即它表示“已派出接管”，不严格等同于已在物理交接点取得货物。实际交接完成应结合 `task_handover_completed` Event 或 Task 字段判断。

任务再次交接时，前一个 helper 的 `TAKES_OVER` 会设为 `active=false`；任务完成时，当前 helper 的 `TAKES_OVER` 也会关闭。

#### 6. 正常配送和互助时的关系变化

##### 正常配送

```text
派单：
  Drone -[:ASSIGNED {active:true}]-> Task

取货：
  Drone -[:ASSIGNED {active:true}]-> Task
  Drone -[:CARRYING {active:true}]-> Task

完成：
  Drone -[:ASSIGNED {active:false}]-> Task
  Drone -[:CARRYING {active:false}]-> Task
  Drone -[:COMPLETED {late,...}]-> Task
```

##### 已取货任务交接

```text
调度援助：
  helper -[:ASSISTS {task_id, active:true}]-> source
  source -[:HANDOVER_TO {task_id, active:true}]-> helper
  helper -[:TAKES_OVER {active:true}]-> Task
  source -[:CARRYING {active:false, handover_time_minute}]-> Task
  source -[:ASSIGNED {active:false, handover_time_minute}]-> Task

援助 drone 到达交接点：
  ASSISTS.active = false
  HANDOVER_TO.active = false
  helper -[:CARRYING {active:true}]-> Task
  helper -[:TAKES_OVER {active:true}]-> Task

援助 drone 完成配送：
  helper.ASSIGNED.active = false
  helper.CARRYING.active = false
  helper.TAKES_OVER.active = false
  helper -[:COMPLETED]-> Task
```

未取货任务的重派不需要等待物理交接，`task_taken_over` 事件会很快把 `ASSISTS/HANDOVER_TO.active` 改为 `false`。

#### 7. 关系语义上需要注意的限制

1. **边存在 ≠ 当前有效。** 当前关系不删除，必须检查 `active`、`Task.status`、`Task.assigned_to`、`Task.onboard_drone_id` 等字段。
2. **关系边不是完整时序日志。** `MERGE` 会将同一对端点的多次 `ASSIGNED/CARRYING/TAKES_OVER` 压到同一条边，某些时间会被覆盖。完整历史以 Event 节点为准。
3. **`CURRENTLY_IN` 不是实时空间归属。** 它没有判断 drone 坐标落在哪个区域边界内。
4. **`HOME_REGION` 不一定唯一。** 跨区任务事件可以让同一 drone 连到多个 Region。
5. **Event 和 step 之间没有直接关系。** Event 通过 `time_minute/run_id` 与 step 对齐，并没有 `Event-[:IN_STEP]->Step`。
6. **Step 与 Drone 之间也没有直接边。** 需经 `Step <-[:IN_STEP]- AgentState -[:OF_DRONE]-> Drone` 连接，且前提是启用 AgentState。

#### 8. 独立规模基准数据的关系

`scripts/build_neo4j_scale_dataset.py` 额外引入 `Courier` 节点，其关系为：

| 关系 | 方向 | 属性 |
|---|---|---|
| `IN_RUN` | `Region/Courier/Task/Event → Run` | 无 |
| `BELONGS_TO` | `Task → Region` | 无 |
| `DELIVERED` | `Courier → Task` | 无 |
| `WORKS_IN` | `Courier → Region` | 无 |
| `IN_REGION` | `Event → Region` | 无 |
| `ABOUT_TASK` | `Event → Task` | 无 |
| `ABOUT_COURIER` | `Event → Courier` | 无 |

与主仿真合并看，仓库中可能出现的关系类型并集为 20 种；其中 `DELIVERED`、`WORKS_IN`、`ABOUT_COURIER` 仅来自该离线基准导入器。

### 后续建议

- 将 `HOME_REGION` 改为只根据 `drone.region_id` 建立一次，并保证每个 run 中每架 drone 只有一条有效归属边。
- 若需要真实 `CURRENTLY_IN`，应根据 drone 坐标与区域多边形判定，或将名称改成更符合现状的 `SERVES_REGION`。
- 统一所有“当前有效任务”查询，对 `ASSIGNED/CARRYING/TAKES_OVER` 明确过滤 `active=true`，并交叉验证 Task 当前状态字段。
- 若需要完整时序关系历史，可为每次分配/交接创建独立关系识别或独立业务节点，避免 `MERGE` 覆盖前一次时间。
- 如果希望按区域查全部事件，应为纯 drone Event 补齐 `IN_REGION`，或在查询中改用 `Event.region_id` 属性。
