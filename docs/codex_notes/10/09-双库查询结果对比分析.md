### 任务背景

用户分别对无实验索引的 `lade` 和带三组 AgentState RANGE 索引的 `lade-index` 执行了 100 并发、100 个 drone、每个 drone 重复 20 次、全部 i0—i11 查询的实验，希望分析 `/data/zc/datasets/LaDe/viewer/test` 中的性能和返回内容特点，并解释原因。

### 关键结论

- 实际文件名与数据库组别相反：`index_*` 文件记录的是 `bolt://127.0.0.1:57687`，即无实验索引的 `lade`；无前缀文件记录的是 `bolt://127.0.0.1:61687`，即有索引的 `lade-index`。
- 两组 JSONL 都追加了两轮完整实验。每轮有 2,000 个 context 和 24,000 次查询；两个 summary 只对应各自最后一轮。
- 有索引库的整轮墙钟时间在两轮中分别约快 11.05 倍和 9.15 倍，结论具有重复性。最后一轮吞吐从 90.916 QPS 提升到 832.190 QPS。
- 性能收益主要来自 i1、i6、i7、i8、i10、i11，这些查询直接或间接先检索百万级 `AgentState`；最后一轮平均耗时分别改善约 16.72、37.62、36.60、16.00、8.25、8.68 倍。
- 两库在每轮 2,000 个 context 中的实际 `queries` 返回值逐项完全一致，说明索引改变的是访问路径和速度，没有改变结果语义，两份数据具备对照可比性。
- i2 在两库、两轮中全部失败，每轮造成 2,000 次 `CypherSyntaxError`，所以每轮成功率只有 22,000 / 24,000 = 91.67%。原因是 Cypher 不支持 SQL 风格的 `BETWEEN` 写法。
- 返回内容存在明显时间语义混用：i0 读取当前 `Drone`，i1 读取 step 2300 的历史 `AgentState`；2,000 个重复 context 中有 1,980 个位置不同、460 个状态不同。i3 返回的 7,300 条 active task 全部在查询时刻 634 分钟之后才 release/建立关系。
- `--repeat 20` 得到 2,000 条 context，但数据库静态且参数相同，实际只有 100 份不同的 query payload；它增加的是延迟样本，不是上下文内容多样性。

#### 为什么 i0、i3、i4、i5 反而更慢

这四条查询分别读取 Drone、Drone→Task、Event、Event 聚合，不访问 AgentState，因此新增三组 AgentState 索引既不会直接帮助它们，正常情况下也不应改变它们的核心执行计划。

当前脚本不是让 12 类查询以固定到达率独立压测，而是启动 100 个 context worker；每个 worker 按 i0→i11 的固定顺序串行执行，完成整个 context 后才领取下一个 context。于是：

- 无索引库中的 i1、i6、i7、i8、i10、i11 很慢，充当了天然的“限流器”。worker 长时间卡在 AgentState 扫描，i0、i3、i4、i5 的后续调用被摊薄到约 264 秒内，进入服务器时往往很稀疏。
- 有索引库消除了这些扫描，2,000 个 context 在约 28.8 秒内完成。worker 很快循环到下一批 context，便宜查询形成更密集、更同步的请求波，客户端记录的 `elapsed_ms` 包含连接获取、Bolt 调度、服务器工作线程等待和 CPU 排队时间。

用“该查询全部 elapsed_ms 之和 / 整轮墙钟时间”估算平均同时处于调用中的数量：

| 查询 | 无索引组 | 有索引组 | 有索引组并发密度约为 |
|---|---:|---:|---:|
| i0 | 0.086 | 6.602 | 77× |
| i3 | 0.084 | 8.775 | 104× |
| i4 | 0.548 | 11.670 | 21× |
| i5 | 0.507 | 7.203 | 14× |
| i9 | 0.262 | 6.236 | 24× |

按每 100 个 context 的 repeat 波次统计也能看到这种差异：无索引组 i0 除第一波 52 ms 外，后续多数波次平均约 7—10 ms；有索引组 i0 各波平均约 70—150 ms。无索引组 i3 后续多数约 7—10 ms，有索引组约 86—153 ms。这说明观测值与请求波/排队强相关，而不是简单的索引查找成本。

还可能存在容器页缓存冷热、Neo4j 页面缓存分配、查询计划缓存、GC 和宿主机调度等次要因素。新增索引也会占用一定页面缓存，但当前日志没有 server-side profile 和资源指标，不能据此断言这是主要原因。

因此应区分两个结论：

- 如果问题是“构建一个完整 LLM context 的系统吞吐是否提升”，答案明确是提升约 9—11 倍。
- 如果问题是“i0 单独执行时，AgentState 索引是否让它变慢”，当前混合并发实验不能回答；必须给两库施加相同的 i0 到达率或单独压测 i0。

后续已完成受控验证，详见 `docs/codex_notes/10/09-非AgentState查询受控实验.md`。在只运行 i0/i3/i4/i5 的相同负载下，单并发两库基本一致；100并发两轮中有索引库平均吞吐反而高约11.6%。四条查询在两库的 `EXPLAIN` 计划完全相同且没有引用 AgentState 索引，确认原始巨大反向差异来自混合负载的排队/节流，而不是索引直接改变这四条查询。

### 性能特点产生的原因

`lade-index` 中的三组索引是：

```cypher
(run_id, drone_id, step_index)
(run_id, region_id, step_index)
(run_id, step_index)
```

- i1 通过 `run_id + drone_id` 定位 AgentState，再对 `step_index <= 2300` 排序取最新值。无索引时需要在百万级 AgentState 中扫描和过滤；复合索引可以把候选集缩小到单个 drone 的时间序列。
- i6、i7 先做与 i1 相同的历史 self 定位，再按 `run_id + region_id + step_index` 查询同区域状态。它们同时命中前两组索引，因此加速最大。
- i8、i10 的 Task/Event 部分不由这三组索引直接加速，但它们的第一步都要定位历史 self，避免 AgentState 全扫描后仍能得到明显收益。
- i11 先找 Step，再按 `run_id + step_index` 聚合 AgentState，第三组索引可以直接定位目标 step 的约 100 条状态，而不是扫描所有历史状态。
- i0、i3、i4、i5、i9 不访问 AgentState，理论上不会直接使用新增索引；它们的差异主要是混合并发负载效应。

第一轮无索引耗时约 307 秒，第二轮约 264 秒，改善约 14%；有索引两轮约 27.8 和 28.8 秒，相差约 4%。这说明缓存预热或宿主机状态会影响绝对值，但两轮都保持约一个数量级的总吞吐优势，索引收益不是单轮偶然值。四轮时间段没有重叠，未发现两个容器同时压测导致的直接资源争用。

### 返回内容特点

第 2 轮的 2,000 个 context 实际由 100 个 drone × 20 次重复组成：

| 查询 | 总返回行数 | 特点 |
|---|---:|---|
| i0 | 2,000 | 每个 context 1 条当前 Drone |
| i1 | 2,000 | 每个 context 1 条历史 AgentState |
| i2 | 0 | 2,000 次全部语法失败 |
| i3 | 7,300 | 平均 3.65 条；340 个 context 为 0，760 个为 6 条 |
| i4 | 11,000 | 平均 5.5 条，0—10 条不等 |
| i5 | 2,000 | 每个 context 1 条聚合结果 |
| i6 | 2,320 | 1 或 2 条区域状态聚合 |
| i7 | 2,000 | 每个 context 恰好 1 个同区域其他 drone |
| i8 | 0 | 所有 context 都没有符合时间窗口的开放任务 |
| i9 | 2,000 | 每个 context 1 条 Step 摘要 |
| i10 | 10,040 | 0—10 条区域事件，760 个 context 达到 LIMIT 10 |
| i11 | 20,000 | 每个 context 都达到 LIMIT 10 |

两库两轮均有 2,000/2,000 个 context 的 `queries` 内容完全匹配，返回行数也一致。这是合格 A/B 数据一致性的积极信号。

但上下文存在历史时间混用：

- step 2300 对应 `time_minute ≈ 634`。
- i1、i6、i7、i8、i10、i11以历史 AgentState/Step 为锚点。
- i0 直接读取当前 Drone 节点；2,000 个重复 context 中有 1,980 个的当前位置、`updated_at` 和总里程明显晚于/大于 step 2300 状态，460 个连 status 也不同。
- i3 直接读取当前 Drone→Task 关系和 Task 当前属性。它返回的 7,300 条任务，其 release 时间和关系时间全部晚于 context 的 634 分钟，属于从未来状态泄漏进历史 context。
- i8 带有 `release_minute <= 634` 的历史时间过滤，所以恰好全部返回空；这与 i3 返回大量未来任务形成明显语义冲突。

因此当前 context 适合测试查询系统性能，但不应未经说明地当作严格的 step 2300 历史决策上下文。

### i2 失败原因

i2 使用：

```cypher
WHERE a.step_index BETWEEN $start_step AND $step_index
```

Neo4j Cypher 2026.05.0 不接受这种 SQL 风格语法，应写成：

```cypher
WHERE a.step_index >= $start_step
  AND a.step_index <= $step_index
```

因为 i2 全部失败：

- 每轮失败率固定为 8.33%；
- trajectory 在所有 context 中为空；
- summary 的 QPS 分母包含这 2,000 次快速失败，而成功查询平均耗时不包含它们；
- 当前整体 QPS 和成功查询平均耗时使用了不同样本口径，需要在报告中注明。

### 后续建议

- 首先修复 i2 的 `BETWEEN` 语法，再重新跑一轮，否则无法衡量历史轨迹查询的索引收益。
- 清空或更换输出文件名后再跑，避免 JSONL 继续追加；文件名应明确使用 `noindex_*` 和 `index_*`，并在 summary 中增加 URI/容器名。
- 将 warm-up 与正式计时分开，至少交替执行多轮；分别报告高并发混合吞吐和低并发单查询延迟。
- 对 i1、i6、i7、i8、i10、i11 分别运行 `EXPLAIN`/`PROFILE`，确认有索引库使用 NodeIndexSeek/Range，基准库使用 Label Scan 或其他扫描算子。
- 对 i0、i3、i4、i5 分别做独立基准：先以 `--max-workers 1` 测纯查询延迟，再按 10、50、100 并发递增；两库必须使用完全相同的查询组合、到达节奏、预热步骤和输出轮次。建议采用无索引→有索引→有索引→无索引的 ABBA 顺序抵消时间漂移。
- 对 i0、i3、i4、i5 使用 `PROFILE` 比较执行计划和 DB Hits；若两库计划和 DB Hits 相同而客户端延迟不同，应重点检查排队、CPU、页缓存命中率和 GC，而不是把差异归因于 AgentState 索引。
- 明确实验是“当前态查询”还是“step 2300 历史回放”。若是历史回放，i0、i3 和 Task/Event 状态也需要按时间版本化或从截止时刻前的事件重建。
- i8 全为空时，性能数字只能代表空结果路径。若业务上期望有任务，应检查 step/time 与 Task 的时间基准是否一致；若空结果符合历史事实，则应修正 i3，避免把未来任务放入同一 context。
