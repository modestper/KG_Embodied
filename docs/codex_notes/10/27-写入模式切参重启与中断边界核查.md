# 写入模式在切参重启和突然中断时的边界

### 任务背景

用户追问新增 Ray / process 写入模式是否覆盖更改仿真参数、重启和突然中断。本文核对实际生命周期和持久化代码，区分正常结束、网页重启、强制终止与检查点恢复。本次只读核查并新增说明，没有修改业务代码或数据库。

### 关键结论

- 当前只完成了部分保护：正常关闭排空、写入错误上报、actor 回收和 headless 检查点边界；没有完整实现任意中断后的无损恢复。
- 网页切参、新 SSE 连接或重连会构建新环境，但显式配置的 KG_RUN_ID 会被复用。当前没有为每次网页重启分配独立运行身份。
- 使用 `s8010 1027_run` 时，后续网页切参仍使用 1027_run。唯一约束不会阻止同一身份被 MERGE 更新，旧 Step、任务和关系也不会自动清理。
- 进程强制终止时，内存队列中的未发送写入可能丢失；已发送而未确认的写入状态可能不确定。当前没有持久待发送日志和完整重放协议。
- 旧运行关闭与新请求之间没有完整的停止、等待退出和数据库写入代次隔离协议，不能保证复用 run_id 时绝不发生旧写入与新运行交叠。
- headless 的 --resume 与网页切参重启不同：它校验关键配置并恢复检查点，不能据此认为动态页面已经支持断点续跑。
- 现有异常测试验证的是写入副程序死亡后主进程能发现错误，不是主进程被杀后重启不丢数据、不串运行的端到端测试。

### 已有保护与缺口

| 情况 | 当前处理 | 保护边界 |
|---|---|---|
| 正常完成或显式 close | 确认待写入，关闭写入器与查询连接 | 确认成功时可以保证此前消息完成；错误或超时会报错 |
| 网页应用参数并重启 | 替换 active_env，调用旧环境 close，再构建新环境 | 未完整等待旧业务线程退出，固定 run_id 会复用 |
| process 副程序意外退出 | 主进程接收 EOF/失败，后续操作报错并回收子程序 | 不是自动恢复或重放未完成写入 |
| 主进程被强制终止 | 未建立专门的恢复协议 | 内存队列可能丢失；旧子程序或在途数据库事务仍可能处理片刻 |
| Ray actor 中途死亡 | headless 可尝试从检查点重建 actor | 不能将各 actor 的部分落库等同于整轮原子提交 |
| headless 同配置 --resume | 校验配置、Step/time 和检查点 | 只接受位置对齐或检查点恰好领先一步等既定情况 |

### 一、固定 run_id 的网页重启会混用运行数据

`KnowledgeWriterConfig.from_env()` 优先使用 KG_RUN_ID；只有未设置该变量时才生成新的 UUID。`args_from_request()` 接受城市、任务数、无人机数等参数，但没有为每次网页运行生成新的 run_id。

例如按当前代码推演：

```text
旧运行：run_id = 1027_run，已经写到 Step 1000。
网页改变任务数或无人机数，重新从 Step 1 开始。
新运行：仍然使用 1027_run。
Step 1 等相同身份节点可能被更新；旧高编号 Step 仍保留。
数据库 max(step_index) 仍可能指向旧运行的 Step 1000。
```

这不是唯一约束能够解决的问题。约束只保证同标签下的身份组合不重复，不判断两批实验参数是否一致，也不阻止更新已存在节点。

同样，旧任务、旧 Drone、已完成关系、ASSIGNED/CARRYING 等关联可能继续存在。部分旧节点可能被新状态覆盖，部分则保留，产生混合数据。稳定事件 ID 只对同一个逻辑执行的重试有帮助，不能把不同实验共用身份变成正确的运行隔离。

源码：`simulation/knowledge_writer.py:40`、`:45`，`scripts/run_dynamic_sim.py:155`、`:469`，`simulation/knowledge.py:293`。

### 二、关闭目前是尽力回收，不是完整重启协议

网页新连接调用 `replace_active_env(None)`，先改变 active_env 指针，再调用旧环境 close。主循环是在生成 SSE 事件后检查运行是否已被替换；事件生成过程中可能已经执行 step 或写入操作。

当前 active_env 的锁保护指针，没有覆盖整个环境构建与切换，也没有把旧运行线程 stop-and-join。多个请求同时启动还可能交错初始化。

Ray 环境批量请求 actor close，最多等待 5 秒，然后 kill。本机写入在 actor 方法内完成，但回收超时和在途数据库操作没有统一代次校验。

process 写入器设置 closing 后拒绝新写请求，并尝试排空；但环境与写入器的 close 仅有普通布尔标记，没有完整处理多个 HTTP 线程同时关闭同一运行的协议。Ray 协调写入器也没有全面的关闭并发保护。

源码：`scripts/run_dynamic_sim.py:330`、`:426`、`:458`，`simulation/ray_delivery_sim.py:366`，`simulation/knowledge_writer.py:186`、`:288`、`:348`。

### 三、强制终止与内存队列

process 模式的 Python 队列、待确认 Future 和管道缓冲都不是持久日志。主进程被杀后，尚未发送的消息无法由新进程找回；写入副程序可能继续处理管道中已到达的数据，随后因 EOF 退出。

Ray 模式中，actor 可能在收到关闭或死亡通知前后仍有写入在途。当前消息只有 run_id 和业务数据，没有 execution_id / writer_epoch 来区分旧实例与重启实例。

单条数据库事务的提交与整轮仿真是不同层次：已提交记录会留存，某个 actor 或某个事件写入方法的后续语句仍可能失败。不能把“主进程没有收到返回”理解为“这一轮什么都没写”，也不能认为这一轮已经完整写入。

代码没有针对 SIGTERM/SIGINT 建立完整的运行停止协议；SIGKILL 本身也无法依赖进程内 finally 清理来处理。动态服务 main 的 finally 只直接关闭 HTTP server 和手动查询服务，活动环境的关闭主要依赖请求线程 finally，不能承诺服务被打断时立刻完成安全收尾。

源码：`simulation/knowledge_writer.py:138`、`:269`，`simulation/knowledge_worker.py:12`、`:43`，`scripts/run_dynamic_sim.py:573`。

### 四、headless 恢复已有的范围

headless 会先排空相关写入，再保存检查点；本步 Step 随后提交。检查点使用 SHA-256、临时文件、fsync 与原子替换，恢复时检查 run_id、城市、日期、任务数、无人机数、时间步、seed、use_llm 等字段，并核对数据库 Step/time。

这有助于同一实验断点续跑，但不允许把修改城市、任务数或无人机数简单当作原实验恢复。写入模式等并未全部纳入关键配置签名，完整的跨模式故障恢复还没有专项验证。

动态页面没有自动接入这套检查点恢复；网页重连会新建仿真环境。数据库高编号 Step 留自旧运行时，headless 位置核对可能拒绝恢复，而不是自动清理或回滚图数据。

源码：`simulation/checkpoint.py:44`、`:114`、`:169`，`scripts/run_headless_sim.py:100`、`:284`，`simulation/ray_delivery_sim.py:465`。

### 后续建议

1. 明确区分“新实验”和“继续原实验”：改变任务或仿真参数默认新建 run；只有显式 resume 才复用原身份并校验配置。
2. 先串行化停止、退出等待和新环境启动，建立 RUNNING/STOPPING/STOPPED 等生命周期状态，并使 close 对并发调用安全。
3. 增加执行实例或写入代次，确保旧实例的消息不能更新新实例的有效状态。校验必须在正确的写入协议中生效，不能只在主进程内比较一个变量。
4. 如要求强杀后无损，增加持久待发送记录、确认进度与幂等重放；数据库查询只读取已提交版本。
5. 补充网页连续切参、断开重连、并发重启、主进程强杀、部分 actor 写成功和恢复时旧写入迟到的测试。

在这些改造完成前，当前使用 s8010 启动新实验应换新的 run 名称；同一个服务里的网页切参不会自动完成身份隔离。已有不满足唯一约束的历史数据仍需另行核查，换 run 名称不会绕过约束创建时的全库校验。
