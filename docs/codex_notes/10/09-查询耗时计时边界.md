### 任务背景

用户希望明确 `scripts/lade_llm_context_queries.py` 的查询测试究竟包含哪些阶段，尤关心连接池等待、Bolt 通信、Neo4j 服务器排队是否被计入，以及单条查询从什么位置开始计时。

### 关键结论

- 单条查询的 `elapsed_ms` 从调用 `session.run(...)` 之前开始，到结果被完整迭代、解码并转成 Python `dict` 后结束。
- 因此，连接池取连接的等待、必要时的 TCP/Bolt 建连与认证、Bolt 往返、服务器侧排队、解析/计划/执行、结果传输与客户端解码，都可能包含在 `elapsed_ms` 中。
- 当前日志只记录端到端总时间，无法从中分离出“连接等待多少毫秒”或“服务器排队多少毫秒”。
- `driver` 的创建和测试前的 `resolve_time_args()` 预查询不在 benchmark 计时中；预查询还可能预热一条连接。
- `driver.session()` 创建会话对象本身在单条查询计时之前，但 Neo4j Python Driver 通常在真正执行 `session.run()` 时才懒加载地从池中取物理连接，所以取连接/建连仍会落入 `elapsed_ms`。
- 单个 context 的 `total_elapsed_ms` 从工作线程真正进入 `execute_context()` 开始，不包含任务在线程池中等待调度的时间。
- 整轮 `wall_ms` 包含线程池排队、所有 context/查询、收集 future 和 JSONL 追加写入，但不包含最终 summary 文件的生成与写入。

计时时序如下：

```text
wall_start
  提交 job
  线程池等待                         [仅 wall_ms]
  context_start（工作线程开始）
    构造 context / 创建 Session 对象      [context]
    build_params                           [context]
    query_start
      连接池等待 / 必要时 TCP+Bolt 建连认证
      Bolt RUN/PULL 发送
      Neo4j 排队、解析/计划、执行
      结果经 Bolt 回传、Driver 解码、row_to_dict
    query_end                              [elapsed_ms]
    构造查询日志记录                    [context]
    关闭 Session / 归还连接              [context]
  context_end                              [total_elapsed_ms]
  收集 future、追加写 JSONL、输出进度   [仅 wall_ms]
wall_end                                   [wall_ms]
```

### 后续建议

- 若要区分“等待首个结果”与“传输全部结果”，可以在 `session.run()` 返回处和结果完全消费后分别打点。
- 可额外记录 Neo4j `ResultSummary` 中的 `result_available_after` 和 `result_consumed_after`，与客户端耗时对照。
- 如果需要独立量化服务器排队、CPU、页缓存或 I/O，还需同步采集 Neo4j 服务器查询日志/指标；仅依靠当前客户端 JSONL 无法准确拆分。
