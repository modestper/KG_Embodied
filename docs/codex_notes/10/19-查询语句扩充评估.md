### 任务背景

用户希望检查当前项目中的 Neo4j/Cypher 查询，并结合“百万级图数据、100 个以上智能体并发、时序知识图谱协同查询低于 500ms”的实际任务，判断能否把查询集合扩充到 50 条以上。项目原有两套不同用途的查询：`scripts/lade_cypher_benchmark.py` 内置 `q0-q12` 共 13 条通用压测查询；`scripts/lade_llm_context_queries.py` 内置 `i0-i11` 共 12 条 LLM 决策前置查询。两套查询不能简单相加当成一套统一 benchmark。

### 关键结论

- 可以扩充，而且已经把通用压测查询从 `q0-q12` 扩充为连续的 `q0-q55`，共 56 条；原有 13 条编号与用途保持不变。
- 新增 43 条查询覆盖全局快照、智能体时序、电量风险、区域态势、任务生命周期、事件统计、多智能体协助/接管、故障韧性和图数据质量，不是仅为达到数量而复制参数变体。
- 查询目录包含 19 个类别，并新增 6 个实用查询包：`smoke`、`online`、`analytics_suite`、`collaboration_suite`、`resilience_suite`、`quality_suite`；`all` 表示全部 56 条。
- 针对当前 Neo4j 环境曾不支持 `BETWEEN` 的历史问题，通用 benchmark 和 LLM 上下文查询 `i2` 的 Step 窗口均统一改为 `>=` 与 `<=`，查询语义不变。
- 56 条查询可以支撑“图 + 时序 + 多智能体并发”的工作负载设计，但当前 schema 没有向量、多模态内容或向量相似度查询，因此不能仅凭这 56 条声称已经覆盖项目中的“跨模态复杂查询 ≤200ms”指标。
- 查询数量也不是验收指标本身。正式验收仍需在标准化百万级数据集、云端/端侧指定硬件上，以 100 个以上客户端做至少 3 轮测试，统计平均值、p50/p95/p99、吞吐量、错误率和稳定性。
- 已通过 20 个相关单元测试、Python 编译检查、56 条模板连续编号/参数一致性/只读性检查，以及 112 个查询作业的 dry-run 参数生成检查。
- 已在 `bolt://127.0.0.1:57687` 的真实 Neo4j 上完成 `q0-q55` 全量只读 `EXPLAIN`，结果为 56/56 成功、0 条语法失败；随后实际执行 `smoke`，结果为 4/4 成功。
- 单次 smoke 实测中，`q1=21.138ms`、`q2=83.1ms`，但 `q0=1495.874ms`、`q13=1637.892ms`，四条平均 `809.501ms`。该库只有两个 LOOKUP 索引，结果说明点查尚可，而全局扫描/排序未满足 500ms；这不是正式三轮性能结论，但已经证明查询数量增加不等于性能指标达标。
- 当前 57687 的旧 run 只有 12 类关系，尚无 `ASSISTS`、`HANDOVER_TO`、`TAKES_OVER` 等新版协作关系，也缺少部分协作/故障属性；相关模板语法有效，但在旧 run 上会返回空或 `null`，应使用按当前代码重新生成的 run 做功能结果验证。

### 后续建议

- 在最终用于第三方测试的 Neo4j 实例上再次执行全量 `EXPLAIN`，因为本次已验证的是 57687 无实验索引库；随后用包含新版协作关系的真实 `run_id` 逐包核对返回结果。
- 不建议第一次就用 100 并发执行 `all`。`q21`、`q25` 是相邻状态自连接，`q52-q55` 是全局诊断查询，和在线低延迟查询的成本模型不同；应分包报告，避免一个总平均值掩盖差异。
- 正式 100 智能体测试优先使用 `online`，并确保 `drone-1` 到 `drone-100` 与目标 Step 确实存在；随后单独跑协作、分析和质量查询包。
- 继续保留 `i0-i11` 作为 LLM 决策前的真实在线上下文查询，不要用 56 条通用压测模板替代它们；通用 benchmark 和在线上下文应分别报告。
- 若要覆盖完整牵引性指标，下一阶段需要在 schema 中加入向量/多模态实体、嵌入版本和相似度查询，再设计“向量召回 + 图关系过滤 + 时间窗”的跨模态查询模板。
- 当前 `q0/q13` 的单次延迟已经超过 500ms，应优先评估 `Run.id`、`Step(run_id, step_index)` 等索引，并用 `PROFILE` 核对是否仍在做标签扫描和全量排序；创建索引属于数据库写操作，本次未执行。
