# 援助无人机选择逻辑

### 任务背景

用户希望了解当前无人机互助中，系统如何从全部 drone 中筛选并选出援助 drone。

### 关键结论

- 援助选择由 `select_assistance_drone()` 执行，不调用普通拍卖协调器或 LLM。
- 候选者必须不是当前求助 drone，也不能是该任务的历史经手 drone。
- 候选者必须未故障、队列未满，且不处于 `failed/charging/returning`。
- 援助选择有独立电量过滤：必须能完成自身已有任务、再完成援助任务、再飞往最近 depot，并保留安全余量。
- 区域不是硬限制；会全城候选，但在时效结果相当时优先同区域 drone。
- `deadline_risk` 求助只接受能在 deadline 前完成的援助者；`failure/low_battery` 情况可接受超时援助者，但优先选不超时或超时更少的。

候选者的硬过滤顺序：

1. 排除 `source_drone` 和 `task.previous_assignees` 中的所有 drone，防止任务在历史执行者之间来回转派。
2. `drone.can_accept()` 必须为真：无故障、`queue < queue_capacity`、不在 `failed/charging/returning`。
3. 剩余电量必须满足：

   ```text
   预计完成候选 drone 已载货任务的路程
   + 预计完成其已排队任务的路程
   + 援助任务的取货/交接与送达路程
   + 援助任务送达点到最近 depot
   + safety_buffer_m
   ```

4. 如果求助原因是 `deadline_risk`，候选 drone 的预计完成时间必须 `<= task.deadline_minute`。

通过硬过滤后，系统按以下 tuple 从小到大排序：

```python
(
    completion > deadline,          # 1. 优先不超时
    max(0, completion - deadline),  # 2. 若超时，优先超时更少
    drone.region_id != task.region_id, # 3. 优先同区域
    completion,                     # 4. 优先预计更早完成
    len(drone.queue),               # 5. 优先队列更短
    drone.drone_id,                 # 6. 最后按 ID 字符串稳定打破平局
)
```

这意味着：

- “能否准时完成”优先于“是否同区域”。
- 一架能准时完成的跨区 drone，会优先于一架会超时的同区 drone。
- 如果多架 drone 都能准时完成，则先选同区 drone，然后才比较谁完成得更早。
- 系统并不直接选“几何距离最近”的 drone；距离通过预计路程和完成时间间接体现。

如果没有候选者，函数返回 `None`：原任务不会被从 source drone 移除，后续 step 会继续尝试寻找援助，且原 drone 仍会保留并继续执行它的任务。

已取货任务在选择 helper 前，会把 source drone 当前位置改成临时取货/交接点；未取货任务仍使用原 region depot 作为取货点。因此 helper 的电量和完成时间估算会随交接位置变化。

需要特别注意：当前 `DroneAgent.can_accept_task()` 和 Ray proxy 的同名方法中，原有普通派单电量判定已被注释，现在只返回 `can_accept()`。因此：

- **援助 drone 选择**仍然有 `required_battery_for_projected_task()` 独立电量硬过滤。
- **普通新任务派单**当前并没有通过 `can_accept_task()` 硬性拒绝电量不足的 drone。

### 后续建议

- 先确认“普通派单电量判定被注释”是否为当前期望设计，它与“已完善派单电量判定”的理解不一致。
- 如果希望更追求最早完成，可将“同区域优先”放到 `completion` 之后；当前是只要都不超时，同区 drone 即使更慢也优先。
- 为援助估算增加充电等待、交接同步和批量取货影响，可进一步减少预计与实际执行的偏差。
