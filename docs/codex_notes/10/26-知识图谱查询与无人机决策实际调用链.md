# 知识图谱查询与无人机决策的实际调用链

分析日期：2026-10-26。依据当前工作区源码及模拟依赖验证。

### 任务背景

核对项目中的知识图谱查询是否真正接入仿真，以及中央进程给无人机派单、重派和互助时使用哪些数据，避免把“写入图谱”“具备查询脚本”和“决策依赖查询结果”混为同一件事。

### 关键结论

- 查询知识图谱的代码有真实调用路径，但是否进入派单闭环取决于调度方式与存储后端。
- 动态启动脚本默认 `USE_LLM=0`，采用 `AuctionCoordinator + RuleBasedPlanner`。正常派单读取内存任务和 Agent 状态；Neo4j 即使启用，也主要接收该流程的结果写入。
- 启用区域 LLM 时，`RegionLLMCoordinator` 调用 `query_region_context()`；使用 Neo4j 后端时，区域近期表现和近期事件会实际通过 Cypher 读取，再加入模型输入。
- 任务与 Agent 候选仍从运行环境传入的内存对象中筛选，没有从 Neo4j 全量恢复这些实时对象再派单。
- 独立的 `q0–q55`、`i0–i55` 查询套件和手动查询面板，没有自动成为中央调度的检索步骤。
- 互助决策与 Agent 的取送货执行继续使用确定性规则；启用 LLM 不会把这些行为全部交给模型。
- 使用 fake Neo4j 和 fake LLM 推进四种配置各一步，确认规则模式没有上下文查询，区域 LLM + Neo4j 模式产生两次历史事件读查询，并把 `kg_context` 放入模型请求。
- 当前可见 `/proc` 范围未发现相关入口进程。本次证明的是实现中的调用关系，没有对某次正在运行的实验做数据库查询审计。

### 一、不同配置的实际行为

以下表格只讨论正常任务派单，不包含初始化索引检查、断点恢复检查和用户手动查询。

| 调度方式 | 存储后端 | 派单前读取什么 | 派单是否执行 Neo4j 读查询 |
|---|---|---|---|
| 规则拍卖 | memory | 当前任务、Agent 状态 | 否 |
| 规则拍卖 | neo4j | 当前任务、Agent 状态；结果另外写图 | 否 |
| 区域 LLM | memory | 当前任务、Agent 状态及内存历史摘要 | 否，历史来自内存 |
| 区域 LLM | neo4j | 当前任务、Agent 状态及数据库历史摘要 | 是，区域表现和近期事件两类查询 |

启动入口会影响默认配置：`run_local_sim.sh` 和 `run_ray_sim.sh` 默认不启用 LLM；headless 也默认不启用 LLM，但知识后端默认 Neo4j。离线 `build_delivery_sim.py` 没有调用 Neo4j 存储工厂，默认使用内存知识存储；`generate_res.sh` 则默认请求区域 LLM。

所以“开了 Neo4j”和“有图查询参与决策”是两个独立条件。判断具体一次实验时，需要核对实际 coordinator 类型、知识后端以及模型调用是否成功，不能只看数据库里有没有新增数据。

### 二、主进程的默认派单依据

调用链：

```text
SimulationEnv / RaySimulationEnv.release_and_assign()
  → 先执行 coordinate_assistance()
  → 选出已释放且 status=waiting 的任务
  → AuctionCoordinator.assign()
  → 筛选可接单 Agent，同区域优先
  → RuleBasedPlanner.estimate_cost()
  → 最小成本者接单
  → 记录派单事件
```

任务来源是启动时加载的 CSV 及其后续内存状态；Agent 来源是本地对象或 Ray actor 返回的快照。环境对任务按释放时间和任务 ID 排序，规则拍卖逐个处理可派任务，是贪心分配。

候选筛选检查故障标记、当前状态和任务队列容量；同区域没有候选时才考虑其他区域。当前 `can_accept_task()` 中的电量硬校验已被注释，电量在普通规则派单中主要体现为成本惩罚。

当前规则成本：

```text
cost = 当前位置到取货点距离 + 取货点到目的地距离
     + 队列长度 × 1500
     + max(0, 预计完成时刻 - 截止时刻) × 250
     + 跨区域惩罚
     + max(0, 所需电量 - 剩余电量) × 10

跨区域惩罚 = 25000；同区域或未绑定区域时为 0。
预计完成时刻 = 当前时刻 + 本次取送距离 / 速度。
```

这条规则没有读取历史完成率、历史事件或 AgentState 数据库快照。普通成本中的预计完成时间也不是完整队列路线模拟。

源码位置：`simulation/delivery_sim.py:387`、`:665`，`simulation/planner.py:11`。配置选择见 `scripts/run_dynamic_sim.py:275`。

### 三、LLM 模式下图查询如何进入决策

调用链：

```text
RegionLLMCoordinator.assign()
  → region_context()
  → knowledge_store.query_region_context()
      ├─ 从传入的内存任务筛选最紧急任务
      ├─ 从传入的 Agent 筛选候选
      ├─ recent_agent_performance()
      └─ recent_events()
  → build_request(..., context=context)
  → HTTP 调用模型
  → 解析 assignments，检查 ID 和当前接单条件
  → 执行派单
```

`query_region_context()` 定义在内存存储父类中。Neo4j 后端继承该方法，并覆盖两个历史读取方法，因此同一段上下文构建代码在 Neo4j 配置下会执行数据库查询。

两次 Cypher 读取限定当前 `run_id`、区域与时间窗口，默认查看最近 30 分钟：

1. `recent_agent_performance()`：按 Agent 统计分配数、完成数、迟到数。
2. `recent_events()`：读取最近事件，默认最多 20 条。

任务默认最多 20 个，按截止时间等条件筛选；Agent 默认最多 10 个，按队列长度、到 depot 的距离等筛选。注意这里候选来自当前内存状态，数据库主要补充历史。

模型请求包含：

```text
time / region_id / depot / objective
tasks: 任务 ID、截止时间、目的地、取送距离
drones: Agent ID、位置、队列长度、到 depot 距离、完成数量
kg_context:
  recent_agent_performance
  recent_events
```

因此可以确认历史查询结果有被送入模型；现有实现没有对照实验可以证明模型在每次决定中确实利用了这些历史，或因此改善了派单。日志中的请求、响应和最终决策可用于进一步验证。

模型调用、响应解析或应用决策发生异常时会尝试规则回退。不过 `region_context()` 位于该 `try` 之前，所以数据库上下文查询本身报错时，并不被这段模型回退逻辑捕获。

另有可选 `LLMPlanner`，用于单 Agent / 单任务估价；它本身没有知识图谱检索。不能把所有名为 LLM 的模式都理解为相同的区域知识增强路径。

源码位置：`simulation/planner.py:136`、`:175`、`:199`，`simulation/knowledge.py:155`、`:833`、`:862`。

### 四、互助与无人机执行依据

互助在新任务派单前运行，其输入仍是当前内存状态或 actor 快照：

- 触发条件：故障、完成当前货物并安全返航的电量不足、预计截止时间风险。
- 援助者筛选：排除当前与历任执行者，检查容量、预计路线电量及必要的时效条件。
- 援助者排序：是否迟到、迟到程度、区域、预计完成时间、队列长度等。
- 执行结果：未取货任务重派；已取货任务保存交接坐标，由援助机前往取货。

该流程调用 `assistance_reason_for()`、`select_assistance_drone()` 等函数，不查询 Neo4j 来寻找援助者；知识存储接收求助、派援和接管事件。

接到任务后的移动和访问顺序也由规则执行：先在当前位置取可取的货，在手任务按截止时间优先，没有在手货物时寻找队列中的未取货任务；低电返航选择最近的配置 depot。这些行为不是每步请求 LLM 规划航线。

Ray 模式中主进程通过 `_sync_drones()` 取得 actor 快照，中央协调器完成派单，再通过 actor 的 `assign.remote()` 确认。actor 负责自己的取货、移动和送达，主进程合并返回状态与事件。

源码位置：`simulation/delivery_sim.py:378`、`:478`、`:540`，`simulation/ray_delivery_sim.py:456`、`:519`、`:652`。

### 五、已有查询功能与决策闭环的区别

| 查询入口 | 是否实际可调用 | 是否自动参与派单 |
|---|---|---|
| 区域历史表现与事件读取 | 是，区域 LLM 模式触发 | 是，以 prompt 上下文形式参与 |
| 手动图查询面板 | 是，由用户提交请求 | 否，返回结果供页面查看 |
| 通用 `q0–q55` 模板 | 是，独立脚本调用 | 否 |
| 决策上下文 `i0–i55` 查询 | 是，独立脚本调用并生成上下文 | 否，当前调度器没有调用这些脚本 |
| headless 恢复的 `latest_step()` | 是，恢复时用于核对数据库位置 | 用于恢复一致性，不是任务选择 |
| AgentState 写入 | 是，按配置启用 | 正常派单没有从这些快照重建实时 Agent |

因此，当前已接通的是“区域历史事件摘要 → LLM 输入”的有限知识增强。更完整的“每个无人机先查询自己的知识上下文，再决策并执行”的闭环仍需将 `i` 系列检索服务接到调度入口。

### 执行过的操作

- 用 `rg -n` 搜索知识读取、调度工厂、查询套件和上下文调用。
- 用 `nl -ba`、`sed -n` 核对 `simulation/planner.py`、`knowledge.py`、`delivery_sim.py`、`ray_delivery_sim.py` 及动态、headless、离线入口的实际代码。
- 只读扫描 `/proc` 的命令行，匹配相关入口名称；仅提取白名单配置，不输出凭证。扫描结果未发现匹配进程。
- 通过 `PYTHONDONTWRITEBYTECODE=1 ./run_in_lade.sh python -` 执行四配置调用验证；Neo4j 使用已有测试中的 `FakeNeo4jDriver`，模型使用固定 JSON 响应函数。

验证场景均为单区域、单任务、单 Agent，推进一步：

| 调度 / 后端 | 区域上下文调用 | Neo4j 历史事件读调用 | 模型调用 | 请求包含 kg_context |
|---|---:|---:|---:|---|
| 规则 / memory | 0 | 0 | 0 | 不调用模型 |
| 规则 / neo4j | 0 | 0 | 0 | 不调用模型 |
| 区域 LLM / memory | 1 | 0 | 1 | 是 |
| 区域 LLM / neo4j | 1 | 2 | 1 | 是 |

两个 Neo4j 场景的 fake driver 还各记录 9 次写入语句调用，说明“有图写入”确实不代表“有图读取用于派单”。这一数字只属于该最小场景，不是通用写入开销。

上述所有断言通过，没有连接真实数据库或模型，没有启动仿真服务，没有改变实验状态。这些结果验证调用路径，不代表真实模型的决策质量或真实数据库查询性能。

### 后续建议

1. 对具体实验记录实际 coordinator、planner、知识后端和模型是否使用回退，避免只凭启动意图判断模式。
2. 如果研究目标要求图谱参与规则决策，应将所需历史或协作查询显式接入规则策略；当前普通派单与互助没有这条读取路径。
3. 如果需要完整的知识增强模型闭环，将选定的 `i` 查询封装为上下文服务接入决策，记录检索、推理和执行的各自耗时与决策来源。
4. 如需评估图谱的贡献，固定任务、随机种子和模型参数，对比无历史、内存历史和 Neo4j 历史条件下的派单行为与业务指标。
