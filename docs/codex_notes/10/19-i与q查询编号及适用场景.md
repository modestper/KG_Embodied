### 关键结论

- 用户记忆正确：`i0-i11` 定义在 `scripts/lade_llm_context_queries.py`，是智能体调用 LLM 前读取知识图谱上下文的即时查询。

- 编号不是从 `i` 改成了 `q`，而是项目中本来就同时存在两套相互独立的编号体系。
- 上次根据“扩充查询语句”和项目的百万节点、100 智能体并发指标，默认选择了通用 benchmark 作为扩充对象。如果用户原意是扩充 LLM 决策前的 `i*` 查询，这一默认理解确实偏离了目标。

### 修改内容

本次仅新增本文档，用于说明两套查询编号和适用场景。

#### 一、`i0-i11`：LLM 决策前即时上下文查询

入口：`scripts/lade_llm_context_queries.py`。

这些查询以某一架 drone、某个 step 和当前时间为中心，结果会被组织为 LLM 上下文。重点是“当前智能体现在需要知道什么”。

| 编号 | 含义 | 适用情景 |
| --- | --- | --- |
| `i0` | 读取 Drone 当前属性，包括状态、位置、队列、载货、电量和里程 | LLM 每次决策前确认自身当前状态；实时模式 |
| `i1` | 读取不晚于指定 step 的最新 AgentState | 历史 step 回放；避免只依赖不断更新的 Drone 当前快照 |
| `i2` | 读取自身最近若干 step 的轨迹、状态、队列和电量 | 给 LLM 提供短期记忆；判断最近是否移动、耗电或持续繁忙 |
| `i3` | 读取当前已分配或正在携带、尚未完成的任务 | 决定继续取件、配送、等待还是请求协助 |
| `i4` | 读取当前智能体近期参与的事件 | 告诉 LLM 刚发生过分配、取件、完成、低电量或协助事件 |
| `i5` | 汇总近期分配、取件、完成和迟到次数 | 用紧凑统计代替大量事件明细，适合 prompt 控长 |
| `i6` | 读取当前区域、当前 step 的智能体状态和负载分布 | 判断所在区域是否繁忙、空闲智能体是否充足 |
| `i7` | 读取同区域其他智能体的位置、队列、电量和状态 | 选择协作对象、避开过载智能体、发起任务接管 |
| `i8` | 读取当前区域内已释放、未完成且临近截止的任务 | 发现紧急任务、辅助重新调度 |
| `i9` | 读取最新全局 Step 汇总 | 让 LLM 了解全局完成数、未完成数和各状态智能体数量 |
| `i10` | 读取当前区域近期事件 | 判断局部是否出现拥堵、集中完成、故障或协助需求 |
| `i11` | 聚合当前 step 各区域的队列、电量和状态瓶颈 | 从全局角度识别最拥堵或风险最高的区域 |

现有查询包：

- `core`：基础自我状态、当前任务、近期事件、区域负载和全局态势。
- `decision`：面向一次完整动作决策，加入短期轨迹和区域紧急任务。
- `coordination`：面向多智能体协同，侧重邻居、区域和全局瓶颈。
- `diagnostic`：面向问题排查，侧重轨迹、事件、表现和系统摘要。
- `all`：执行全部 12 条；适合功能验证，不一定适合高频在线调用。

#### 三、两套查询应该如何选择

| 目标 | 应使用的查询 |
| --- | --- |
| 智能体调用 LLM 前取得上下文 | `i*` |
| 验证知识图谱是否正确写入 | `q0`、`q52-q55` |
| 测单条在线查询延迟 | `i*` 或 `q2/q3/q5/q6` |
| 做百万节点数据库综合性能测试 | `q*` |
| 做 100 智能体真实并发决策查询 | 以 `i*` 查询包为主 |
| 做复杂聚合、路径和数据库极限压力测试 | `q7-q12`、`q21/q25`、`q35-q48` |
| 给 LLM prompt 填充内容 | 只选择结果短、语义直接的 `i*`；不要直接塞入全部 `q*` 结果 |

### 后续建议

- 如果用户原本想扩充的是 `i0-i11`，下一步应先定义智能体真正需要的新知识上下文，例如故障诊断、协助候选、任务接管、能量安全、历史结果反馈，再新增 `i12` 之后的即时查询。
- 即使候选查询达到 50 多条，也应设计按决策阶段选择的查询包；每次调用 LLM 前固定执行全部 50 多条会显著增加数据库负载、上下文长度和决策延迟。
- `q0-q55` 可以保留作为第三方性能测试和数据库诊断工作负载，不需要因为目标转回 `i*` 就删除。
- 在继续修改前，需要用户确认目标是哪一种：扩充“性能测试查询目录”，还是扩充“LLM 前置即时查询目录”。
