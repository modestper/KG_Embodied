# i 系列扩充：面向 drone 调用 LLM 前的知识上下文

> 修订提示：本文记录最初扩充版本，其中协作/交接等查询依据写入代码能力，未与当前入库数据充分区分。当前目录已按真实图谱改为 `i56-observed-graph-v2`，仍为 56 条，但部分编号含义和测试方式已变化。请以 [现有图谱结构修订说明](20-i查询按现有知识图谱结构修订.md) 为准；下文保留为历史记录，不应继续作为当前目录定义。

### 任务背景

用户要求扩充 i 系列查询，并与当前 drone 仿真的实际场景和需求连贯衔接。沿用前面提出的“50 多条查询”目标，本次将 `i0-i11` 扩充为 `i0-i55`，共 56 条。新增内容围绕 drone 的状态判断、任务处理、电量安全、请求协助、承担协助、实物交接、结果反馈组织。

这次扩充的是 `scripts/lade_llm_context_queries.py` 使用的即时上下文目录。查询结果仍由现有 context 执行器组织并计时，本次不改变仿真调度策略或 LLM 请求流程。

### 关键结论

- 当前共有 56 条 i 查询，连续编号 `i0-i55`；新增 44 条全部带 `run_id` 和 `drone_id`，从当前智能体的自身、任务、伙伴和所在区域出发。
- 原有 `core`、`decision`、`coordination`、`diagnostic` 查询包保留原编号选择与顺序；`all` 扩为 56 条。新增 9 个情景包，每包 6–10 条，按当次决策需求选择。
- 新增模板共同使用现有 `Drone/AgentState/Task/Event/Region` 与任务、协助关系，不引入虚构的图谱实体或事件；协助请求使用写入端真实的 `task_assistance_requested`。
- 普通入口、single 入口和分阶段计时入口均能使用扩展目录。新增模板集中维护在同一个模块，返回结果、JSONL 日志及上下文指标仍沿用现有结构。
- 查询元数据和执行结果增加 `temporal_scope`，区分当前态、历史快照和事件窗口。当前 Task/Drone 属性没有被冒充成历史版本，历史回放仍需专门的数据版本设计。
- 电量和协助信息与当前任务链衔接：取件点考虑 handover 坐标，返航考虑最近已知 depot 与安全余量，任务级 helper 估算排除原承担者并检查已知容量/电量；直达估算明确不代表完整队列可行性。
- 已完成本地回归、CLI 参数检查、Neo4j EXPLAIN 及事务内真实场景验证；具体计数与验证范围见本文“验证结果”。测试使用随机 run_id，事务结束后回滚。
- 当前目录适用于决策前的知识获取，不代表已达到 100 并发或 500ms 指标。实际 LLM 接入与正式性能测试仍是后续独立步骤。

### 一、怎样保持场景连贯

新增查询沿着以下决策链组织：

```text
判断信息是否够新、能力限制是什么
  i12 / i13 / i55
        ↓
确认自己的任务、目标位置、截止风险
  i18–i25
        ↓
检查电量、返航点、单任务航程需求
  i38–i43
        ↓
需要帮助：看请求、派遣、候选与任务级估算
  i26 / i27 / i32 / i33 / i34 / i35 / i50
        ↓
完成任务接管或实物交接
  i19 / i28 / i29 / i36
        ↓
追踪任务是否完成、协作是否得到结果
  i30 / i37 / i51 / i54
```

局部负载与故障信息由 `i44-i49` 提供，近期状态记忆由 `i14-i16` 提供，当前态与历史快照的差异由 `i52/i53` 补充说明。

每次根据情景选一个包，或组合少量查询；不需要每次 LLM 调用前执行全部 56 条。

#### i32-i37：helper 候选与协作承诺

| 编号 | 名称 | 决策前回答的问题 |
| --- | --- | --- |
| `i32` | `self_nearby_available_helpers` | 在同一实际快照中，半径内有哪些已知容量可用、状态允许的智能体？ |
| `i33` | `self_task_helper_route_estimates` | 针对我的具体任务，哪些 helper 的直达取送及返航航程符合已知电量，且不是原承担者？ |
| `i34` | `self_cross_region_helper_candidates` | 邻近其他区域有哪些可进一步评估的 helper？ |
| `i35` | `self_active_assigned_helpers` | 当前谁还在协助我，关联哪项未完成任务？ |
| `i36` | `self_active_help_commitments` | 我已承诺协助谁，不能忽略哪项任务？ |
| `i37` | `self_recent_collaboration_partners` | 我最近与哪些伙伴共同处理过任务？ |

`i32/i34` 使用相同 resolved_step 的状态，计算真实坐标距离，排除自身、已知故障和队列已满者；容量配置来自 Drone，前提是同一 run 内配置稳定。

`i33` 进一步使用当前任务、当前 helper 配置与位置，排除 `previous_assignees`，检查单任务取件→投递→最近已知 depot→安全余量的航程，并返回直达完成时间估算。helper 已有队列的绕行没有包含，返回字段明确标记 `individual_direct_route_not_full_queue_feasibility`，不能代替仿真的完整 `select_assistance_drone()` 评估。

`i35/i36` 除检查 ASSISTS.active，还核对 Task 未完成及当前 owner，防止把已经完成或已转交的旧协助边当成当前承诺。

#### i38-i43：电量安全与返航

| 编号 | 名称 | 决策前回答的问题 |
| --- | --- | --- |
| `i38` | `self_known_depot_return_margin` | 按当前位置与最近已知 depot，电量是否已经接近返航阈值？ |
| `i39` | `self_reachable_known_depots` | 加上安全余量后，哪些已知 depot 仍可到达？ |
| `i40` | `self_individual_task_energy_estimates` | 单独完成我的每项任务并返航，需要多少最低航程？ |
| `i41` | `self_recent_charge_cycle_events` | 最近是否发生低电量、返航或充电完成？ |
| `i42` | `self_observed_battery_changes` | 相邻状态中观察到了多少电量下降和恢复？ |
| `i43` | `self_last_known_charge` | 截至当前时间，上一次已知充电是什么时候？ |

`i38` 对齐当前返航判据的形式：

```text
已知返航阈值 = max(最低电量阈值, 距最近已知 depot 的距离 + 安全余量)
返航余量 = 当前剩余航程 - 已知返航阈值
```

Region 的 depot 坐标来自已有图谱写入；它们未必覆盖仿真内所有可用充电点，尤其尚未入图的区域。因此字段明确标记 `known_graph_depots_only`，不会声称与完整仿真 depot 列表绝对一致。缺少 depot 或关键安全配置时，阈值/余量可返回 null，表示未知。

`i40` 与 i33 一样是单任务直达估算。`i42` 只统计相邻 step 对的净电量变化，不从缺失样本推导真实累计能耗；充电与耗电在同一步发生时，净变化也无法还原全部动作。

#### i44-i49：以自己为中心的局部态势

| 编号 | 名称 | 决策前回答的问题 |
| --- | --- | --- |
| `i44` | `self_region_known_task_pressure` | 我当前区域里已知未完成、逾期和求助任务有多少？ |
| `i45` | `self_region_available_queue_capacity` | 我的区域里，其他智能体还剩多少已知可用队列容量？ |
| `i46` | `self_region_recent_completion_quality` | 所在区域近期完成量与迟到比例如何？ |
| `i47` | `self_region_recent_assistance_pressure` | 所在区域近期有多少请求、派遣和交接事件？ |
| `i48` | `self_nearby_known_unassigned_tasks` | 我附近有哪些图谱已知、已释放而尚未分配的紧急任务？ |
| `i49` | `self_nearby_failed_peer_states` | 同一快照中，附近有哪些故障智能体可能需要帮助？ |

这组查询均从自身所在区域或位置出发，没有搬入全 run 无关报表。`i44/i48` 只能查图谱已经知道的任务；当前写入方式主要在事件发生后建立 Task，因此未写入图谱的等待任务不能凭此发现。

#### i50-i55：结果反馈与决策数据就绪

| 编号 | 名称 | 决策前回答的问题 |
| --- | --- | --- |
| `i50` | `self_assistance_response_evidence` | 每次求助多久获得派遣？请求是否已被后续请求取代？ |
| `i51` | `self_helped_task_completion_feedback` | 我接管的任务有没有产生完成事件，由谁完成？ |
| `i52` | `self_current_snapshot_comparison` | 当前 Drone 属性和目标 step 快照是否不同，是否存在时间混用？ |
| `i53` | `self_recent_snapshot_coverage` | 我的近期记忆窗口有多少不同 step 样本，缺少多少？ |

`i50` 把每次请求与其后、下一次请求前的首个派遣匹配，输出 dispatched/superseded/awaiting_dispatch。没有观察到派遣表示截至时间窗内未观察到，并不等同于已写出的“协助不可用”事件。

### 三、情景查询包与调用方式

原有包保持选择不变：`core` 7 条、`decision` 9 条、`coordination` 5 条、`diagnostic` 7 条。新增包如下：

| 包名 | 条数 | 使用时机 |
| --- | --- | --- |
| `task_decision` | 9 | 决定接下来处理哪项取件、交接或投递任务 |
| `energy_safety` | 8 | 判断继续执行、返航、充电或求助 |
| `request_help` | 10 | 自身故障、电量或截止风险触发求助 |
| `provide_help` | 8 | 评估自己的能力、承诺和附近求助环境 |
| `handover` | 9 | 跟踪待交出、待接管和完成反馈 |
| `recovery` | 9 | 故障、停滞、逾期等异常处置前 |
| `memory_review` | 9 | 需要短期记忆、协作经验和历史执行反馈 |
| `local_awareness` | 8 | 需要自身区域的供需、事件和邻近状态 |
| `data_readiness` | 6 | 先确认数据是否存在、新鲜且足够支持决策 |

原有选择机制仍支持单条、连续范围、类别和组合包，并自动去重，例如：

```text
--queries i26
--queries i12-i25
--queries request_help
--queries request_help,energy_safety
```

组合包可能超过单包 10 条，应按实际需要控制总查询数和上下文长度；all 用于目录验证和专项测试，默认仍是 core。

```bash
# 查看 56 条模板、时间语义和查询包
./run_in_lade.sh python scripts/lade_llm_context_queries.py --list-queries

# 离线检查求助包参数，不访问数据库
./run_in_lade.sh python scripts/lade_llm_context_queries.py \
  --run-id validation-run --drone-id drone-7 \
  --step-index 2300 --time-minute 634 \
  --queries request_help --radius-m 5000 --dry-run

# 在目标查询库获取某个 drone 的求助上下文
./run_in_lade.sh python scripts/lade_llm_context_queries.py \
  --uri bolt://127.0.0.1:57687 --database neo4j \
  --run-id <RUN_ID> --drone-id drone-7 --step-index <STEP_INDEX> \
  --queries request_help --radius-m 5000 --max-workers 1
```

最后一个例子的 run 与 step 需替换成实际值；涉及时间的查询会按原逻辑从 Step 解析 time_minute。当前态查询应与实际最新决策时刻配合使用，旧 run 或没有协助事件的 run 可能返回空。

需要分阶段计时，可将入口换成 `scripts/lade_llm_context_queries_stages.py`，同样支持新目录和新参数。single 入口保持与主入口一致，文件名本身仍不强制单线程。

### 四、新增参数与时间语义

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `--radius-m` | 5000 | 邻近 helper、任务和故障状态的查询半径，米 |
| `--min-battery-m` | 0 | helper 候选的最低剩余航程筛选；不替代任务级航程评估 |
| `--max-state-age-steps` | 10 | 快照新鲜度允许的最大 step 年龄 |
| `--movement-epsilon-m` | 1 | 近似静止证据的坐标范围阈值，米 |

这些参数均可由 `--param key=value` 覆盖，覆盖优先于 CLI 属性。参数会拒绝负数、非有限值、布尔值等不适合比较的输入；step 年龄还要求整数。历史步数、事件窗口、截止视野和 limit 沿用原有参数。

所有扩展明细返回都使用 LIMIT；摘要返回一行或有限分组。限制返回条数不保证数据库扫描开销同样小，正式运行仍应检查执行计划与索引。

每条 `ContextQuery` 增加可选 `temporal_scope`，原有构造调用兼容。scope 会出现在目录、dry-run、逐条日志、query_metrics 和 context.query_temporal_scopes 中：

| scope | 解释 |
| --- | --- |
| `current` | 读取可变的当前 Drone/Task/关系属性 |
| `snapshot` | 读取不晚于目标 step 的 AgentState/Step |
| `snapshot_with_config` | 历史快照结合 Drone 能力配置，要求同一 run 内配置稳定 |
| `event_window` | 事件按传入的时间上界读取；i43 特别表示截至时间的最近充电，不局限短窗口 |
| `current_with_snapshot` | 当前属性与历史快照并列或组合，明确不是纯历史回放 |
| `current_task_events` | 当前有效任务集合，加截至时间的事件 |
| `current_region_events` | 当前 Drone 所在区域，加截至时间的事件 |
| `snapshot_region_events` | 原 i10：自身快照区域，加截至时间的事件 |

新标记用于解释结果，不会自动让可变属性具备历史版本，也不会自动强制所有包读取同一数据库版本。缺失快照、缺配置、缺事件与“真实没有风险”需要区别解释。

### 后续建议

- 先用 data_readiness 检查目标 drone 的实体与状态，再按具体决策使用 task_decision、energy_safety 或 request_help，逐项核对输出。
- 查询目录已具备 LLM 前置上下文形态；接入实际仿真时，应明确调用时刻、选择规则、上下文长度与动作校验。
- 对当前态包使用实时最新时刻；要回放历史任务与交接关系，应先补齐版本化或事件重建，不把 scope 标记当作历史一致性保证。
- 在数据、索引、环境稳定后，按情景分别开展 100 智能体与多轮性能测试，同时报告单条 query、整包 context 和失败率。
- 对尚未入图的任务、未收录 depot、缺少能力配置或事件的情况，保留 unknown/空结果语义，避免让 LLM 误判为不存在风险。
