### 任务背景

用户希望在原有 `scripts/lade_llm_context_queries.py` 的基础上，将查询流程拆分为多个可观测阶段，同时记录单查询、context 和整轮实验总时间，最终输出各阶段平均值，用于判断主要性能开销。

### 关键结论

- 新脚本为 `scripts/lade_llm_context_queries_stages.py`，查询模板、参数解析和辅助函数复用原脚本，原脚本未被修改。
- 客户端直接计时拆分为：参数构造、`session.run()` 到结果头、全部记录拉取/解码、ResultSummary 取得、Record 转 `dict`、查询日志记录构造、单查询总时间与含参数的流水线总时间。
- Neo4j 服务端计时单独记录 `server_available_ms` (`t_first`)、`server_consumed_ms` (`t_last`) 及两者之和 `server_query_ms`。这些时间嵌套在客户端 `run_to_header_ms`/`fetch_records_ms` 内，不能重复相加。
- 脚本额外计算“客户端阶段减去服务端阶段”的组合估算，用于粗略观察连接池等待、必要时的建连、网络和 Driver 开销；由于服务端只返回整数毫秒，估算值可能出现很小的负数。
- context 级别记录线程池等待、Session 对象创建/关闭、context 内查询时间之和和 context 总时间。`session_create_ms` 只是创建轻量 Session 对象，物理连接通常在首次 `session.run()` 中延迟取得。
- summary JSON 中同时输出全局和每个 i0/i1/... 的阶段统计，每项包含 `avg_ms`、`p50_ms`、`p95_ms`、`max_ms` 和 `count`。
- 最小真实 i0 验证成功：其中一次客户端总时间为 `7.037 ms`，服务端报告为 `1 ms`，首结果前非服务端组合估算为 `5.157 ms`。单次样本仅用于验证脚本，不作为正式性能结论。

与原实验参数对应的使用命令：

```bash
DRONE_IDS=$(printf "drone-%s," $(seq 1 100))
DRONE_IDS=${DRONE_IDS%,}
NEO4J_URI=bolt://127.0.0.1:57687 \
NEO4J_USER=neo4j \
NEO4J_PASSWORD=neo4j123456 \
./run_in_lade.sh python scripts/lade_llm_context_queries_stages.py \
  --run-id hangzhou-0621-headless-002 \
  --drone-ids "$DRONE_IDS" \
  --step-index 2300 \
  --queries all \
  --repeat 20 \
  --max-workers 100 \
  --max-connection-pool-size 100 \
  --query-log-jsonl test/stages_query_logs.jsonl \
  --context-jsonl test/stages_contexts.jsonl \
  --summary-json test/stages_summary.json
```

其中 JSONL 文件是追加写入，summary JSON 是覆盖写入。为避免不同轮次混在一起，正式实验建议每轮使用新文件名。

### 后续建议

- 分别对 `lade` 和 `lade-index` 使用相同参数执行，但为每个库使用独立输出文件名。
- 正式比较时建议先做预热轮，再采集多轮数据；冷连接和页缓存会明显影响首轮。
- 先查看 `stages_summary.json` 中各查询的 `direct_stage_ms`，再用 `server_stage_ms` 判断服务端占比，不要把两组时间直接相加。
- 如果需要把连接池等待、TCP 建连、Bolt 往返和 Neo4j 内部排队进一步精确拆分，需要引入 Driver 调试日志、服务端 query log 或监控指标，单靠当前公开 Driver API 不足以完成。
