# 带索引 56 条查询高延迟排查

### 任务背景

用户提供 56 条 i 查询的平均/p95 耗时，部分平均达到 500–2500 ms，希望确定原因。本次先匹配原始结果、目录版本和计时边界，再只读核查索引，并进行少量单并发查询及 PROFILE。不修改产品代码、数据库、索引或原实验结果。

### 关键结论

- 已找到与用户贴出数值一致的 `test50/summary.json` 和配套明细，连接确实是带索引实例 `bolt://127.0.0.1:61687`，不是误连基线库。
- 这份结果测试时间为 15:11–15:17，使用修订前的旧 56 条目录；实际结构修订于 15:41 后才写入脚本。不能用当前 v2 的编号含义直接解释这份旧结果，也不是要求用户对已完成测试承担版本错误责任。
- 该库只有原 3 组 AgentState 属性索引，Event/Drone/Task/Step 没有属性索引。事件扫描是真实开销，但不足以单独解释所有秒级端到端时间。
- 旧查询引用的故障、协作、交接属性在该实例仍未登记，旧 i17/i4/i50 在诊断中分别产生 3/5/4 条通知。Driver 在结果消费阶段同步处理这些日志，处于脚本的单查询计时范围内；大量并发日志是重点嫌疑。
- 单并发、预热后、内存捕获而非终端输出告警时，代表性旧 i17/i4/i50 客户端平均仅约 1.3/27.0/10.0 ms，服务端报告约 0.2/25.0/8.8 ms。因此原先 1217/2467/1469 ms 不能直接称作这些语句固有的服务端计算时间。
- 这不是原实验的时间分账：缺少当时的服务端计时、stderr 时序和资源监控，不能给出“多少百分比来自日志/排队”的确定数字。综合证据指向旧目录告警、并发客户端/输出等待及数据库扫描的叠加。
- 有 23 类查询始终返回零行；抽查首批 100 个上下文，i3 返回的 365 个当前任务全部晚于请求时间 634 分钟才释放。历史快照与当前任务混用也是结果代表性问题，不应把空结果当作已验证完整业务场景。
- 优先固定版本与数据时间语义，再低并发分阶段测量，然后处理真实扫描和索引覆盖；不建议先盲目给所有字段建索引或仅屏蔽告警后重跑 100 并发。

### 二、这些毫秒数到底测了什么

普通执行器的实际路径为：

```text
开始计时
  → session.run / 可能的连接获取与建连
  → 服务端执行与等待
  → Bolt 接收、解码、遍历结果
  → Driver 处理服务端通知，可能同步记录告警
  → 行转换完成
停止计时
```

因此 `elapsed_ms` 是客户端观察到的端到端时间，不是纯数据库 CPU 时间。

几个重要边界：

- 参数构造在单查询计时开始之前；查询记录 dict 构造在结束之后。
- 线程池中等待任务开始的时间不在单查询计时内，不能直接把 executor 的任务队列等待算到每个 query 上。
- 物理连接获取可能发生在 session.run 内；但仅凭 max-workers 和连接池都设为 100，既不能证明完全无等待，也不能断定连接池不足。
- 两个 JSONL 在完整 context 返回后，由收集端写入，不直接属于每条 query 的计时段；它们可能通过 GIL、CPU、磁盘竞争间接影响其他查询。
- Driver 告警日志不同：当前驱动的 `_handle_warnings` 在结果消费流程中调用 `neo4j.notifications` logger，确实可能在单查询计时段内发生。
- 服务端 available/consumed 时间是服务器报告的阶段耗时，也不等同于纯 CPU 时间；整数毫秒精度不适合对亚毫秒差异过度解读。

Neo4j 提供查询 summary、计划和服务端时序用于区分执行细节，不能只看一个客户端总时长归因。[官方 summary 说明](https://neo4j.com/docs/python-manual/current/result-summary/)

### 三、确实存在索引覆盖不足

当前 61687 的 3 个 RANGE 索引均为 ONLINE：

```text
AgentState(run_id, drone_id, step_index)
AgentState(run_id, region_id, step_index)
AgentState(run_id, step_index)
```

另外只有默认的节点/关系 LOOKUP。没有 Event、Drone、Task、Step 的属性索引。

这解释了为什么部分状态查询较快，但不能保证 Event、任务关联或距离查询也快。无匹配结果也不代表没有扫描。

本次对代表语句的实际 PROFILE：

| 语句 | 标签/索引入口实际读取 | 计划总 DB hits | 结果 |
| --- | --- | ---: | --- |
| 重建旧 i17 | Drone 标签扫描，样本在第 20 个候选命中并停止 | 70 | 1 行 |
| 重建旧 i4 | Event 标签扫描 26454 行 | 81363 | 10 行 |
| 当前 v2 i4 | Event 标签扫描 26454 行 | 79670 | 10 行 |
| 重建旧 i3 | Drone 标签扫描 100 行及关系扩展 | 634 | 此 drone 为 0 行 |
| 重建旧 i50 | request 入口扫描 Event 26454 行；后两子查询入口未实际运行 | 52909 | 0 行 |
| 当前 v2 i13 | AgentState RANGE 索引读取 2300 个候选 | 2302 | 1 行 |

两个容易误解的地方：

1. 旧 i50 虽然计划里有三处 Event 入口，但因为没有 request 匹配，后两处 PROFILE 的 rows 和 DB hits 均为 0。不能仅凭三个算子就说当次一定完整扫描三遍。
2. v2 i13 虽命中索引并只返回一行，该计划仍读取了 2300 个历史状态候选。索引命中不等于只访问一行，排序和查询形状仍需分析。

以 i4 样本入口估算，重复 2000 次可能读取约 5290 万次 Event 标签候选，而不是只处理最终返回的几千行。候选索引和限制全目录重复负载仍有必要，但这不构成原秒级时间的完整解释。

### 四、旧目录告警是本轮额外的重要问题

在当前索引库中，检查的下列属性名全部未登记：

```text
failure_mode takeover_mode source_drone_id helper_drone_id reason
handover_x handover_y takeover_count previous_assignees assistance_reason
```

实际关系也没有 ASSISTS、TAKES_OVER、HANDOVER_TO 等。旧目录中的一些查询与这个库不匹配。

代表性旧语句的诊断通知数量：

| 旧语句 | 每次告警 | 内存格式化消息体约字节 |
| --- | ---: | ---: |
| i17 | 3 | 3280 |
| i4 | 5 | 6677 |
| i3 | 1 | 1893 |
| i50 | 4 | 9223 |

消息会附带 Cypher，所以单条文本很长。若原 2000 次调用都收到同样通知，仅 i4+i17 两类就可能输出约 16000 条告警；该估算不等于原始 stderr 的精确条数或大小，因为原始 stderr 没有保存在 test50 中，重建语句空白格式也与原文件未必相同。

Python logging 的 handler 会用锁保护输出；大量线程共享终端输出路径时，格式化、输出和等待都可能相互放大。[Python 官方线程安全说明](https://docs.python.org/3/library/logging.html#thread-safety)

结合旧 i17 只是读取一个小型 Drone 实体，却与无告警状态查询出现巨大差异，日志等待是需要优先排除的强嫌疑。没有原轮次的分阶段数据，不能据此宣称全部 1217 ms 都由日志造成。

### 五、单并发对照测到了什么

使用已有 61687 库、drone-18、相同 run/step/time 参数，只建立一个连接，执行预热和每项 5 次热调用；告警在独立诊断进程中保留计数和文本格式化，但放入内存，不刷终端。没有全局修改产品的日志配置。

原日志没有保存 Cypher，因此“旧语句”是依据此前目录记录重建的代表语句，不能称为原实验逐字节重放。每项另执行一次 PROFILE；连同准备查询共 50 次只读请求，不是 100 并发重测。

| 语句 | 用户原轮次 client avg | 本次单并发热 client avg | 本次服务端报告阶段之和 avg |
| --- | ---: | ---: | ---: |
| 重建旧 i17 | 1216.995 ms | 1.318 ms | 0.2 ms |
| 当前 v2 i17 | 不适用，含义已变 | 1.017 ms | 0.2 ms |
| 重建旧 i4 | 2466.970 ms | 26.996 ms | 25.0 ms |
| 当前 v2 i4 | 无同版本全量数据 | 28.607 ms | 27.4 ms |
| 重建旧 i3 | 570.036 ms | 1.280 ms | 0.2 ms |
| 重建旧 i50 | 1469.253 ms | 9.998 ms | 8.8 ms |
| 当前 v2 i13 | 原同名 9.033 ms，但条件不同 | 1.566 ms | 1.0 ms |

这些数字说明：

- 原轮次的巨大数值包含负载、客户端或输出条件的放大，不是单凭查询数据量决定的固定时间。
- i4 即使去掉告警仍扫描 Event，v2 并未凭空消除这个瓶颈；单并发两种版本相近也支持“结构修正不是完整性能优化”的判断。
- 不能把两列相除后宣称 v2 带来对应倍数的加速：版本、并发、输出、缓存和系统负载条件都不同，且只有少量样本。
- 没有当时服务器阶段时序，不能做原实验的精确 CPU/排队/网络/告警耗时拆分。

### 六、预热和查询返回内容也影响结论

#### 首批开销不是稳态

按 context_index 分组，i0 在首批 100 个上下文中平均约 911 ms，而其余约 1900 次平均约 5.5 ms，最终混合为 50.787 ms。这提示启动建连、首次编译/缓存或初始并发突发的影响，不能只看整体平均。

分组不是严格同步的独立轮次；工作线程完成一个 context 后立即领取下一个任务。不能将每组均值视为条件完全一致的单独实验。

#### 23 类全零结果

```text
i8 i19 i20 i21 i22 i23 i24 i25 i26 i27 i28 i29
i30 i31 i33 i35 i36 i37 i40 i48 i49 i50 i51
```

部分旧协作查询为空是数据中不存在对应事件/关系；部分任务查询还受到混合时间语义影响。

抽查 contexts 文件首 100 条：i3 共返回 365 条任务，全部 release_minute > 634。例：drone-30 的当前 Drone.updated_at 约 1403.3，i3 中任务释放时间为 861，但 AgentState 是 step 2300、time 634。i18 对当前任务增加 release<=634 后计数为 0，这是两个不同时间截面的混用，不是“历史时刻实际没有任务”的证明。

上述判断针对这 100 条抽样上下文，不扩大为所有历史任务。当前 Task/Drone 没有历史快照，传 step 2300 不能自动回放它们。

#### 优先级

平均超过 500 ms 的 11 类为 i4、i50、i19、i48、i17、i23、i49、i33、i3、i37、i20。其中前 5 类合计约占累计客户端查询时间的 43.28%。这是客户端计时总和占比，不是墙钟时间或 CPU 占比。

### 七、建议下一轮这样验证

1. 先用 `--list-queries` 确认输出 `i56-observed-graph-v2`，并核对 i17/i36/i50 名称。已经启动的 Python 进程不会因源文件修改自动切换目录；新版本应重新启动测试。
2. 使用独立目录，保留 test50 原始结果，不追加混合新旧日志。加 `--include-cypher` 以便以后还原真正运行的语句。
3. 使用分阶段计时入口，从单 drone、单 worker、少量 repeat 开始，先看服务端 reported time、client total 和数据内容，再逐步增加并发。不要在问题尚未分离时直接重跑整个 112000 次混合负载。
4. 确认当前任务判断与历史时间是否一致；需要历史任务时只能基于已存在的 Event 重建，不能把当前 Task 当历史 Task，也不应补造节点使测试非空。
5. 对确有扫描问题的 Event 查询评估 run/drone/time 与 run/task/type/time 等索引；这要在明确的实验组中进行，不能随意破坏原基线。
6. 不要只关闭通知后把旧目录的空结果当成正常有效业务测试。结构修正、日志配置、索引优化和并发优化是不同层次。

下面是供用户选择执行的低负载分阶段检查示例，本次没有代跑这条命令：

```bash
OUT_DIR="test/i56_v2_stage_check_$(date +%Y%m%d_%H%M%S)"
NEO4J_URI=bolt://127.0.0.1:61687 \
NEO4J_USER=neo4j \
NEO4J_PASSWORD=neo4j123456 \
./run_in_lade.sh python scripts/lade_llm_context_queries_stages.py \
  --database neo4j \
  --run-id hangzhou-0621-headless-002 \
  --drone-id drone-18 --step-index 2300 \
  --queries i0,i3,i4,i17,i50 \
  --repeat 5 --max-workers 1 --max-connection-pool-size 1 \
  --include-cypher --progress-every 1 \
  --query-log-jsonl "$OUT_DIR/query_logs.jsonl" \
  --context-jsonl "$OUT_DIR/contexts.jsonl" \
  --summary-json "$OUT_DIR/summary.json"
```

这个命令用于分离耗时因素，不承诺在旧 step 上验证完整当前任务场景。官方也建议用执行计划定位问题，并指出大量简单查询并不总能从增加客户端并发中受益。[Neo4j 官方性能建议](https://neo4j.com/docs/python-manual/current/performance/)
