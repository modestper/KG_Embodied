# 知识图谱两种外置写入模式实现

### 任务背景

用户要求实现两版知识图谱写入：一版由 Ray 无人机侧写入，另一版由独立副程序接管全部写入；通过参数切换，主进程保留读取和任务规划。

本次实现写入位置切换，并保留旧的主进程写入模式用于对照。同步时间步、Ray 快照读取、业务规则和电量准入行为保持原有语义，没有把全局调度改成异步执行流水线。

### 关键结论

- 新增 `--kg-write-mode main|ray|process`，默认 `main`；启动脚本对应 `KG_WRITE_MODE`。
- `ray`：无人机 actor 写本机派单、取货、完成、运行事件、Drone 状态和可选 AgentState；专门的零逻辑 CPU Ray 写入 actor 处理跨机协调记录、全局 Step 和快照关联。
- `process`：自动启动独立 Python 子进程，以有界 FIFO、JSON-lines 协议和确认结果接管全部数据库写入；主进程保持查询连接和显示用事件摘要。
- 新模式统一 run ID，Driver 在所属进程内创建；初始化唯一约束和索引也在写入端完成，主进程查询连接不执行写入。
- 写入失败、子进程退出、队列超时会反馈给主进程；正常关闭、最终完成和需要已提交数据的查询会排空写入。
- 检查点钩子前增加写入确认，避免异步队列使检查点领先数据库多步；无人机 actor 不单独发布全局 Step。
- 已验证独立子进程与真实 Ray 多进程路由，以及两版与原模式的仿真帧、互助帧和内存事件一致性。
- 没有可用的隔离 Neo4j 测试库，因此真实落库集成未执行；已提供显式启用的测试入口。全量回归仍存在原有 3 项电量准入失败，本次没有修改该规则。

### 使用方式

先沿用已有的 `NEO4J_URI`、`NEO4J_USER`、`NEO4J_PASSWORD`。两种模式分别启动，使用不同的实验 run：

```bash
# 版本一：无人机 Ray 侧写入
KG_BACKEND=neo4j KG_RECORD_AGENT_STATE=1 \
KG_RUN_ID=writer-ray-demo KG_WRITE_MODE=ray \
./run_in_lade.sh bash run_ray_sim.sh

# 版本二：独立子进程写入
KG_BACKEND=neo4j KG_RECORD_AGENT_STATE=1 \
KG_RUN_ID=writer-process-demo KG_WRITE_MODE=process \
./run_in_lade.sh bash run_ray_sim.sh
```

直接调用 Python 入口时：

```bash
KG_BACKEND=neo4j KG_RUN_ID=writer-ray-cli \
./run_in_lade.sh python scripts/run_dynamic_sim.py \
  --backend ray --kg-write-mode ray

./run_in_lade.sh python scripts/run_headless_sim.py \
  --backend ray --kg-backend neo4j --kg-write-mode process \
  --run-id writer-process-headless
```

模式要求：

| 模式 | KG 后端 | 执行后端 |
|---|---|---|
| `main` | memory / neo4j | local / ray |
| `ray` | neo4j | ray |
| `process` | neo4j | 动态 local / ray；headless 仍依赖原有 Ray 检查点能力 |

非法组合在加载数据、启动写入器之前报错。动态运行配置中增加 `kg_write_mode` 和 `kg_run_id`，headless 启动日志也显示写入模式。

### 实现与顺序保证

#### Ray 版

每个 `_DroneActor` 使用同一配置，在 actor 进程中构造自己的存储连接。局部写入在 assign/step 返回前完成；actor 产生的这些记录在主进程只做内存镜像，不重复落库。

互助会同时影响源无人机、援助机和任务，因此仍由明确的协调写入 actor 提交。跨机记录完成确认后才进入后续 actor 修改，减少旧记录覆盖新分配的窗口。本机事件写入只在公共 Run/Region 创建时设置静态属性，避免每次重写这些公共属性。

各 actor 独立写 AgentState，但不创建或提交全局 Step。主进程收到全轮结果、检查点钩子完成后，把全局摘要发送给协调写入 actor；该 actor 发布 Step 并关联已经写好的 AgentState。

协调写入 actor 使用 `num_cpus=0`，避免所有逻辑 CPU 已被无人机占用时无法调度这个辅助 actor。此设置只是 Ray 逻辑资源声明。

#### 副程序版

`ProcessKnowledgeWriter` 启动 `python -u -m simulation.knowledge_worker`。配置经标准输入发送，不放在命令行；协议输出与子程序日志分离。

主进程先冻结任务与无人机载荷，再放入有界队列；发送和结果读取由后台线程处理，子程序顺序执行写入。逐请求确认用于检测故障，`flush` 用于建立已提交边界。已确认且没有待处理记录时，flush 直接返回。

全局 Step 只传预计算摘要和必要的 AgentState，避免为了写一步汇总而重复发送所有任务对象。主进程仍需要构造这些消息和现有页面指标，但不执行数据库写语句。

#### 查询、关闭和恢复

- 查询区域上下文、近期表现、近期事件或数据库最新 Step 前，确认此前待处理写入已完成。
- 正常结束与关闭先排空，再关闭写入进程和查询连接；独立子程序会被等待和回收。
- headless 在保存下一检查点之前排空先前记录，本步 Step 仍在检查点钩子后提交，继续匹配原有最多领先一步的恢复逻辑。
- Ray actor 的关闭请求批量发送并有等待上限，随后终止本环境拥有的 actor；不关闭外部已有 Ray 集群。
- 记录继续使用稳定事件 ID。多进程模式不是一笔覆盖所有 actor、数据库和检查点的分布式事务；部分写入失败后会显式报错，不能宣称整轮数据库已原子提交。

### 数据库与运行边界

新写入器在启动端检查/创建 Run 唯一身份，以及 Drone、Task、Region、Event、Step、AgentState 的运行内唯一身份约束。Event/Step 的匹配显式包含 run_id，避免全库 ID 假设影响不同实验。

不会自动删除或合并重复数据。若已有库不满足约束，启动会失败，建议先在隔离库验证。AgentState 查询索引沿用原配置；`KG_AUTO_CREATE_INDEXES=0` 不会取消新写入模式要求的身份约束初始化。

多节点 Ray 模式下，数据库地址必须从所有写入 actor 所在节点可达。每个新模式的数据库 Driver 连接池上限为 2；数据库吞吐和锁竞争仍需实际测量。

`process` 队列和 `ray` 协调写入的待确认请求都有上限。数据库持续慢于生产速度时会产生等待，代码不以静默丢弃关键事件换取运行速度。

### 执行过的操作

主要命令：

```bash
./run_in_lade.sh python scripts/run_dynamic_sim.py --help
./run_in_lade.sh python scripts/run_headless_sim.py --help

PYTHONDONTWRITEBYTECODE=1 ./run_in_lade.sh python -m unittest -v \
  tests.knowledge_writer_test

LADE_KG_RAY_INTEGRATION=1 PYTHONDONTWRITEBYTECODE=1 \
./run_in_lade.sh python -m unittest -v \
  tests.knowledge_writer_integration_test.KnowledgeWriterRayIntegrationTest

PYTHONDONTWRITEBYTECODE=1 ./run_in_lade.sh python -m unittest discover \
  -s tests -p '*_test.py'

bash -n run_local_sim.sh run_ray_sim.sh run_million_data_sim.sh
git diff --check
```

验证范围包括：

- 独立副程序 PID 与主进程不同，关闭前排空，异常退出与写入错误上报；
- 主进程的 Neo4j 连接只执行读取；
- Ray 本机事件由对应 actor 写入，互助与 Step 由协调写入 actor 处理；
- 三种模式的正常配送与已取货故障交接帧、内存事件和汇总一致；
- 检查点钩子前事件已提交，本步 Step 尚未发布；
- 公共 Run/Region 属性在 actor 路径仅创建时设置；
- 启动参数、非法组合检查、事件载荷冻结及全局快照关联。

验证结果：新增 14 项单元测试全部通过；真实 Ray 多进程专项 1 项通过；全量回归 211 项中 199 项通过、3 项既有失败、9 项显式跳过；Shell 语法与 `git diff --check` 通过。

真实 Ray 测试使用独立临时目录、仅 2 CPU 的新本地集群，比较三种模式的实际进程与仿真帧，测试结束调用 shutdown。它使用内存存储验证进程边界，没有据此宣称真实 Neo4j 落库已验证。Ray 包输出了其自身的资源清理提示，测试断言通过。

全量回归的既有失败为：

1. `test_battery_insufficient_for_task_and_return_prevents_assignment`
2. `test_auction_retries_other_region_when_same_region_drone_lacks_battery`
3. `test_ray_reassigns_task_when_preferred_actor_rejects_assignment`

这些对应原有电量硬准入被注释的行为，不属于本次新写入路由引入的问题。沙箱禁止 HTTP socket 和初次 Ray 启动，相关验证改在获准的沙箱外完成。

Docker 普通访问被系统权限拒绝；获准的沙箱外检查仍被拒绝，sudo 无免密权限，因此未创建 Neo4j 测试容器。没有修改现有数据库、容器、实验数据或已有运行参数。

已提供真实 Neo4j 集成入口，仅对隔离库显式启用：

```bash
LADE_KG_WRITER_INTEGRATION_URI=bolt://127.0.0.1:7687 \
LADE_KG_WRITER_INTEGRATION_WRITE=1 \
./run_in_lade.sh python -m unittest -v \
  tests.knowledge_writer_integration_test.KnowledgeWriterNeo4jIntegrationTest
```

该测试会建立约束，比较三种模式的实体/事件数量、任务结果和快照关联，只清理自身创建的 UUID run。
