# 任务配色调整与轨迹回放机制

日期：2026-10-21

### 任务背景

用户指出“未下发”与“已完成”的任务颜色过于接近，同时询问“轨迹回放”展示的数据是否已经生成，以及每次仿真是否都会保存回放轨迹。本轮修正任务配色，并结合现有代码核实轨迹产生、保存和展示流程。

### 关键结论

- 已将未下发任务改为浅灰色 `#cbd5e1`，已完成任务改为紫色 `#8b5cf6`；实时页、回放页的地图与图例同步更新。
- “轨迹回放”读取服务器上已经保存的 trace JSON，不会因为打开该页面或点击播放而重新运行仿真。
- 回放目录来自 `data/traces.json`，当前列出 7 个文件，已核对这些文件均存在。
- 网页实时仿真每步产生状态帧，但当前没有把这些帧自动写成回放文件，也不会自动更新回放目录。
- 实时页时间轴只在浏览器内存保存本次连接收到的帧；刷新或重新运行后清空，不是永久归档。
- 专门的静态生成脚本会在仿真结束后写出 trace JSON；需另外构建回放索引。`generate_res.sh` 已串起这两个步骤。
- Headless 长时仿真主动关闭完整帧保留，按配置写图谱与断点；这些数据不会自动作为前端回放文件出现。

#### 1. 回放页面读取什么

[loadTraceIndex](/data/zc/datasets/LaDe/viewer/src/simulation_app.mjs:63) 请求 `./data/traces.json`，填充轨迹文件下拉框。[loadSelectedTrace](/data/zc/datasets/LaDe/viewer/src/simulation_app.mjs:87) 根据所选文件名请求 `./data/<文件名>`，读取其中的 `frames`、`tasks`、`metrics` 等数据，再逐帧绘制。

因此，当前“轨迹回放”更准确的含义是“已保存轨迹文件的播放器”，并不是每次仿真自动生成的一条运行记录。

#### 2. 不同启动方式的保存行为

| 运行方式 | 状态帧如何产生 | 是否自动生成前端回放文件 |
| --- | --- | --- |
| 网页实时仿真：`run_local_sim.sh` / `run_ray_sim.sh` → `run_dynamic_sim.py` | 每步推进环境，生成 snapshot；按 `frame_stride` 采样后通过 SSE 推送 | 否；服务端普通环境保留内存帧，浏览器缓存已收到的帧，但没有 trace 文件写入逻辑 |
| 静态生成：`scripts/build_delivery_sim.py` | `env.run()` 运行仿真并组织完整 trace，按 `frame_stride` 对帧列表采样 | 是；结束后通过 `args.out.write_text(...)` 写 JSON |
| 长时后台：`scripts/run_headless_sim.py` | 推进状态并写入按配置启用的图谱、断点数据 | 否；`disable_frame_retention()` 把帧列表替换成计数器，并关闭 snapshot 保留 |

实时流的关键代码在 [stream_simulation](/data/zc/datasets/LaDe/viewer/scripts/run_dynamic_sim.py:105)：依次发送 `init`、`frame`、`done`。结束事件包含最终统计、近期事件等，没有保存 trace 或刷新索引的调用。

浏览器缓存见 [FrameTimeline](/data/zc/datasets/LaDe/viewer/src/dynamic_timeline.mjs:1)：`append()` 往内存数组添加帧，`reset()` 将数组清空。没有写入文件、IndexedDB 或 localStorage 的逻辑。

Headless 的关键代码见 [disable_frame_retention](/data/zc/datasets/LaDe/viewer/scripts/run_headless_sim.py:68)，新运行和断点续跑都会调用它。Neo4j 数据和 checkpoint 文件也不会被回放页直接读取。

启用 LLM 时产生的 JSONL 调用日志，以及图谱中保存的 Step/AgentState，也不等于现有回放页要求的 trace JSON；如需从图谱恢复回放，需要额外导出与转换。

#### 3. 已保存轨迹如何生成并出现在列表中

现有流程是：

```text
scripts/build_delivery_sim.py
  → 运行一场仿真
  → 生成包含 config / tasks / depots / metrics / frames 的 trace
  → 保存为 data/delivery_sim_<城市>_<日期>_<任务数>tasks_<无人机数>agents.json

scripts/build_trace_index.py
  → 扫描 data/ 顶层的 JSON 文件
  → 筛选包含 frames / tasks / metrics 的 trace
  → 写入 data/traces.json

simulation.html
  → 加载索引和所选 trace
  → 播放已保存的数据
```

[generate_res.sh](/data/zc/datasets/LaDe/viewer/generate_res.sh:41) 顺序执行生成 trace 和构建索引，因此使用它成功生成的文件会进入更新后的回放目录。

如果只单独运行 `build_delivery_sim.py`，文件虽然生成了，但还需要运行 `build_trace_index.py` 才会进入下拉列表；当前前端也支持通过 `?trace=<文件名>` 直接选择可用文件。

文件保存细节：

- 默认文件名由城市、日期、任务数量、无人机数量组成，没有时间戳。
- 使用相同组合再次生成，会写到相同路径并覆盖该文件，不会自动为每次运行新增独立文件。
- `--out` 可指定其他输出文件名；希望被现有索引扫描到，应放在 `data/` 顶层。
- 两个入口中的 `frame_stride` 都决定展示帧的采样密度，保存的轨迹不一定包含每个仿真步。
- 目前没有“网页仿真结束后自动保存轨迹并更新列表”的开关或实现。本轮没有新增该行为。
