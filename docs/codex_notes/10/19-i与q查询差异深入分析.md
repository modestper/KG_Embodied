# i 系列与 q 系列查询的代码级对比

### 任务背景

用户希望仔细理解当前项目中 `i0-i11` 与 `q0-q55` 的区别，包括设计目的、查询内容、时间语义、返回结果、执行方式、并发负载、计时边界和适用场景。本次依据当前工作区代码分析，不修改查询代码，不重新启动数据库压测。

本文进一步核对了上一份“编号及适用场景”文档中的概括。例如，“用于 LLM 前置上下文”是 `i*` 的设计用途，当前脚本并没有自动调用 LLM，也没有被仿真调度器直接调用。

### 关键结论

- `i*` 和 `q*` 都是项目自定义的只读 Cypher 模板，访问同一类 Neo4j 图谱；字母不代表不同查询语言、不同索引或不同数据库。
- `i*` 的组织中心是“某个智能体在一次决策时需要的上下文”；`q*` 的组织中心是“数据库需要测试的查询模板”。两者有重叠，也有不同过滤条件，不能通过换编号直接互相替代。
- 当前 `i*` 有 12 条，`q*` 有 56 条。`q*` 数量更多、场景更广，但其中若干模板访问相同数据、只改变投影或入口，不能把 56 条直接理解为 56 类完全独立的查询结构。
- `i*` 保存实际结果并构造上下文 JSON；`q*` 消费结果、统计行数和耗时。两套脚本当前均不执行 LLM 推理，仿真中的区域 LLM 协调器走另一条知识查询路径。
- `i*` 按整包上下文并发、包内顺序查询；`q*` 按单条查询并发。因此同为 100 个 worker，访问顺序、热点、连接使用方式和延迟口径仍不同。
- `i*` 更贴近在线决策，但并不自动保证快、结果完全同一时刻、或者正确历史回放；`q*` 也包含点查和在线查询，并不全部是重型离线查询。
- 当前代码存在需要另行修正的语义问题：`q42/q43/q48` 使用了与写入端不一致的协助请求事件名；`i7` 的“nearby”只是同区域过滤；`i0/i3/i8` 和部分 `q*` 读取的是可变当前属性。
- 针对多智能体时序知识图谱查询任务，适合用 `i*` 衡量单智能体上下文构建，用 `q*` 补充图查询结构、全局分析和数据质量覆盖，并分别报告单条延迟、整包延迟、吞吐与正确性。

### 一、它们在项目中分别是什么

| 对比项 | i 系列 | q 系列 |
| --- | --- | --- |
| 模板入口 | `scripts/lade_llm_context_queries.py` 的 `CONTEXT_QUERIES` | `scripts/lade_cypher_benchmark.py` 的 `DEFAULT_TEMPLATES` |
| 数量 | `i0-i11`，12 条 | `q0-q55`，56 条 |
| 扩充位置 | 当前仍为原有 12 条 | `q13-q55` 来自 `scripts/lade_cypher_templates.py` |
| 面向的问题 | 这个智能体现时需要知道什么 | 这类图查询能查什么、执行成本如何 |
| 默认选择 | `core`，7 条 | `all`，56 条 |
| 常见查询中心 | 自身、同区域智能体、近期历史、局部任务、全局摘要 | Run、Drone、Step、AgentState、Event、Task、Region 及其组合 |
| 结果用途 | 组成一个智能体的上下文 JSON | 延迟、吞吐量、行数、失败信息等压测记录 |
| 时间范围 | 以指定 step 和时间为上界，自动回看历史窗口 | 显式的起止窗口、精确 step 或数据库最新状态，依模板而定 |
| 并发单位 | 一个 drone 的一次整包上下文 | 一条模板的一次执行 |
| 是否调用 LLM | 否 | 否 |
| 是否要求不同数据库 | 否 | 否 |

`i`、`q` 是代码中的模板 ID。Neo4j 接收到的是模板中的 Cypher 文本和参数，不会因为 ID 以 `i` 开头就启用“即时查询模式”，也不会因为以 `q` 开头就把它当成复杂查询。

两套脚本均通过 `--uri`、`--database`、`--run-id` 选择连接和目标实验。模板中的 `run_id` 用于限定逻辑结果；它不会自动把该 run 变成物理独立的存储分区。实际是否能高效定位，取决于查询条件、关系入口、数据规模和执行计划。

### 二、从使用者角度理解区别

假设 `drone-7` 准备进行一次决策，需要了解：

1. 我现在在哪里，电量多少，手里有多少任务？
2. 最近发生了什么，哪些任务快到期？
3. 同区域是否有空闲智能体可以帮助我？
4. 系统其他区域是否也在过载？

这些问题对应 `i0/i1`、`i3/i4/i8`、`i6/i7`、`i9/i11`。设计目标是把一次决策需要的多种信息组织在一起。

如果研究者想检查数据库，则可能关注：

1. 当前 run 到底有多少节点？
2. 某条 AgentState 轨迹在 20、100、1000 个 step 窗口内分别多快？
3. 跨多个实体的路径查询、相邻状态自连接、全局聚合会有多大开销？
4. 协助关系是否完整，是否存在孤立的状态或事件？

这些对应 `q0/q55`、`q3/q18/q19`、`q7/q10/q11/q21/q25`、`q42-q54`。设计目标是覆盖数据库的不同访问模式，并检查数据与执行成本。

因此，两套查询可以用于同一研究任务的不同层次。`i*` 也可以压测；部分 `q*` 也可以在经过裁剪、结果校验和接口接入后用于在线上下文。

### 三、12 条 i 查询与 q 查询的逐项对应

下表是功能相近关系，不表示 SQL/Cypher 等价。

| i 查询 | 它实际查询什么 | 相近的 q 查询 | 关键区别 |
| --- | --- | --- | --- |
| `i0` | 一架 Drone 的当前状态、坐标、负载、电量、里程、更新时间 | `q2` | `q2` 额外要求 Drone 到 Run 的 `IN_RUN` 边；`i0` 返回字段更多且有 `LIMIT 1` |
| `i1` | 不晚于指定 step 的自身最新 AgentState | `q3`，部分接近 `q15` | `q3` 是一个窗口内的轨迹；`q15` 是全局最新 step 下多智能体状态，没有同样的自身历史上界语义 |
| `i2` | 自身近期轨迹，倒序，最多 N 条 | `q3/q18/q19` | `q3/q18/q19` 都按 step 正序返回完整窗口，关注字段有所不同；没有相同的结果条数限制 |
| `i3` | 自身当前未完成且关系有效的任务明细 | `q6/q33` | `q6` 读历史分配/完成关系；`q33` 跨所有智能体聚合有效任务数量，并纳入 `TAKES_OVER` |
| `i4` | 自身作为执行者、请求方或协助方参与的近期事件 | `q37`，也与 `q5` 相关 | `q37` 最接近，但返回字段和时间右边界不同；`q5` 是全局事件，不限定一个智能体，且正序取前 N 条 |
| `i5` | 自身近期分配、取件、完成、迟到次数 | `q35/q9` | `q35` 按全局事件类型分组；`q9` 基于全 run 的完成关系排序，都不是同一智能体的同一窗口统计 |
| `i6` | 先确定自身历史状态，再聚合当时所在区域的智能体状态 | `q4/q16/q23` | `q4/q16` 是全局某 step 的状态分布；`q23` 聚合所有区域，返回结构也不同 |
| `i7` | 与自身在同一区域、同一 step 的其他智能体，按队列/电量排序 | `q15/q20` | `q15` 返回全局最新快照；`q20` 取队列最大的智能体，排序方向与选低负载协作候选的用途不同 |
| `i8` | 自身区域中已释放、未完成且不晚于截止视野的任务 | `q26/q27/q31` | `q26` 是当前积压聚合；`q27` 是全局到期窗口，包含已完成任务；`q31` 是当前未完成且截止时间早于指定时间的任务 |
| `i9` | 不晚于指定 step 的全局 Step 摘要 | `q13/q14` | `q13` 没有历史上界，始终取数据库最新 step；`q14` 取窗口内多条摘要 |
| `i10` | 自身区域内近期事件明细 | `q38/q5` | `q38` 返回全局各区域聚合；`q5` 返回全局事件明细，都没有先根据自身状态定位区域 |
| `i11` | 在不晚于指定 step 的全局快照上，聚合各区域瓶颈 | `q23/q24/q8` | `q23` 用精确 step 按总队列排序；`q24` 关注低电量；`q8` 聚合一段时间，而非一个快照 |

#### 例 1：i0 与 q2 都查 Drone，为什么还不一样

`i0` 的定位模式为：

```cypher
MATCH (d:Drone {run_id: $run_id, id: $drone_id})
```

`q2` 的定位模式为：

```cypher
MATCH (d:Drone {run_id: $run_id, id: $drone_id})
      -[:IN_RUN]->(:Run {id: $run_id})
```

后者还验证了一条归属路径。如果 Drone 的两个属性存在，但 `IN_RUN` 边缺失，`i0` 仍可能返回结果，`q2` 就返回空。当前状态写入路径可以创建 Drone，而 `IN_RUN` 边由事件写入路径补充，因此这种差异值得留意。

`i0` 返回 `x/y/updated_at` 等字段并限制 1 条；`q2` 不返回这些字段，也没有 `LIMIT 1`。即便两者都只返回一行，也不能把延迟差异全部归因于脚本计时方式；Cypher 本身已经不同。

代码依据：[i0](/data/zc/datasets/LaDe/viewer/scripts/lade_llm_context_queries.py:33)、[q2](/data/zc/datasets/LaDe/viewer/scripts/lade_cypher_benchmark.py:81)、[状态写入](/data/zc/datasets/LaDe/viewer/simulation/knowledge.py:509)。

#### 例 2：i2 与 q3 都查轨迹，结果为何可能不同

使用相同的 `drone-7` 和 step 窗口 `2281-2300`：

| 项目 | i2 | q3 |
| --- | --- | --- |
| 顺序 | `ORDER BY step_index DESC` | `ORDER BY step_index` |
| 条数 | `LIMIT $limit`，默认 10 | 不使用 `$limit` |
| 状态完整时返回 | `2300,2299,...,2291` | `2281,2282,...,2300` |
| 典型用途 | 给当前决策提供最近记忆 | 完整轨迹回放和窗口成本测试 |

所以 `i2` 的 `--history-steps 20` 表示最多回看 20 个 step 的候选范围；若 `--limit 10`，实际最多只拿最近 10 条。`q3` 即使收到参数字典中的 `limit=10`，其 Cypher 没有使用 `$limit`，也不会自动截断。

`q18` 关注电量和里程，`q19` 关注坐标、区域和里程。它们与 `q3` 的数据入口和窗口过滤很接近，主要改变返回字段，不代表三种完全不同的图遍历结构。

#### 例 3：i3 与 q6 的任务集合不同

`i3` 使用：

```cypher
-[rel:ASSIGNED|CARRYING]->(t:Task)
WHERE coalesce(t.status, "") <> "completed"
  AND coalesce(rel.active, true) = true
```

它按任务合并关系类型，返回当前仍有效的任务，主要回答“我还有什么任务需要处理”。

`q6` 使用 `ASSIGNED|COMPLETED`，没有排除已完成任务，也不要求关系 `active=true`，主要回答“我关联过哪些分配/完成记录”。同一个任务可能因两种关系产生两行。

`q33` 则将 `ASSIGNED|CARRYING|TAKES_OVER` 中有效且未完成的任务按智能体汇总。它返回任务数量、最早截止时间和关系类型，不返回 `i3` 那样的每项任务坐标与详情。

#### 例 4：i9 的“最新”与 q13 的“最新”参照点不同

假设数据库已经写到 step 5000，调用者希望回看 step 2300：

- `i9` 加了 `s.step_index <= 2300`，返回不晚于 2300 的最新摘要。
- `q13` 没有这个上界，返回 step 5000 的摘要。

两者查询文本看起来相似，但时间意义不同。若把 `q13` 直接替换 `i9`，历史回放的上下文就会混入之后才发生的全局状态。

### 四、参数生成与重复查询行为的区别

#### i 系列：围绕一个决策时刻向前回看

`build_params()` 根据当前参数生成：

```text
start_step = max(0, step_index - history_steps + 1)
start_time = max(0, time_minute - event_window_minutes)
```

例如 `step_index=2300`、`time_minute=634`、`history_steps=20`、`event_window_minutes=30`，得到 step 候选范围 `2281-2300`，事件候选范围 `604-634` 分钟。

需要时间参数而没有显式传 `--time-minute` 时，主函数会先读取指定 Step 的 `time_minute`。这条辅助读取在 benchmark 的 `wall_ms` 计时之前执行，没有算作一条 `i*` 查询记录。

`--repeat 3` 会按同一组 step/time 参数重复构建上下文，不会自动把仿真时间推进到下一时刻；整个运行开始前只做一次必要的 Step 时间解析。数据库如果继续写入，当前态属性仍可能变化。

#### q 系列：围绕测试范围生成窗口

`build_step_window()`、`build_time_window()` 根据起点、终点、窗口宽度和 stride 生成每轮参数。与 `i*` 的固定决策时刻不同，重复轮次可以移动或循环窗口。

`--end-step 10000` 不代表每次都扫描 `1-10000`：默认 `--step-window 100`，每次通常只查其中 100 个 step。要在已有 `--end-step` 时用完整范围，需要理解 `--step-window 0` 的分支。

若显式给了 `--step-index`，使用精确 step 的模板每轮都使用该值；未给时，脚本使用该轮窗口起点，不会自动查“数据库最新 step”。只有模板本身写了最新状态逻辑，如 `q13/q15`，才会读取最新状态。

q 脚本分别生成 step 窗口和分钟窗口，没有从 Step 自动换算两者的逻辑。做同一时刻的比较时，需要自行核对窗口是否匹配。

#### 时间右边界也要对齐

多数 i 事件查询采用 `start_time <= time <= time_minute`，包含当前端点；多数 q 事件查询采用 `start_time <= time < end_time`，不包含右端点。

因此事件恰好发生在 634 分钟时，可能被 `i4` 选中，却被 `end_time=634` 的 `q37` 排除。对比行数和性能时，需先对齐边界，不能只把时间参数写成相同数字。

代码依据：[i 参数](/data/zc/datasets/LaDe/viewer/scripts/lade_llm_context_queries.py:466)、[Step 时间解析](/data/zc/datasets/LaDe/viewer/scripts/lade_llm_context_queries.py:489)、[q 窗口](/data/zc/datasets/LaDe/viewer/scripts/lade_cypher_benchmark.py:430)。

### 五、时间语义：两套都需要区分当前态、快照与事件

同一张图中，三种数据承担不同作用：

| 数据 | 写入方式和意义 | 典型查询 |
| --- | --- | --- |
| `Drone`、`Task` 当前属性 | 随仿真状态和事件更新，通常只保留当前值 | `i0/i3/i8`，`q2/q26/q28/q31/q33/q49` |
| `AgentState`、`Step` | 带 step 的历史状态与汇总 | `i1/i2/i6/i7/i9/i11`，`q3/q4/q14-q25/q51` |
| `Event` | 表示发生过的事件，按 `time_minute` 检索 | `i4/i5/i10`，`q5/q35-q43/q48/q50` |

上述只是主要来源。有些查询还关联其他实体，因此会混合不同时间语义。

例如任务在 step 2300 时未完成、在 step 4000 时完成。数据库已推进至 5000 后：`i1` 能读到 step 2300 的无人机状态，但 `i3/i8` 会根据 Task 当前的 completed 状态把该任务排除。整包里写了 `step_index=2300`，也无法自动把 Task 恢复到当时。

同样，`q31` 实际表达的是“当前还没完成，且截止时间早于传入 end_time 的任务”。若 end_time 是历史时刻，它不能找回那些当时逾期、后来已经完成的任务。

`q10` 从历史事件关联到 `d.status`，读到的是 Drone 当前状态，而非事件发生时的状态；`q40` 的任务状态也是查询时状态，如果 run 尚在写入，字段别名 `final_task_status` 也不保证最终结果。

`i1/i6/i7/i8/i10` 还允许向旧的自身状态回退；如果指定 step 没有该智能体样本，就使用更早的状态。`i9/i11` 按全局 Step 回退，选中的 step 可能与自身回退结果不同。

同一个 Session 中连续执行 12 次 `session.run()`，代码没有把它们绑定到一个统一的历史数据版本。并发写入期间，整包查询也可能跨越多个提交状态。

要做正确历史回放，需要给 Task/协作关系增加版本或有效时间，或从截至目标时间的事件重建；要做实时决策，也应返回实际 step 和状态年龄，以判断是否过期。本次只分析这些边界。

### 六、返回内容和 LLM 接入的实际区别

i 脚本 `execute_context()` 把每条结果转成 Python 字典并保存：

```text
一个 context
  run_id / drone_id / step_index / time_minute
  queries
    current_drone_state: [...]
    latest_agent_state: [...]
    active_tasks_for_drone: [...]
    ...
  query_metrics: [...]
```

上下文结果默认写入 `data/lade_llm_contexts.jsonl`，逐条计时写入另一份 JSONL。它具备作为 prompt 原料的形态，但并没有进行最终 prompt 选择、长度控制、API 调用和动作执行。

q 脚本 `execute_query()` 遍历 Neo4j 返回记录以统计行数，返回模板 ID、参数、耗时、是否成功等指标；它没有保留每条业务结果的字段内容。因此运行 q benchmark 后，默认日志能告诉你“返回了几行、用了多久”，不能直接展示这几行任务或事件详情。

本次还沿仿真调用路径核实：

```text
scripts/lade_llm_context_queries.py
  → Neo4j 查询
  → context JSON / 查询计时

scripts/lade_cypher_benchmark.py
  → Neo4j 查询
  → 行数 / 查询计时

simulation/planner.py 中的 RegionLLMCoordinator
  → knowledge_store.query_region_context(...)
  → build_request(...)
  → LLM 请求
```

当前区域协调器使用 `query_region_context()`，其中任务与候选智能体来自传入的仿真对象，近期表现和事件由知识存储查询。它没有导入 `CONTEXT_QUERIES`，没有自动逐条执行 `i0-i11`。`LLMPlanner` 也直接根据传入 drone/task 构造请求。

因此此前“i 查询结果会直接拼入实际 LLM prompt”的表达需要收窄为：**i 系列模拟并测量可用于 LLM 决策前的知识上下文获取，接入实际 LLM 流程仍需单独实现。**

代码依据：[i 结果组织](/data/zc/datasets/LaDe/viewer/scripts/lade_llm_context_queries.py:540)、[q 结果消费](/data/zc/datasets/LaDe/viewer/scripts/lade_cypher_benchmark.py:534)、[区域协调器](/data/zc/datasets/LaDe/viewer/simulation/planner.py:136)。

### 七、并发方式差异，会直接改变性能实验

#### i：每个 worker 获取一整个 context

执行结构为：

```text
worker 1：drone-1 → i0 → i1 → i2 → ... → i11 → context
worker 2：drone-2 → i0 → i1 → i2 → ... → i11 → context
...
worker 100：drone-100 → i0 → i1 → ... → i11 → context
```

同一个 context 的查询按所选顺序执行，共用一个 Session。前一条慢，后一条的开始时间就向后推。不同智能体的 context 可以并发。

当显式给出 100 个不同 drone ID、`--queries all --repeat 3` 时，代码生成 300 个 context，合计 `100 × 3 × 12 = 3600` 次模板查询。默认只有 `drone-1`，只把 worker 数设为 100 不会自动生成 100 个智能体 ID。

#### q：每个 worker 执行一条模板查询

q 的每个 Future 都是 `execute_query()`。同一个 `agent_index` 下的多条模板可以重叠执行，没有“等该 agent 的 q0 执行完再执行 q1”的约束。

q 的作业生成顺序是：

```text
agent 1：第 1 轮的所有模板 → 第 2 轮的所有模板 → 第 3 轮的所有模板
agent 2：第 1 轮的所有模板 → 第 2 轮的所有模板 → 第 3 轮的所有模板
...
```

本次离线调用实际 `build_jobs()` 验证：`--agents 100 --queries-per-agent 3 --templates all` 生成 `100 × 3 × 56 = 16800` 个作业；最先提交的 100 个作业，其 `agent_index` 全部是 0，也就是同一个 agent 标签下的模板与轮次。

这不保证前 100 个作业同时执行，但足以说明提交模型：100 个 worker 表示最多 100 个单查询执行任务，不能直接解释成“100 个不同智能体同时各做一次决策”。

此外，很多 q 模板不需要 `drone_id`。例如 q13 是全局最新 Step，给它挂上 100 个 agent 标签，是对同一个全局查询发起重复请求，而非 100 份不同的局部状态检索。i9/i11 等全局查询也有类似重复访问，应识别其全局共享性质。

两套脚本都使用本机 Python 线程池模拟客户端，100 个线程本身不能证明已经部署了 100 台边端设备。是否满足指标中的“100 个智能体节点”，还需按验收定义说明客户端与设备部署方式。

代码依据：[i 并发](/data/zc/datasets/LaDe/viewer/scripts/lade_llm_context_queries.py:691)、[q 作业生成](/data/zc/datasets/LaDe/viewer/scripts/lade_cypher_benchmark.py:624)、[q 并发](/data/zc/datasets/LaDe/viewer/scripts/lade_cypher_benchmark.py:636)。

### 八、计时口径不同，平均毫秒数不能直接横比

| 时间组成 | i 的单条 elapsed_ms | i 的 context total_elapsed_ms | q 的单条 elapsed_ms |
| --- | --- | --- | --- |
| 线程池等待任务开始 | 不含 | 不含 | 不含 |
| 创建/关闭 Session 对象 | 不含 | 包含 | 包含 |
| 构造查询参数 | 不含 | 包含 | 不含，作业生成时已完成 |
| session.run 与结果读取 | 包含 | 包含 | 包含 |
| 获取连接、网络往返和服务端处理 | 实际发生在被计时调用中时包含 | 包含对应查询的这部分时间 | 实际发生在被计时调用中时包含 |
| 将每条结果转成字典/JSON 兼容值 | 包含 | 包含 | 不做，只计行数 |
| 构造逐条指标与上下文字典 | 单条计时外 | 包含主要构造过程 | 单条计时外 |
| 结果 JSONL 落盘 | 不含 | 不含 | 不含 |
| LLM 推理 | 没有调用 | 没有调用 | 没有调用 |

两套 `wall_ms` 都衡量整批任务的墙钟时间，包含线程池调度和运行期间的结果处理/日志写入；最终 summary JSON 写入在 wall_ms 计算之后。

原 i 脚本创建一个 Session 顺序执行整包，连接开销可能偏向包内前面的查询。q 为每条查询新建 Session；Session 对象并不等同于物理新连接，两套都使用 Driver 的连接池。不能据此说 q 每条都重新 TCP 建连，也不能把创建 Session 的时间当成全部网络连接时间。

举一个仅用于说明口径的例子：若每包 12 条查询，每条都恰好 50ms，且顺序执行，那么该包的查询部分就是约 600ms，再加上组织开销。单查询平均低于 500ms，不意味着整包上下文低于 500ms。

吞吐量中 `QPS` 的分子是查询条数，不是 context 数。对相同查询包、全部成功时，可用 `context_count / wall_seconds` 单独计算 context/s；不能把 1200 QPS 直接写成每秒 1200 次完整决策。

两套默认汇总平均延迟主要针对成功查询，失败数另列；错误增加可能让成功样本平均看起来更小，报告应同时列成功率与错误类型。

#### stages 和 single 文件分别意味着什么

`scripts/lade_llm_context_queries_stages.py` 复用原 i 模板和参数，增加结果头等待、记录拉取、结果转换、Session、worker 排队等计时，并读取 Neo4j 返回的服务端时间。因此它是 i 工作负载的计时增强版，不是另一套查询语义。

服务端时间与客户端时间也不是互斥的可直接相加项：客户端 run/fetch 已经等待了服务端处理。差值只能按该脚本的估算口径解释，不能把所有差值直接叫“纯网络耗时”。

本次字节比较发现 `scripts/lade_llm_context_queries_single.py` 与主 i 脚本内容完全相同。文件名里的 `single` 不保证单线程，实际仍由 drone 数量与 `--max-workers` 决定。

代码依据：[i 单查询计时](/data/zc/datasets/LaDe/viewer/scripts/lade_llm_context_queries.py:564)、[i 整包计时](/data/zc/datasets/LaDe/viewer/scripts/lade_llm_context_queries.py:540)、[q 计时](/data/zc/datasets/LaDe/viewer/scripts/lade_cypher_benchmark.py:534)、[分阶段计时](/data/zc/datasets/LaDe/viewer/scripts/lade_llm_context_queries_stages.py:108)。

### 九、q 比 i 多覆盖了哪些内容

| 覆盖方向 | 主要 q 模板 | 对当前研究任务的价值 |
| --- | --- | --- |
| 数据规模与连接基线 | `q0/q1/q55` | 确认 run 存在、节点规模和基础查询通路 |
| 指定 step 的全局快照 | `q4/q15/q16/q20/q23` | 模拟中心节点批量查询多智能体状态 |
| 大窗口时序聚合 | `q7/q8/q14/q18/q19/q22` | 观察历史窗口扩大时的延迟变化 |
| 相邻状态关联 | `q21/q25` | 检查时序自连接成本、状态迁移和运动趋势 |
| 多实体关联与路径 | `q10/q11/q40` | 测多关系展开、聚合与中间结果增长 |
| 任务与事件整体分布 | `q9/q26-q31/q33-q39` | 构造全局分析工作负载，检查热点和结果分布 |
| 显式协助和接管关系 | `q32/q42-q48` | 扩充跨智能体关系查询，评估知识共享与责任追踪 |
| 电量和故障 | `q17/q24/q41/q49-q51` | 支持风险状态检索及协作异常场景 |
| 图数据质量 | `q12/q52-q54` | 发现缺失关系，辅助解释空结果或统计不一致 |

这些方向能提高图/时序查询的覆盖面。但 `q4/q16` 很接近，`q3/q18/q19` 很接近；只有投影字段变化的模板仍有测试价值，但不能据条数声称覆盖了同样多的独立图结构。

当前两套都没有向量召回、图像检索或多模态关联实现。增加 q 或 i 的数量，并不会自动补齐项目的跨模态指标。

### 十、本次核对发现的具体语义问题

这些问题说明，模板描述、语法通过和业务结果正确，需要分别核验。

| 位置 | 当前代码行为 | 对结果解释的影响 |
| --- | --- | --- |
| `q42/q43/q48` | 筛选 `assist_requested`；本地与 Ray 仿真实际写入 `task_assistance_requested` | 会漏掉真实协助请求；q48 的 requested 可能为 0。此前 56/56 EXPLAIN 通过只能证明语法可接受，不能发现事件名错配 |
| `q42/q43/q48/q50` | 依赖 `assist_unavailable`；当前协助路径未选到 helper 时直接返回 False，检索未找到该事件的写入 | unavailable=0 不能证明没有发生过协助不可用 |
| `i7` | 只按同区域筛选，按队列升序、电量降序排序 | “nearby”不是距离最近；未计算半径，也未排除全部不能接单的状态，不能直接当成可执行的协助候选集 |
| `i3` | 关系模式只包含 `ASSIGNED|CARRYING` | 没有直接读取 `TAKES_OVER`；当前派遣流程会给 helper 记 assignment，因此不能直接断言现流程必漏，但若后续仅有接管关系就会漏 |
| `i4/i5` | i4 统计参与事件时看执行者/请求方/协助方；i5 只按 e.drone_id | 两者针对“与我有关”的事件口径不同，行数/总数不一定对应 |
| `i8` | 截止时间只有上界，没有“deadline 大于当前时间”的下界 | 候选中会包含已逾期的未完成任务，不能理解成仅未来一小时新到期任务 |
| `i9/q13/q14` | 返回 Step.completed_tasks，写入值为 len(completed_this_step) | 表示该步完成数，不是截至该步的累计完成数 |
| `q24/q30/q36` | 分别返回低电量数量、迟到数量、每 10 分钟桶的事件数量 | 描述中提到的“比例/迟到率/速率”还需要明确分母或时间归一化，当前结果没有直接计算这些比率 |
| `q17/q24/q41` | 用 Drone.low_battery_threshold_m 这个字段判断风险 | 仿真实际返航阈值还考虑到充电点距离和安全余量，结果不一定等于仿真 is_low_battery 的判断；历史配置变化也需版本处理 |
| `q21/q25` | 要求 next.step_index = previous.step_index + 1 | 相邻 step 缺样本时无法跨缺口关联，不能认为统计了全部状态变更/全部里程 |
| `q22` | 返回每种状态的样本数，以及该状态首末出现 step | 没有计算连续停留区间；采样间隔不固定或有缺口时，样本数不能直接转换成真实分钟数 |
| `q11` | Event→Drone→Task→Region 固定三跳，按同区域限制 | 不要求 e.task_id = t.id，因此不代表该事件本身的任务；length(p) 恒为 3，不是最短路径/变长路径算法 |
| `q34/q45/q47` | 统计保留关系或关联过的多个智能体 | 不能把历史携带关系数当成当前载货，也不能把多个关联智能体理解为同时共同执行同一任务；MERGE 保留关系数也不等于所有事件次数 |
| `q48` | 返回几类事件的总数，没有按请求标识连接闭环 | 不能直接推导严格协作成功率；请求/派遣/交接可能落在不同时间窗口 |
| `q52-q55` | 检查部分关系是否存在，或统计沿 IN_RUN 可达节点 | 不是完整一致性证明。例如 q52 不核对关系终点 step 与 a.step_index 是否相同；q55 看不到缺失 IN_RUN 的节点 |

其中协助事件名不一致由当前代码直接确认：

- 写入端：[本地仿真](/data/zc/datasets/LaDe/viewer/simulation/delivery_sim.py:701)、[Ray 仿真](/data/zc/datasets/LaDe/viewer/simulation/ray_delivery_sim.py:564)。
- 查询端：[q42/q43](/data/zc/datasets/LaDe/viewer/scripts/lade_cypher_templates.py:589)、[q48](/data/zc/datasets/LaDe/viewer/scripts/lade_cypher_templates.py:718)。
- 无协助者的处理：[helper 为 None 时返回](/data/zc/datasets/LaDe/viewer/simulation/delivery_sim.py:724)。

本次依据当前写入代码指出语义问题，没有把旧数据库中缺少新版字段的现象当作全部原因，也没有修改这些查询实现。

### 十一、结合当前任务应怎样使用

如果目标是“单智能体在决策前低延迟获得自身和协作知识”，以 i 系列组织工作负载更自然：记录具体 drone、目标 step、局部数据范围和整包结果。把返回内容逐项核对后，再接入实际 LLM 调用。

如果目标是“证明百万级图数据上能处理不同形状的协同查询”，q 系列有补充价值：按点查、状态时间窗、事件、跨智能体关系、聚合、路径和质量检查分组测试。全局诊断与每次在线决策的访问频率应按实际需求设定。

对于同一条查询的索引前后对比，需统一查询文本、参数、返回字段/行数限制、结果消费方式、并发调度、连接池、数据版本、预热与日志方式。i0 与 q2、i2 与 q3 的原始平均值，不能充当严格的同查询优化对照。

对于 500ms 指标，报告应明确对象是单条查询、一个 context 还是含 LLM 的完整决策：

```text
整次决策耗时
  = 调度等待
  + 获取知识上下文
  + 构造 prompt
  + LLM 请求与推理
  + 解析与动作应用
```

当前 i/q 脚本测量的是其中知识查询相关部分，不能代替完整决策延迟。`--repeat 3` 是同一次进程中的重复作业，也不自动构成验收要求的三轮独立实验；需要固定环境、分别运行并保留各轮报告。

若后续扩展到 50 多条 i 查询，应围绕单智能体情境设计：自身异常、任务优先级、能量安全、协助候选、接管过程、历史反馈。建立候选目录后按情境选包，每次具体取哪些信息，应由实际决策需求决定。
