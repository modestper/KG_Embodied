### 任务背景

用户希望在已有新任务替补派单的基础上，完善无人机之间的互助功能，使故障、低电和 deadline 风险无人机的未完成任务可以由其他无人机接管，并在 local、Ray、checkpoint、Neo4j 和动态页面中保持一致。

### 关键结论

- 互助会在每轮正常派单前执行，触发条件包括无人机 `failed/failure_mode`、剩余电量无法安全完成当前载货路线，以及预计无法在 deadline 前完成任务。
- 援助候选无人机必须队列可接单，且电量覆盖“现有路线 + 交接/取货 + 送达 + 返仓 + 安全余量”；deadline 风险转移只会选择能按时完成的援机。
- 未取货任务直接从原无人机释放并重派；已取货任务以原无人机当前位置为交接点，援机到达后才把货物加入 `onboard_tasks`。
- 支持多次接管：如果第一架援机尚未取得货物就故障，货物仍保留在原交接点，不会错误回到 depot；`previous_assignees` 防止任务在几架无人机之间来回循环。
- Ray 接管使用“源 actor 释放 -> 目标 actor 接收 -> 拒绝时恢复源 actor”流程，避免任务丢失或双重持有。
- Neo4j 新增 `task_assistance_requested`、`assist_dispatched`、`task_handover_completed`、`task_taken_over` 事件，以及 `ASSISTS`、`HANDOVER_TO`、`TAKES_OVER` 关系；旧 `ASSIGNED/CARRYING/TAKES_OVER` 关系会通过 `active=false` 结束当前有效性。
- 任务交接字段已进入 Ray payload、checkpoint、Neo4j Task、frame/task trace，旧 checkpoint 缺少字段时会使用默认值恢复。
- 动态页 Agent 和任务表新增互助状态，KG 事件会显示源无人机、援助无人机和互助原因。

### 后续建议

- 当前故障通过 `DroneAgent.mark_failed()` 或设置 `failure_mode` 注入，未实现随机故障模型和动态页手动故障按钮；如需现场演示，可再增加可重现的故障时刻/无人机 ID 参数。
- 当前环境无 Docker socket 权限，Neo4j 已通过 fake driver 验证字段、事件和 Cypher 关系结构，但未对真实 Neo4j 实例执行写入验收。
- `scripts/run_headless_sim.py --backend local --no-checkpoint-enabled` 仍会在初始化时捕获 checkpoint 并报“local 不支持 checkpoint”，属于已有 headless 脚本问题，本次未扩大范围修改。
- 接管策略目前是中央协调式，后续可在不改变任务所有权协议的前提下，把候选打分替换为知识图谱/LLM 协同决策。
