# i 系列查询的索引覆盖与性能风险

### 任务背景

用户希望确认：新增的 i 系列查询是否需要原先未配置的索引，否则查询可能很慢。本次以当前 `i56-observed-graph-v2` 目录及 `57687/61687` 两个真实实例为依据，只读检查索引和代表性查询计划；不创建索引、不改查询、不运行完整压测。

### 关键结论

- 部分新增查询确实有原三组索引之外的优化需求，主要是 Event 的时间窗口和任务事件关联。但没有这些索引并不导致语法错误或无法查询，而是可能扫描更多数据。
- 上轮修订完成的是现有结构对齐和有限功能验证，不代表已完成索引适配或全量性能优化。
- 当前 `57687` 只有 2 个默认 LOOKUP 索引，没有属性 RANGE 索引；因此一些旧查询和新增查询都存在按标签扫描后过滤的情况。
- 当前 `61687` 有同样的 2 个 LOOKUP，以及原来的 3 个 AgentState RANGE 索引，全部 ONLINE；它们能够被部分新增状态查询直接复用，不需要为每条新查询单独建索引。
- 两库的 i50/i54 仍使用 Event 标签扫描；仅把 URI 改为 `61687`，不能让整套 56 条查询都获得属性索引加速。
- 距离计算、排序、聚合和关联子查询也会产生开销；增加索引不能消除全部计算成本，LIMIT 也不保证扫描量同样很小。
- 不应在 `57687` 直接补索引，破坏现有基线；若评价整个 56 条目录的最佳性能，宜新增综合索引实验组，保留原 A/B 分组不变。
- 本次只有 SHOW INDEXES 和 12 条代表查询在两库各一次 EXPLAIN；没有 PROFILE、并发测试或速度倍数测量，不能给出实际加速倍数。

### 一、当前实际索引

| 实例 | 实际索引 | 当前状态 |
| --- | --- | --- |
| `bolt://127.0.0.1:57687` | 1 个节点 LOOKUP、1 个关系 LOOKUP | 均 ONLINE |
| `bolt://127.0.0.1:61687` | 同上，再加下列 3 组 AgentState RANGE | 均 ONLINE |

```text
lade_agent_state_run_drone_step
  AgentState(run_id, drone_id, step_index)

lade_agent_state_run_region_step
  AgentState(run_id, region_id, step_index)

lade_agent_state_run_step
  AgentState(run_id, step_index)
```

两个实例内部数据库名均为 `neo4j`。当前没有 Event、Drone、Step 或 Task 的属性索引。

LOOKUP 主要按标签/关系类型定位，不能等同于按 run_id、drone_id、时间区间等属性精确定位的 RANGE 索引。Neo4j 官方示例也区分 NodeByLabelScan 与属性索引访问。[官方索引使用说明](https://neo4j.com/docs/cypher-manual/current/indexes/search-performance-indexes/using-indexes/)

查询脚本只创建 Driver 并执行已有语句，不会调用仿真写入器的自动建索引逻辑。新增查询和“数据库新增索引”是两件独立的事，本轮及上轮均没有替用户创建索引。

### 二、实际 EXPLAIN 对照

参数为 run `hangzhou-0621-headless-002`、drone-1、step 2300、time 634、历史窗口 20 step、事件窗口 30 分钟、limit 10。这里只生成计划，不读取全部业务结果。

| 查询 | `57687` 的关键访问 | `61687` 的关键访问 | 解读 |
| --- | --- | --- | --- |
| i0 当前 Drone | Drone 标签扫描 | 同左 | 原有三索引不覆盖 Drone |
| i9 最新 Step | Step 标签扫描 + Top | 同左 | 原有三索引不覆盖 Step |
| i13 状态新鲜度 | AgentState 标签扫描 + Top | run/drone/step 索引查找 + Top | 能复用原索引 |
| i14 状态变化 | AgentState 标签扫描 + Sort | run/drone/step 索引查找 + Sort | 索引缩小候选，但本次计划仍有排序 |
| i32 附近可用伙伴 | 自身 AgentState 标签扫描，伙伴侧可通过 Drone/关系扩展 | 自身 run/drone/step、伙伴 run/step 索引查找 | 两处状态定位受益 |
| i33 任务/候选直达估算 | Drone、Region 标签扫描及关联计算 | 同左 | 不是 AgentState 查询，不受三组索引直接覆盖 |
| i36 区域队列比较 | 自身/伙伴 AgentState 标签扫描 | 自身 run/drone/step、伙伴 run/region/step 索引查找 | 能复用原索引 |
| i42 相邻快照电量变化 | 两处 AgentState 标签扫描 | 两处 run/drone/step 索引查找 | 可避免大范围状态扫描 |
| i44 区域任务压力 | Drone、Task 标签扫描 | 同左 | 可考虑 Task 区域入口 |
| i48 附近未完成任务 | Drone、Task 标签扫描，另有组合与 Top | 同左 | 还存在逐项距离计算 |
| i50 派单→取件 | assigned/later/pickup 三处 Event 标签扫描 | 同左 | 外层查询及内层任务关联缺少事件属性索引 |
| i54 取件→完成 | done/pickup 两处 Event 标签扫描 | 同左 | 同上 |

NodeByLabelScan 是扫描相应标签的候选，不应称为一定扫描全库所有标签。Apply 等相关子查询算子还可能使扫描随外层结果重复；仅统计计划中扫描算子的个数，不等于实际扫描次数。

EXPLAIN 不执行查询；实际耗时、行数、DB hits 和内存成本需要安全的小规模执行或 PROFILE 进一步测量。[官方执行计划说明](https://neo4j.com/docs/cypher-manual/current/planning-and-tuning/execution-plans/)

### 三、索引候选清单：仅建议，未创建

以下候选来自当前语句的实际谓词，不涉及新增节点、字段或虚构 location 属性。优先级是待验证的优化判断，不是已证实的加速排名；不建议一次全部创建。

| 优先级 | 索引候选 | 主要服务查询 | 说明 |
| --- | --- | --- | --- |
| 原有优先 | AgentState 的 3 组现有复合索引 | i1/i2/i6/i7/i11、i13-i16/i32/i34-i36/i42/i45/i49/i52/i53/i55 等 | 多条查询可共享；索引版已有，无需重复建 |
| 新增重点 | `Event(run_id, drone_id, time_minute)` | i4/i5/i26/i27/i30/i31/i37/i41/i43/i50/i51/i54 等的个人事件入口 | 对 actor 和时间先缩小范围；type 等额外条件仍可能需过滤 |
| 新增重点 | `Event(run_id, task_id, type, time_minute)` | i28/i50/i54 等内部任务事件关联 | i50 的后续派单和取件都带 task/type/time；drone 条件可作为额外过滤 |
| 后续评估 | `Event(run_id, region_id, time_minute)` | i10/i46/i47 等 | 补区域事件入口，不能被个人事件索引直接替代 |
| 后续评估 | `Drone(run_id, id)` | i0 及大量 SELF_CURRENT 入口 | 实体规模目前仅百级，单次收益不一定比大表重要 |
| 后续评估 | `Step(run_id, step_index)` | i9/i11、启动时解析 step 时间 | 需实查计划与读取规模 |
| 后续评估 | `Task(run_id, region_id)` | i8/i44 等区域任务检索 | status、deadline 等仍可能后过滤；不覆盖所有 Task 查询 |

复合索引的列顺序及实际谓词会影响可用性，不能把一个很宽的索引视作所有查询通用。尤其不能直接假定 Event 的 task 索引可以替代没有 task_id 条件的 actor 时间窗口查询。实际是否选用，以创建后的 EXPLAIN/PROFILE 为准。

不建议为 56 条查询各建一个索引，也不建议为所有返回字段建索引；很多字段只用于返回，不参与入口过滤。

### 四、不能单靠加索引解决的开销

- 当前距离条件是 x/y 标量运算和 sqrt。普通 x/y 索引不会自动把这个表达式变成空间索引查找。POINT 索引有专门的空间属性和查询方式，当前图谱没有这样的 location 字段，本轮不会凭空引用它。[官方空间类型说明](https://neo4j.com/docs/cypher-manual/current/values-and-types/spatial/)
- i33 按任务、候选无人机、已知 depot 计算路线，即使入口索引完善，仍有实际组合与距离计算。
- i14/i42 等需要窗口样本、相邻状态与聚合；状态索引可以缩小范围，但不会替代这些计算。
- 多数 LIMIT 位于过滤或排序之后，不能据 LIMIT 10 认定只读取 10 个节点。
- 每个 context 执行 56 条，而不是原来的 12 条；100 drone × 20 次为 112000 次模板调用，负载增加本身也会影响总耗时。
- 数据缓存、连接池、并发竞争和日志输出也影响观测耗时。本轮没有测这些因素。

### 五、保持实验可解释

建议区分三种实验目标：

1. **原有 A/B 对照**：A 为 57687，B 为 61687，只比较原三组 AgentState 索引；两组其他条件应保持一致，不随意增加 Event 等索引。
2. **56 条目录综合优化**：在单独实验组中逐步补充 Event 等候选索引，保留 A/B，明确这是新配置，不把全部收益归因于原三组索引。
3. **单项瓶颈验证**：先少量 drone、少量 repeat，对具体慢查询看计划和实测，不直接启动 100 worker 全目录重复扫描。

新增索引需要占用磁盘、构建资源并增加后续写入维护成本。由于本轮用户只询问原因，没有授权变更实验条件，因此仅给出候选与证据，不执行建索引。
