### 任务背景

原始 `--queries all --max-workers 100` 实验中，i0、i3、i4、i5 在无 AgentState 实验索引的 `lade` 上反而明显快于 `lade-index`。用户要求按原查询模板实际设计并执行实验，验证该差异是索引直接导致，还是混合查询的排队和负载节奏造成。

### 关键结论

- 猜想得到实验支持：三组 AgentState 索引没有直接拖慢 i0、i3、i4、i5。两库单并发平均耗时已经基本一致，原来约 1.5—11 倍的反向差异缩小到不足 1 ms 的绝对差值。
- 在100并发、只运行相同四条查询的两轮复测中，有索引库整体吞吐反而连续更高；两轮平均为 769.962 QPS，无索引库为 689.714 QPS，有索引库高约 11.6%。
- 合并两轮100并发的4,000个样本后，有索引库的 i0、i3、i4、i5 平均耗时分别比无索引库低约 21.5%、10.0%、4.2%、17.7%。因此无法复现原始混合负载中的反向退化。
- 单并发和两轮100并发共三组对照中，均有 2,000/2,000 个 context 的实际查询结果完全一致，所有正式实验均为0失败。
- `EXPLAIN` 显示四条查询在两库中的执行计划逐项相同：i0/i3 从 `NodeByLabelScan(Drone)` 开始，i4/i5 从 `NodeByLabelScan(Event)` 开始，没有使用或引用任何 AgentState 索引。
- 原始现象的主因是 `all` 混合负载中的自限流：无索引库的 i1、i6、i7、i8、i10、i11 很慢，阻塞每个 context worker，使 i0/i3/i4/i5 稀疏到达；有索引库快速通过这些步骤，100个 worker 持续形成更密集、更同步的查询波，客户端 `elapsed_ms` 包含更多排队和调度时间。

### 实验设计

实验前只读确认：

- `bolt://127.0.0.1:57687`：没有 `lade_agent_state_*` 索引，作为无索引组。
- `bolt://127.0.0.1:61687`：三组 `lade_agent_state_*` RANGE 索引均为 `ONLINE`，作为有索引组。

控制条件沿用用户模板：

- `run_id=hangzhou-0621-headless-002`
- 100个 drone：`drone-1` 到 `drone-100`
- `step_index=2300`
- `repeat=20`，每轮2,000个 context
- `max-connection-pool-size` 与 worker 数一致
- 查询只选择 `i0,i3,i4,i5`，去除会造成自限流的 AgentState 查询

执行两类实验：

1. `max-workers=1`：观察基本不排队时的单查询延迟，各库正式运行一轮。
2. `max-workers=100`：给两库施加完全相同的高并发查询组合，执行两轮并交换顺序：
   - 第1轮：有索引 → 无索引
   - 第2轮：无索引 → 有索引

正式运行前分别执行了100个 context 的预热。所有结果写入：

```text
test/controlled_non_agentstate_20261009/
```

没有追加或覆盖原来的 `test/index_*.jsonl` 和 `test/*.jsonl`。

### 单并发实验结果

每库2,000个 context、8,000次查询，全部成功：

| 查询 | 无索引 avg | 有索引 avg | 无索引 P95 | 有索引 P95 | avg绝对差 |
|---|---:|---:|---:|---:|---:|
| i0 | 1.081 ms | 1.297 ms | 1.688 ms | 1.983 ms | 0.216 ms |
| i3 | 1.423 ms | 1.621 ms | 1.971 ms | 2.209 ms | 0.198 ms |
| i4 | 21.968 ms | 22.534 ms | 25.971 ms | 27.889 ms | 0.566 ms |
| i5 | 21.824 ms | 22.583 ms | 25.820 ms | 29.661 ms | 0.759 ms |

整体：

| 指标 | 无索引 | 有索引 |
|---|---:|---:|
| 墙钟时间 | 93.065 秒 | 96.540 秒 |
| 吞吐 | 85.962 QPS | 82.867 QPS |
| 成功查询平均耗时 | 11.574 ms | 12.009 ms |

两库整体差约3.7%，单条查询绝对差都小于1 ms。预热轮中方向还发生过反转：有索引库为75.470 QPS，无索引库为69.141 QPS，说明这个量级会受缓存、容器状态和运行时抖动影响，不能解释为索引导致的稳定退化。

### 100并发实验结果

两轮每库均为2,000个 context、8,000次查询且0失败：

| 轮次 | 无索引吞吐 | 有索引吞吐 | 有索引相对提升 |
|---|---:|---:|---:|
| 第1轮（有索引先跑） | 674.919 QPS | 758.972 QPS | 12.5% |
| 第2轮（无索引先跑） | 704.509 QPS | 780.951 QPS | 10.8% |
| 两轮平均 | 689.714 QPS | 769.962 QPS | 11.6% |

合并两轮、每条查询4,000个样本：

| 查询 | 无索引 avg/P50/P95 | 有索引 avg/P50/P95 | avg对比 |
|---|---:|---:|---:|
| i0 | 108.051 / 101.686 / 212.320 ms | 84.828 / 75.182 / 170.746 ms | 有索引低21.5% |
| i3 | 142.924 / 125.504 / 300.875 ms | 128.635 / 119.752 / 255.461 ms | 有索引低10.0% |
| i4 | 183.003 / 154.529 / 375.980 ms | 175.395 / 163.092 / 329.157 ms | 有索引低4.2% |
| i5 | 115.666 / 109.911 / 211.034 ms | 95.210 / 86.435 / 177.267 ms | 有索引低17.7% |

这里有索引库更快也不能解释为 AgentState 索引直接优化了这些查询，因为查询计划中没有使用它们。更合理的理解是两个独立容器的缓存、CPU调度和运行时状态存在小幅波动；关键证据是，在相同查询组合与并发压力下，原始的巨大反向差异彻底消失，而且交换顺序后结论保持。

### EXPLAIN 结果

两库四条查询的规范化计划完全相同：

- i0：`NodeByLabelScan(Drone)` → `Filter(run_id,id)` → `Limit`
- i3：`NodeByLabelScan(Drone)` → `Filter` → `Expand(ASSIGNED|CARRYING)` → Task过滤与聚合
- i4：`NodeByLabelScan(Event)` → 时间和drone过滤 → `OptionalExpand(ABOUT_TASK)` → Top/Limit
- i5：`NodeByLabelScan(Event)` → 时间和drone过滤 →聚合

计划同时暴露了后续优化机会：

- i0/i3 每次扫描约100个 Drone，单并发仅约1—2 ms，当前收益空间不大。
- i4/i5 每次计划扫描约26,454个 Event，单并发约22 ms；若需要继续优化，应评估 Event 的 `(run_id, drone_id, time_minute)` 复合索引，而不是 AgentState 索引。

### 原始现象为何出现

原始 `--queries all` 中，每个 worker 串行执行 i0→i11，再领取下一个 context：

```text
无索引：i0 → [i1慢扫描] → i3/i4/i5 → [i6/i7等慢扫描] → 下一context
有索引：i0 → i1很快 → i3/i4/i5 → i6/i7等很快 → 迅速进入下一context
```

无索引库整轮约264秒，有索引库约29秒。虽然两边都是100个 worker，但 i0/i3/i4/i5 的实际到达率完全不同：无索引组被其他慢查询节流并逐渐错峰；有索引组持续快速循环，形成请求波。查询脚本测量的是客户端从 `session.run()` 到结果读取完毕的端到端时间，其中包含连接、Bolt、服务器队列、线程调度和执行时间，所以在更密集的请求波中单条便宜查询可能显示更高延迟。

受控实验把查询组合固定后，这种跨查询自限流差异被移除，两个数据库表现接近，有索引库甚至在两轮高并发中稳定略快。因此原结果不能用于声称 AgentState 索引使 i0/i3/i4/i5 退化。
