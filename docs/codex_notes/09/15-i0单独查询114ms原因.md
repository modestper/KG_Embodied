### 任务背景

用户反馈只运行 i0 时平均延迟仍约 114 ms，怀疑 AgentState 索引使原来 11 ms 的查询变慢。本次结合最新原始日志，用保持索引不变、只改变查询工作线程数的对照测试验证。

### 关键结论

- 找到用户本次结果：2026-09-15 15:20，2000 个 context，每个仅执行 i0，涉及 100 个 drone；2000 次全部成功，整批耗时 3382.994 ms，吞吐 591.192 次/秒，单查询平均 114.002 ms，P95 为 252.804 ms。
- 只选择 i0 并不代表串行。脚本使用 `max_workers = args.max_workers or len(drone_ids)`，没有显式设置线程数时，100 个 drone 对应最多 100 个工作线程。原日志未保存确切 max_workers 命令值，但执行区间明显重叠，排除了逐个串行执行；结合总耗时与各 context 耗时，本次整批平均约有 67.49 个 context 同时执行。
- 使用相同 100 个 drone、相同 run 和 i0 模板，每组 2000 次，固定连接池上限 100，保持三组 AgentState 索引不变；线程数 1/10/100/1 对应单查询平均 0.757/11.705/95.163/0.757 ms。
- 在未删索引的情况下恢复串行就能恢复到亚毫秒级，证明 i0 并未因索引而永久增加约 100 ms 的固有读取成本。高并发在当前客户端与数据库组合下足以产生接近用户结果的延迟。
- 用户旧混合测试中的 i0 每秒约完成 4.53 次，本次 i0 独立测试每秒约完成 591 次，强度约为旧值 130 倍。相同工作线程总数下，其他慢查询会改变各线程执行 i0 的时间分布，因此这两种工作负载不能直接作为索引前后单查询性能对照。
- 当前对照支持并发负载是重要原因，不能据此精确归因为某一个因素，例如 Python GIL、连接池耗尽、服务端排队或 GC；这些需要进一步记录或剖析。

### 原理解释

#### 查询工作没有自动增加

此前保存的索引前后执行计划表明 i0 均为 Drone 标签扫描、run_id/id 过滤、LIMIT 1、属性读取和输出。新增索引属于 AgentState，i0 没有访问 AgentState，也不会因 schema 新增三组索引而在每次读取时额外遍历它们。

目前未进行删除索引的因果 A/B 实验，因此严格说不能宣称索引对整个混合读写系统毫无间接影响；但是本次索引始终保留，串行延迟始终约 0.76 ms，已经足以否定“索引导致 i0 无法回到低延迟”的判断。

#### 114 ms 是端到端响应时间

脚本计时覆盖 `session.run()` 和结果遍历、转为 Python 字典的过程。该区间可包含连接获取、网络协议处理、数据库执行以及线程调度和解码等待。程序开始执行 context 之前的线程池任务等待不包含在单条查询计时内。

一个很短的查询在单线程下可以很快完成；多个线程密集发出这种短请求时，客户端共享资源、连接管理、服务端事务和调度等开销可能超过有效读取工作。此时增加线程并不一定增加吞吐；本次 100 线程吞吐低于 1 线程，说明当前配置下出现了并发扩展效率下降。

不能用 `114 ms / 100 = 1.14 ms` 推出真正数据库执行时间，也不能把 `3383 ms / 2000 = 1.69 ms` 当成单请求响应延迟：并发请求的等待与执行在墙钟时间上相互重叠。后一数值是吞吐的倒数，含义不同。

#### 为什么以前混合查询只有 11 ms

旧测试 2000 个 context、每个 12 条查询，在 441.252 秒完成。每个线程内部依次执行 i0 到 i11；i1/i6/i7 等慢查询让线程长时间停留在其他查询，i0 的完成频率只有约 4.53 次/秒。

只执行 i0 时，完成一次后线程立即开始下一次 i0；本次达到 591.192 次/秒。总并发工作线程数即便相同，i0 的请求密度也完全不同。这里比较的是稀疏混合负载下 i0 的响应与密集同类型负载下的响应，不能只看“有没有索引”一个条件。
