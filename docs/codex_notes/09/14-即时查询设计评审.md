# 即时 Neo4j 查询设计评审

### 任务背景

评审 `scripts/lade_llm_context_queries.py`，判断其是否适合 drone 调用 LLM 前获取上下文，并检查查询类型覆盖情况。实际模板为 i0 到 i11，共 12 条；如果不计 i0，则是 11 条。此次为静态评审，不修改查询代码、不访问实验数据库。

### 关键结论

- 围绕自身状态、短期记忆、任务、区域协同及全局摘要获取小结果集，业务方向合理；但尚不能称为全面的图查询基准。
- i2 使用 SQL 风格 BETWEEN，应改为 Cypher 的两个比较条件；现有 mock 测试不会解析 Cypher，不能证明模板可执行。
- i0、i3、i8 读取可变 Drone/Task 当前属性，不能保证对应指定的历史 step，可能向 LLM 泄露未来状态。
- 已覆盖点查、范围过滤、排序截断、一跳遍历、可选匹配、属性关联、去重和聚合；业务 category 不等同于数据库操作类型。
- 未覆盖存在性/反连接、多跳图模式、真正的空间查询、跨时刻变化检测和路径搜索；应按业务价值选择补充。
- 逻辑上 i11 只聚合一个 step 的状态，有完整快照且每 step 为 100 个 drone 时约为 100 条。实际访问量取决于执行计划和索引，不能据此认定它比 i2 更慢。
- 本次没有运行真实 Neo4j EXPLAIN/PROFILE，因此不提供性能排序或实际耗时结论。

### 逐条分类

同一条查询可以包含多种操作，以下是逻辑结构分类，实际物理算子以执行计划为准。

| 编号 | 业务内容 | 查询类型 | 说明 |
| --- | --- | --- | --- |
| i0 | 单个 drone 当前属性 | 复合键等值点查 | run_id + drone_id 定位；LIMIT 1 不等于有唯一约束 |
| i1 | 不晚于指定 step 的最近状态 | 时间上界过滤 + Top-1 | 返回一条，但不属于严格等值点查，可能匹配多条历史状态 |
| i2 | 自身近期轨迹 | 双边时间范围 + Top-K | 最近窗口内按 step 倒序截断；当前 BETWEEN 需修正 |
| i3 | 已分配或携带的未完成任务 | 一跳关系遍历 + 过滤 + 去重聚合 + Top-K | ASSIGNED/CARRYING 两类边，collect DISTINCT 合并任务关系 |
| i4 | 自身近期事件及关联任务 | 时间窗口 + 可选一跳匹配 + Top-K | OPTIONAL MATCH 保留没有任务关联的事件 |
| i5 | 自身近期分配、取件、完成及超时数 | 时间窗口 + 条件聚合 | 扫描窗口内匹配事件后形成单行摘要 |
| i6 | 本区域同一步状态分布 | 最新状态定位 + 属性关联 + 分组聚合 | 按 region_id 和 step_index 关联其他状态，再按 status 分组 |
| i7 | 本区域其他 drone 候选 | 最新状态定位 + 属性关联 + 排除自身 + Top-K | 按队列长度及剩余电量排序，没有空间距离过滤 |
| i8 | 本区域已知、临近截止的未完成任务 | 状态到任务的属性关联 + 多条件过滤 + Top-K | 含 release/deadline 条件，但 Task.status 是最新值 |
| i9 | 指定 step 之前最近全局摘要 | 时间上界过滤 + Top-1 | 读取预先写好的 Step 摘要，不现场扫描全部任务聚合 |
| i10 | 本区域近期事件 | 最新状态定位 + 属性关联 + 时间窗口 + Top-K | 获取所在区域后过滤事件，不是多跳图遍历 |
| i11 | 同一步的区域负载排行 | 最新 Step 定位 + 属性关联 + 分组聚合 + Top-K | 按区域汇总该 step 的 AgentState，非整个 run 历史扫描 |

整体主要是属性检索和聚合，一跳关系访问集中在 i3/i4。self、history、task、event、region、coordination、global 是业务标签；例如 global 不能直接解释为高成本查询。

### 需要优先处理的问题

1. **高优先级：i2 的范围表达式。** `scripts/lade_llm_context_queries.py:86` 使用 `WHERE a.step_index BETWEEN $start_step AND $step_index`。应写为 `WHERE a.step_index >= $start_step AND a.step_index <= $step_index`。i2 被 decision、diagnostic、all 包引用，错误会导致这些包中的轨迹查询失败；core 未包含它。官方文档以不等比较表达范围，本次未连接数据库复现。

2. **高优先级：历史上下文混入当前状态。** i0 位于脚本第 33 行，i3 位于第 99 行，i8 位于第 213 行。`simulation/knowledge.py:265` 每步更新 Drone，事件写入也更新 Drone/Task。若数据库已跑到 step 1000，查询 step 100 时，i1 返回历史状态，而 i0 返回最新状态；i3/i8 会按最新 completed 状态排除 step 100 当时尚未完成的任务。仅自动解析 step 对应时间不能解决，应明确“实时最新读取”与“历史回放”的语义。历史任务信息需从截止时刻之前的事件重建，或增加任务快照/有效时间版本。

3. **中优先级：在线查询可能读到不完整或混合 step。** `simulation/knowledge.py:243` 的 Step 写入与后续 AgentState 写入是两次 session.run；查询脚本第 536 行开始逐条执行查询，不能据此保证整包结果来自同一已完整写入的 step。i1/i6/i7 等允许向旧 step 回退，i9/i11 可能使用较新的 Step。建议采用完整写入的 step 标记或原子提交 Step 与状态，并让查询围绕已完成 step 工作，返回实际 step 和状态年龄；只把读取放进一个事务也不能替代数据版本设计。

4. **中优先级：i7 的 nearby 容易被误解。** 脚本第 188 行的查询只筛同一区域，未计算距离，也没有容量、可接单状态、续航可达性等完整候选约束。可以作为区域人员列表，但不足以直接作为最近可用协作对象列表。

5. **中优先级：摘要字段解释与写入不同步。** i9 的 completed_tasks 来自 `simulation/knowledge.py:80` 的 `len(completed_this_step)`，表示本步完成数，不是累计完成数。i0 的 updated_at 在事件写入时设置，但 AgentState 批量更新 Drone 时未同步，因此不能用它精确表示这些属性最后一次更新的时间。

6. **数据覆盖限制：i8 不是全部待分配任务。** 当前 Task 节点在任务事件发生时写入，而不是必然在任务释放时全部写入。查询描述中的“图谱已经知道的”是必要限定。若要让 LLM 据此安排所有待分配任务，需先确保任务释放时已入图。deadline 条件没有下界，会包含已过期任务，这可以合理，但最好区分已逾期与即将到期；若要任务接单候选，还需排除已被其他 drone 接管的任务。

### 可以补充的类型

| 类型 | 本项目中的例子 | 优先级及条件 |
| --- | --- | --- |
| EXISTS / NOT EXISTS，半连接及反连接 | 判断某任务是否已被接管；筛出已释放但没有有效分配的任务 | 高；先保证 Task 入库完整，并定义分配有效性及历史时间条件 |
| 空间范围 / 最近邻 | 查询一定距离内、容量和续航满足条件的 drone，按距离取前 K | 高；可使用现有 x/y，先确认坐标单位；空间索引需相应 point 数据 |
| 跨时刻关联 / 差分 | 对比同一 drone 在两个 step 的位置、电量、队列，找停滞或异常消耗 | 高；现有 AgentState 可支持，缺失采样不能当成零变化 |
| 固定多跳图模式 | Drone → ASSIGNED → Task → BELONGS_TO → Region，或 Drone ← ABOUT_DRONE ← Event → ABOUT_TASK → Task | 中；现有边可支持，需与单跳查询形成不同业务问题，而不是只增加跳数 |
| 多分支关联 / 星型模式 | 围绕任务同时获取相关事件、执行 drone 和区域状态 | 中；避免多分支匹配将结果行乘开而重复计数，分支可先聚合 |
| 可达性 / 有界变长路径 / 最短路径 | 查询区域之间能否通行、最低成本路线 | 有明确路网需求再加；当前图谱关系主要是归属和事件，不能把这些边的跳数当成飞行距离 |
| 全文 / 向量检索 | 从文本经验或异常说明中查类似案例供 LLM 参考 | 当前非优先；需要文本或嵌入数据及检索质量评估 |

UNION、UNWIND 批量参数、子查询等也尚未在这 12 条模板中充分覆盖，但它们更多是表达或执行组织方式，不必每个关键字都单独设计一条业务查询。查询类型全面性应由真实决策需求和实验目标驱动。

### 性能实验的边界

- LIMIT 限制返回行数，不保证只访问这些行；聚合前的匹配规模与排序/索引利用更重要。
- 数据库有百万 AgentState，不等于每条查询访问百万条。单 step、单 drone 与全历史范围应作为不同负载分别报告。
- i11 可能只聚合约 100 个状态，i2 默认也是短窗口，不能在没有 PROFILE 的情况下固定排成轻量、中等、重型。
- 保留逐条 elapsed_ms、成功率、结果行数和整包延迟；当前 elapsed_ms 包括 session.run 到结果遍历和 Python 转换，可包含连接等待及网络成本，不是纯服务器执行时间。
- 当前按模板汇总可用于比较；by_category 仍按业务分类，若要按查询算子比较，应另加分类维度。
- 100 个 context 的线程池提交是并发负载，不保证 100 条语句同一时刻开始。真实 agent 工作负载和同步突发测试应分别描述。
- 比较多个 step、繁忙/空闲区域、不同时间窗口、不同结果上限、冷热缓存和并发度，并单独报告失败，避免把错误返回很快当作查询优化。
- 正式业务中 i9 可以按 run/step 共享，i6 可按 run/step/region 共享；若实验要求每个 drone 独立查库，应保留该负载，同时注明没有启用共享缓存。

### 后续建议

1. 先修复 i2 范围语法，并确定当前查询是实时最新语义还是严格历史回放语义。
2. 用目标 Neo4j 版本对每个模板运行 EXPLAIN 校验，再使用少量真实数据核对结果；mock 测试只能验证脚本编排和计时。
3. 优先补充存在性/反连接、空间候选和跨 step 差分，再按决策需求添加固定多跳查询。
4. 查看实际索引和 PROFILE，记录匹配量、访问量及耗时后，再定义查询复杂度分组。
