# 100 个 drone 并发查询秒级延迟排查

### 任务背景

用户对 run `million-nodes-hangzhou-0621-100agents` 的 step 2300，使用 100 个 drone、repeat=20、max_workers=100 执行 i0–i11。总计 2000 个 context、24000 条查询，22000 成功、2000 失败，墙钟耗时 441.252350 秒。目标是解释秒级延迟，不修改数据库配置、不改变已有实验结果。

### 关键结论

- 当前数据库版本为 Neo4j Community 2026.05.0。SHOW INDEXES 仅返回两个 ONLINE 的 LOOKUP 索引，没有任何属性搜索索引。
- 当前数据库全部 run 合计有 1,645,930 个 AgentState。EXPLAIN 确认慢查询使用 NodeByLabelScan 后再按 run/drone/step 过滤，而非属性索引定位。
- i1 有一次 AgentState 标签扫描；i6/i7 各有两次。其平均耗时分别约 2.47 秒、5.55 秒、5.29 秒，与扫描结构高度吻合。
- i1/i6/i7/i8/i10/i11 占成功查询累计客户端计时时间约 97.21%；i6+i7 占约 49.79%。优化应先集中在这些查询的 AgentState 访问方式。
- i2 的失败日志明确报 Invalid input 'BETWEEN'，是语法错误，与数据库并发承载能力无关。
- 计时覆盖客户端调用到结果读取和转换，可能包含连接等待、服务端排队、执行、网络及客户端调度成本，不能全部归为服务器计算时间。
- 100 worker 将昂贵查询并发执行，是延迟放大因素；没有原实验 CPU/I/O/GC 监测，无法量化各项资源争用。本次 EXPLAIN 是当前计划，不是原实验 PROFILE。
- 本次未创建索引、未修改查询或原始日志，也未重跑压测。

### 为什么返回一行也要几秒

以 i1 为例：

```cypher
MATCH (a:AgentState {run_id: $run_id, drone_id: $drone_id})
WHERE a.step_index <= $step_index
RETURN a.step_index AS step_index, a.status AS status
ORDER BY a.step_index DESC
LIMIT 1
```

当前 EXPLAIN 的关键逻辑为：

```text
NodeByLabelScan(a:AgentState)
  -> Filter(run_id, drone_id, step_index)
  -> Top(step_index DESC LIMIT 1)
  -> 返回属性
```

没有对应属性索引时，run_id 条件不是先把存储物理分成一个 run 再扫描，而是在 AgentState 标签扫描之后筛选。扫描范围包括其他 run 的 AgentState。

由于要找最大 step，Top 需要检查全部满足过滤条件的候选；LIMIT 1 限制输出，不使前面的无序标签扫描只读一个节点。Top 也不一定完整排序全部候选，不能把全部耗时简单称为“排序耗时”。主要已证实的问题是访问路径过宽。

SHOW INDEXES 的两个 LOOKUP 索引只能帮助按标签或关系类型定位，不支持 run_id、drone_id、step_index 属性条件的快速定位。它们与复合属性索引不是一回事。

| i7 | 5288.977 ms | 同样两次 AgentState 扫描，之后排除自己并做候选排序 |

AgentState 总数 1,645,930 来自实际计数；上表其他标签行数来自 EXPLAIN 的 EstimatedRows，是估计，不能当成实际 PROFILE 行数或 DB Hits。

i6/i7 各包含两个 AgentState 标签扫描节点，self 被 Top-1 限定，因此这里不是 self 历史条数乘以全部状态的无限扩张，但仍要做两次大范围扫描。i8/i10 虽然主要业务是任务/事件，它们的前置 self 查询同样昂贵。

这也解释了为何 i11 逻辑上只需要某一步约 100 个状态，仍然很慢：当前访问路径先从百万标签记录中找出这 100 个。最终 rows_avg=10 是区域聚合和截断后的行数，无法反映此前的访问规模。

### 100 并发和计时的含义

一个 worker 执行某个 drone 的一包 12 条查询，包内顺序执行，不是 100 × 12 = 1200 条同时执行。线程池会提交 2000 个 job，最多约 100 个同时运行，剩余 job 排队。repeat=20 不包含每一轮所有 drone 必须同步完成的屏障，某个 worker 空闲后会直接执行下一个 job。

单条 elapsed_ms 从 session.run 前计时，到结果遍历和 Python 字典转换完成为止。连接获取如在 session.run 内发生，其等待也会计入；数据库及客户端线程争用同样可能计入。日志不能将这些阶段单独拆开。

context 的计时在 worker 真正开始 execute_context 时开始，因此不包含 job 在线程池提交队列里的等待。整体 wall_ms 包含所有 job 执行和输出日志开销。

本次结果算得：

- 成功查询平均耗时约 1.978 秒；每个 context 有 11 条成功查询，11 × 1.978 约为 21.759 秒，与 context 平均 21.776 秒吻合。
- 2000 × 21.775865 / 441.252350 约为 98.70，可理解为按 context 计时覆盖范围推算的平均活跃 context 数，说明线程池大部分时间处于接近 100 个活跃 job 的状态，不等于 CPU 有 98.7 个核心在运行。
- 打印的 54.391 qps 包含失败尝试，成功吞吐为 22000 / 441.252350，约 49.858 qps。
- 100 个 context 同时进行大范围读取，会竞争 CPU、内存带宽、页缓存和调度资源；若缓存不命中还会引入磁盘读取。但没有当时的遥测，不能确定哪项资源已经饱和，也不能断言连接池就是主要瓶颈。

### i2 和资源情况

原始日志的 i2 错误是：

```text
Neo.ClientError.Statement.SyntaxError
Invalid input 'BETWEEN'
WHERE a.step_index BETWEEN $start_step AND $step_index
```

应修为：

```cypher
WHERE a.step_index >= $start_step AND a.step_index <= $step_index
```

本次 2000 个 context 都缺少成功的 i2 轨迹结果，不能将本次称为完整 12 条查询全部成功的测试。None 表示没有成功样本，不是零耗时。

当前 /tmp 与 /data 分区均约 73% 使用率；当前 MemAvailable 约 149 GiB，swap 9.5 GiB 已用满。不能从 swap 已占用就推断正在频繁换页，也不能把当前磁盘/内存情况当成 9 月 7 日实验现场。需要在后续对照实验同步记录 CPU、I/O、换页和 Neo4j 内存指标。

### 后续建议

先在独立的优化实验阶段创建对应索引，再验证计划和少量查询。创建索引会改变后续基线并产生建索引负载，本文只给出候选命令，尚未执行。

```cypher
CREATE INDEX lade_agent_state_run_drone_step IF NOT EXISTS
FOR (a:AgentState) ON (a.run_id, a.drone_id, a.step_index);

CREATE INDEX lade_agent_state_run_region_step IF NOT EXISTS
FOR (a:AgentState) ON (a.run_id, a.region_id, a.step_index);

CREATE INDEX lade_agent_state_run_step IF NOT EXISTS
FOR (a:AgentState) ON (a.run_id, a.step_index);
```

第一条服务 i1/i2 和 i6/i7/i8/i10 的 self 定位，第二条服务 i6/i7 的同区域同一步定位，第三条服务 i11。不能因为前两条包含 run_id 和 step_index 就认定它们能够直接替代第三条：i11 没有 drone_id 或 region_id 过滤，复合索引使用条件需看实际计划。

索引 ONLINE 后检查计划是否改为合适的 NodeIndexSeek/范围检索，是否利用索引顺序避免额外 Top/Sort；不能仅根据索引已经创建就认定优化成功。必要时再考虑 Step(run_id, step_index)、Event(run_id, drone_id, time_minute)、Event(run_id, region_id, time_minute) 等索引。

后续验证顺序建议：

1. 先保存当前汇总和原始日志为未优化基线，避免把追加 JSONL 中的旧实验混入本次。
2. 修复 i2 语法，另行验证它的结果和访问计划；修复后会新增实际轨迹查询负载，不能忽略这个前后差异。
3. 建立优先的 AgentState 索引并等到 ONLINE；小样本核对语义与计划。
4. 在相同 run/step/查询参数下比较 1、10、20、50、100 worker；记录池大小、成功率、每条延迟分位数、成功吞吐和实际系统负载。
5. 优化前后分别保存文件，明确数据是否继续增长、Neo4j 是否有并发写入及缓存状态。不能保证建索引后固定降到某个毫秒值，需实测。
6. 业务接入时再考虑复用 i1 的自身状态、按 run/step 共享 i9/i11 等结果；作为独立 drone 查库基准时则明确保留重复查询负载。
