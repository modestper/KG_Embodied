### 任务背景

用户观察到：删除三组 `AgentState` 索引后，大部分即时查询耗时下降，但不直接访问 `AgentState` 的 `i0`、`i3` 反而变慢。用户希望通过可重复实验找到原因。

被删除的索引为：

```text
lade_agent_state_run_drone_step
lade_agent_state_run_region_step
lade_agent_state_run_step
```

### 关键结论

- `i0` 只读取 `Drone`；`i3` 读取 `Drone`、`ASSIGNED|CARRYING` 和 `Task`。删除 AgentState 索引理论上不会直接增加二者的图访问工作量，应先比较 ON/OFF 执行计划。
- 当前压测器是闭环模型：worker 完成一个 context 后立即领取下一个。其他查询变快会自动提高下一轮 `i0` 和后续 `i3` 的到达率，可能使其排队时间增加。
- 第一优先实验是分别只跑 i0、只跑 i3，在索引 ON/OFF 下测试 `1/10/25/50/100` worker。如果单线程相同而高并发分叉，说明主要是并发排队而非 Cypher 固有成本。
- 第二优先实验是固定请求到达率。当前闭环模型不能保证索引 ON/OFF 承受相同 QPS，不能直接作为严格因果 A/B。
- `--queries all` 包含当前会报语法错误的 i2，失败响应也会改变 i3 的到达节奏。第一轮应使用单查询、`core` 或显式排除 i2。
- 应做 A-B-A 或两个独立副本的重复实验，排除缓存、测试顺序、后台负载和 schema 刚变化后的瞬态影响。

### 待验证假设

#### H1：闭环负载放大

```text
多数查询变快
  -> context 更快完成
  -> worker 更快发出下一轮请求
  -> i0/i3 的单位时间请求数增加
  -> 共享资源排队增加
  -> 端到端 elapsed_ms 上升
```

支持证据应为：串行 i0/i3 基本不变，高并发才分叉；删除索引后 context 吞吐和 i0/i3 每秒完成数更高；固定 QPS 后差异减小。

#### H2：i0/i3 执行计划变化

支持证据应为：ON/OFF 的 Operator、Rows、DB Hits 或 runtime 不同，并且单线程预热后仍稳定分叉。

如果执行计划完全相同且单线程相同，可以基本排除。

#### H3：缓存或 schema 瞬态

删除索引可能触发查询计划失效、checkpoint、page cache 重排。支持证据应为：第一轮差异大，预热后收敛；A-B-A 中结果随测试顺序漂移；慢的一轮 page cache misses 或 I/O 更高。

#### H4：客户端、Bolt 或结果消费瓶颈

当前 `elapsed_ms` 包含 `session.run()`、Neo4j 排队、Bolt 往返、结果拉取、驱动解码和 `row_to_dict()`。如果不访问图的 `RETURN 1` 也在高并发下变慢，说明主要延迟不在图扫描。

#### H5：连接池或服务端饱和

如果增加 worker 后延迟上升而吞吐不再增加，说明进入饱和区。pool=10 明显差于 pool=100 说明连接池不足会放大延迟；pool=100 仍恶化则瓶颈更可能在服务端或客户端调度。

### 实验前固定条件

每轮必须固定并记录：

- 同一个目标容器、相同数据，两个 run 不再写入；
- 相同 run、drone、step、repeat、worker、连接池；
- 相同查询集合和顺序；
- 相同日志开关与预热方法；
- 不同时运行其他压测；
- 所有现存索引均为 `ONLINE`；
- 每轮使用新的输出文件，不追加旧 JSONL；
- 每个条件至少重复 3 次。

### 实验 0：保存数据与 schema 基线

ON/OFF 两种状态都保存：

```cypher
SHOW INDEXES
YIELD name, state, type, labelsOrTypes, properties
RETURN name, state, type, labelsOrTypes, properties
ORDER BY name;
```

保存目标 run 的节点分布：

```cypher
MATCH (n)
WHERE n.run_id = 'million-nodes-hangzhou-0621-100agents'
   OR (n:Run AND n.id = 'million-nodes-hangzhou-0621-100agents')
RETURN labels(n) AS labels, count(*) AS node_count
ORDER BY node_count DESC;
```

目的：确保 ON/OFF 之间只改变索引，没有改变数据。

### 实验 1：比较 i0/i3 执行计划

ON/OFF 分别运行相同 `EXPLAIN`；需要实际 Rows/DB Hits 时只运行少量 `PROFILE`。重点比较：

```text
Operator
Details
Rows
DB Hits
Page Cache Hits/Misses
Runtime
```

i0 示例：

```cypher
PROFILE
MATCH (d:Drone {
  run_id: 'million-nodes-hangzhou-0621-100agents',
  id: 'drone-1'
})
RETURN d.id AS drone_id,
       d.status AS status,
       d.region_id AS region_id,
       d.x AS x,
       d.y AS y,
       d.queue_len AS queue_len,
       d.onboard_count AS onboard_count,
       d.battery_remaining_m AS battery_remaining_m,
       d.total_distance_m AS total_distance_m,
       d.updated_at AS updated_at
LIMIT 1;
```

i3 应复制脚本中的完整模板，使用相同参数。PROFILE 有额外开销，不应把它的耗时放入正式排行榜。

### 实验 2：单查询 × worker 曲线

这是优先级最高的实验。准备变量：

```bash
DRONE_IDS=$(printf "drone-%s," $(seq 1 100))
DRONE_IDS=${DRONE_IDS%,}

read -rsp '目标查询库密码: ' TARGET_NEO4J_PASSWORD
echo
export TARGET_NEO4J_PASSWORD
```

索引 OFF 时只测 i0：

```bash
mkdir -p data/index_experiments/off

for WORKERS in 1 10 25 50 100; do
  NEO4J_URI=bolt://127.0.0.1:37687 \
  NEO4J_USER=neo4j \
  NEO4J_PASSWORD="$TARGET_NEO4J_PASSWORD" \
  NEO4J_DATABASE=neo4j \
  ./run_in_lade.sh python scripts/lade_llm_context_queries.py \
    --run-id million-nodes-hangzhou-0621-100agents \
    --drone-ids "$DRONE_IDS" \
    --queries i0 \
    --repeat 20 \
    --max-workers "$WORKERS" \
    --max-connection-pool-size 100 \
    --no-query-log \
    --no-context-log \
    --summary-json "data/index_experiments/off/i0_w${WORKERS}.json" \
    --progress-every 0
done
```

将 `--queries i0` 改为 `--queries i3`，输出文件名改成 `i3_w...`，再执行一组。

索引 ON 时使用完全相同的命令，只把目录从 `off` 改成 `on`。每个条件重复 3-5 轮，记录 avg、P50、P95、P99、wall 和 QPS。

判断：

- worker=1 接近、高 worker 分叉：支持并发排队。
- worker=1 也稳定分叉：检查计划、缓存、后台活动。
- 延迟上升且吞吐下降：系统可能过饱和。
- 延迟上升但吞吐显著提高：可能是更高吞吐换取更高响应时间。

### 实验 3：固定 drone 的串行固有成本

```bash
NEO4J_URI=bolt://127.0.0.1:37687 \
NEO4J_USER=neo4j \

  --progress-every 0
```

ON/OFF 各执行多轮。该实验消除不同 drone 扫描位置和关系数量差异，最接近热缓存串行固有成本。

### 实验 4：查询组合消融

固定 worker=100，依次测试：

```text
i0
i3
i0,i3
i0,i1,i3
i0,i1,i3,i6
core
```

如果单独 i0/i3 不变，但加入 i1/i6 后开始变化，说明影响来自查询混合和请求节奏。

### 实验 5：查询顺序

显式选择会保留输入顺序，可测试：

```text
--queries i0,i1,i3
--queries i1,i0,i3
--queries i0,i3,i1
--queries i3,i1,i0
```

如果 i0 放在第一位时总慢，可能与 context 起始突发或连接首次使用有关；如果 i3 紧跟某条查询时才慢，前一查询改变了 i3 到达集中度。

### 实验 6：空查询基线

通过自定义查询文件测试：

```cypher
RETURN 1 AS value
```

以及固定返回 10 行：

```cypher
UNWIND range(1, 10) AS value
RETURN value
```

同样测试 `1/10/25/50/100` worker。如果空查询也明显变慢，几十毫秒延迟主要位于连接、Bolt、服务端排队、线程调度或 Python 结果消费，而非 Drone/Task 扫描。

### 实验 7：连接池矩阵

固定 worker=100，分别设置：

```text
pool=10
pool=25
pool=50
pool=100
```

分别对 i0、i3、空查询测量。pool=10 很差而 50/100 接近，说明池不足会放大延迟；pool=100 仍恶化，则瓶颈在其他位置。

### 实验 8：日志 ON/OFF

分别测试关闭日志：

```text
--no-query-log --no-context-log
```

与使用独立 JSONL。写日志不直接包含在已完成查询的 `elapsed_ms` 中，但会与仍运行的 worker 竞争 CPU、文件系统和调度资源，并影响 wall time。

### 实验 9：分段计时

当前一行代码合并了提交和结果消费：

```python
rows = [row_to_dict(row) for row in session.run(query.cypher, **params)]
```

诊断版应拆分记录：

```text
session.run 返回 Result 的时间
遍历/拉取记录的时间
row_to_dict 转换时间
result_available_after
result_consumed_after
```

服务器摘要短、客户端 fetch 长，重点检查 Bolt/驱动/线程调度；服务器摘要也长，重点检查 Neo4j 排队和执行资源。

### 实验 10：资源监控

压测时在另一个终端运行：

```bash
sudo docker stats lade-query-neo4j
```

记录 CPU、内存、Block I/O 和网络。若有系统工具，再记录 `pidstat`、`iostat` 和 swap。结合少量 PROFILE 的 page cache hits/misses 判断缓存影响。

### 实验 11：A-B-A 可逆性

```text
A1：有索引
B：删除索引
A2：重建索引并等待 ONLINE
```

每阶段使用相同预热、命令和重复次数。如果 A2 恢复 A1，索引状态关联较强；如果 A2 更像 B，说明存在时间漂移、缓存或后台负载混杂。

更严格的方法是建立两个相同数据副本，一个保留索引、一个删除索引，在同一宿主机上顺序测试，不能同时压测。

### 实验 12：固定请求到达率

这是验证闭环假设最强的实验，但当前脚本尚无固定 QPS 模式。建议新增 open-loop 发生器，分别测试：

```text
5 contexts/s
10 contexts/s
20 contexts/s
40 contexts/s
```

请求按计划时间提交，不因上一个请求更快完成而自动增加请求数。

- 固定到达率后 i0/i3 差异消失：此前主要是闭环负载变化。
- 固定到达率后仍分叉：继续检查缓存、服务端资源和执行计划。
- 某个速率后延迟突增：该点接近系统饱和区。

### 推荐最小实验顺序

先完成五步：

1. ON/OFF 各保存 `SHOW INDEXES` 和 i0/i3 PROFILE。
2. i0 单独测试 worker=`1/10/25/50/100`。
3. i3 单独测试 worker=`1/10/25/50/100`。
4. 测试 `i0,i3`、`i0,i1,i3`、`core`。
5. 做一次 A-B-A，并全程记录 `docker stats`。

如果结论仍不明确，再实现固定 QPS 和分段计时。

### 当前最可能的解释

在没有看到新实验原始日志前，最值得优先验证的是：

```text
删除索引后多数查询变快
  -> context 周转更快
  -> 闭环 worker 更密集发请求
  -> i0/i3 请求率和并发重叠提高
  -> 它们的端到端排队时间增加
```

这不是“i0/i3 多扫描了 AgentState”，而是共享系统中的间接负载效应。它目前只是首要假设，需要由单线程曲线、混合消融和固定 QPS 验证。
