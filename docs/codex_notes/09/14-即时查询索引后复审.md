# LLM 前置查询索引后复审

### 任务背景

重新评审当前 `scripts/lade_llm_context_queries.py` 的查询设计、类型覆盖和缺失类型。此前三组 AgentState 属性索引已建立，需把访问性能改善与查询语义正确性分开评估。当前有 i0–i11 共 12 条模板，之前压测仅 11 类查询成功，i2 全部失败。

### 关键结论

- 业务方向合理：自身状态、近期记忆、当前任务、区域协同和全局摘要能够支撑基础 LLM 上下文，短窗口与输出上限也符合在线查询需求。
- 目前仍有语法和历史时间一致性问题，不能将索引建立完成视为整个查询设计已完善。
- 覆盖以属性等值/范围过滤、Top-K、聚合、属性关联为主，显式关系访问集中在 i3/i4，尚不是全面的图查询基准。
- i1/i9 虽只返回一条，但属于上界范围检索加 Top-1，不能与 i0 的等值点查混为一类。
- 高优先级补充方向为存在性/反连接、空间候选、跨 step 差分；之后按业务需求增加多跳和多分支模式。
- 最短路径、可达性需有真实通行图；全文/向量检索需有经验文本或嵌入，不能只为增加类型而套在归属图上。
- 本轮仅阅读代码、已有验证证据和官方文档，没有重新访问数据库或运行压测。

### 优先发现

1. **P1：i2 仍有确定的语法错误。** `scripts/lade_llm_context_queries.py:86` 仍是 `WHERE a.step_index BETWEEN $start_step AND $step_index`。之前真实 EXPLAIN/压测已报错，当前应改为 `a.step_index >= $start_step AND a.step_index <= $step_index`。这会影响 decision、diagnostic、all 包中的轨迹查询。当前 mock 测试不解析 Cypher，不能发现此问题。此次只评审，尚未修改。

2. **P1：历史回放会混入未来状态。** i0（第 33 行）、i3（第 99 行）、i8（第 213 行）读取当前 Drone/Task 属性，而 i1 等查询使用指定 step 的 AgentState。例如指定 step 2300，但数据库已经运行到 5000，i0 可以返回 5000 的状态；i3/i8 可以排除在 2300 尚未完成、后来才完成的任务。自动由 Step 解析 time_minute 不能解决可变属性的版本问题。应明确实时最新模式与历史回放模式，后者需要截止时刻的事件重建或任务状态版本。

3. **P2：step 可见性与查询整包一致性没有完整保证。** `simulation/knowledge.py:243` 先单独提交 Step，再调用第 265 行的 AgentState 批量写入；查询脚本第 536 行开始使用多次独立 session.run。并发写入时可能看到已有 Step、尚无对应 AgentState 的阶段，也可能在一包查询中跨越写入时点。建议让查询锚定完整提交的 step，并返回实际 step 和状态新鲜度。单纯增加索引不会消除这类时序问题。

4. **P2：i7 的候选条件不足以直接表示最近可用协作对象。** 第 188 行的查询按同一区域、同一步筛选，再按队列和电量排序，未计算距离，也未完整过滤充电状态、载荷上限和续航可达性。作为区域同伴列表合理；用作最近可用 drone 列表则需要补充条件。

5. **P2：上下文字段容易误读。** i9 第 255 行返回的 completed_tasks，在 `simulation/knowledge.py:80` 是本步完成数，并非累计值。i0 的 updated_at 来自事件写入，而 AgentState 批量更新 Drone 属性时未同步更新时间，不能可靠地表明这些动态属性最后更新的时刻。

6. **P2：i8 的未完成任务不能直接当成待接单任务池。** 非 completed 包括已分配/已携带任务，也包括缺失 status 的节点；当前写入路径主要在任务事件发生时创建/更新 Task，不能保证所有已释放未分配任务都已入图。查询还包含已逾期任务，这是可接受的策略，但需要与“未来预警窗口”区别展示。i3 不检查 CARRYING.active；当前完成过滤能排除已完成任务，但若将来支持撤销、重分配，应同步定义有效关系语义。

### 当前类型覆盖

下表按逻辑操作分类，类别可重叠。self、task、region 等脚本 category 是业务维度，不是数据库操作类型。

| 查询 | 业务内容 | 主要类型 | 关键写法 |
| --- | --- | --- | --- |
| i0 | 当前自身属性 | 复合键等值点查 | MATCH Drone(run_id, id) |
| i1 | 指定 step 前最近状态 | 上界范围过滤 + Top-1 | step_index <= 参数、DESC、LIMIT 1 |
| i2 | 自身短期轨迹 | 双边范围 + Top-K | 起止 step、DESC、LIMIT；目前语法无效 |
| i3 | 自身未完成任务 | 一跳遍历 + 过滤 + 去重聚合 + Top-K | ASSIGNED 或 CARRYING、collect DISTINCT、min |
| i4 | 自身近期事件 | 时间窗口 + 可选一跳关联 + Top-K | OPTIONAL MATCH ABOUT_TASK |
| i5 | 自身近期表现统计 | 时间窗口 + 条件聚合 | sum(CASE ...)、count |
| i6 | 所在区域状态分布 | 属性关联 + 分组聚合 | self.region_id/self.step_index、按 status 分组 |
| i7 | 同区域其他 drone | 属性关联 + 排除自身 + 多字段 Top-K | drone_id <>、queue_len ASC、电量 DESC |
| i8 | 区域紧急未完成任务 | 属性关联 + 多条件过滤 + Top-K | 状态、释放时间、截止时间 |
| i9 | 最近全局摘要 | 上界范围过滤 + Top-1 | 读取 Step 的预计算属性 |
| i10 | 区域近期事件 | 属性关联 + 时间窗口 + Top-K | 先定位 self，再按区域/时间查 Event |
| i11 | 区域负载排行 | 属性关联 + 条件/分组聚合 + Top-K | 同 step 状态按 region_id 分组 |

重要区分：i6/i7/i8/i10 的两个 MATCH 用属性值衔接，不是沿两条边做多跳遍历。i9 读取已计算好的摘要，也不等价于现场扫描全部任务做聚合。节点量大并不自动意味着每种查询都属于复杂图分析。

### 值得补充的类型

| 缺失类型 | 面向 drone 决策的问题 | 优先级与前提 |
| --- | --- | --- |
| 存在性、半连接 | 这个任务是否已有有效接管者？ | 高；可用 EXISTS，需定义有效时间和有效关系 |
| 反连接 | 哪些已释放任务还没有有效分配？ | 高；可用 NOT EXISTS，先确保任务释放时已入图 |
| 空间范围/距离 Top-K | 500 米内有哪些具备载荷和续航余量的协作 drone？ | 高；现有 x/y 可用于计算，先确认单位和坐标系 |
| 跨 step 关联/差分 | 最近几步是否没有移动、队列持续增长或电量异常下降？ | 高；AgentState 已提供基础，需处理缺失采样与时间间隔 |
| 固定多跳图模式 | 某任务关联哪些执行 drone、事件和区域？ | 中；使用现有 ABOUT_TASK、ABOUT_DRONE、BELONGS_TO 等边 |
| 多分支/星型图模式 | 同一任务的执行者、事件、区域负载如何共同影响风险？ | 中；多分支先适当聚合，防止行数相乘造成重复计数 |
| 有界变长路径、可达性、最短路径 | 哪些区域可通行、能否绕开受限通道？ | 需通行图；归属关系路径的跳数不能解释为飞行距离 |
| 全文/语义相似检索 | 过去是否有类似异常以及处理经验？ | 需经验文本和相应检索数据；当前结构化状态查询不必强加 |

EXISTS 用于判断模式是否存在，无需把所有匹配结果都返回，适合决策前的布尔检查。[官方文档](https://neo4j.com/docs/cypher-manual/current/subqueries/existential/)

空间距离可用 point.distance；笛卡尔坐标距离单位与坐标一致，不能在未确认 x/y 单位时直接声称是米。[官方文档](https://www.neo4j.com/docs/cypher-manual/current/functions/spatial/)

Cypher 支持固定和变长图模式，但在本项目加入路径类查询前，应先定义具有业务意义的关系路径。[官方文档](https://www.neo4j.com/docs/cypher-manual/5/patterns/)

UNION、UNWIND、CALL 子查询是其他可使用的表达方式，但不必为了“语法覆盖”逐一增加在线查询；应先明确它们对应的业务问题。
