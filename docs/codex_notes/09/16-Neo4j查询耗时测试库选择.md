### 任务背景

用户需要统计 `scripts/lade_llm_context_queries.py` 的查询时间，担心现有 Neo4j 中其他实验、历史 run 和多余节点干扰结果，并希望判断应使用现有 Neo4j 还是单独建立查询实例。

### 关键结论

- `run_id` 能隔离返回结果，但不能保证性能隔离；其他 run 的节点仍可能增加标签扫描、缓存占用和服务端负载。
- 当前查询是否受多余数据影响，主要取决于执行计划是 `NodeIndexSeek` 还是 `NodeByLabelScan`，以及数据库是否同时有后台写入。
- 项目代码只自动创建三组 `AgentState` 复合索引；不能据此假定 `Drone`、`Event`、`Task`、`Step` 也有适合这些查询的属性索引。
- 日常功能验证和真实运行延迟观测应使用现有库；正式、可重复的性能对比应使用独立 Neo4j 实例和固定数据快照。
- 独立测试库不能是空库，应复制或构造与目标规模、标签分布、关系度数和索引配置相近的数据，否则结果虽然稳定但没有代表性。
- 同一 Neo4j 实例中的另一个 database 只能隔离数据，CPU、内存、页缓存和进程仍共享；严格性能隔离应使用独立容器、独立数据卷，并尽量固定资源和后台负载。

### 多余数据如何影响当前查询

查询带 `run_id` 并不意味着 Neo4j 一开始就只读取该 run。若没有匹配的复合索引，执行过程可能是：

```text
扫描某个标签下的候选节点
  -> 逐个检查 run_id、drone_id 等属性
  -> 留下目标 run 的节点
```

此时其他 run 的同标签节点虽然不会出现在结果中，却会增加扫描工作。

按当前脚本分析：

- `i0`：匹配 `Drone(run_id,id)`。没有对应索引时，其他 run 的 `Drone` 会增加标签扫描。
- `i1/i2`：匹配 `AgentState(run_id,drone_id,step_index)`；项目已有相应复合索引，通常受益明显。
- `i3`：先匹配 `Drone(run_id,id)`，再展开 `ASSIGNED|CARRYING`。其他 `Drone` 影响前端定位；目标 drone 自身的历史关系数量影响后续展开、聚合和排序。
- `i4/i5`：匹配 `Event(run_id,drone_id)` 并按时间过滤。若没有 Event 复合索引，大量历史 Event 会显著影响扫描。
- `i6/i7`：依赖两种 `AgentState` 访问路径，项目已有 `run/drone/step` 和 `run/region/step` 索引。
- `i8`：先通过 AgentState 定位区域，再查 `Task(run_id,region_id)`；Task 数量和 Task 索引会影响耗时。
- `i9`：匹配 `Step(run_id)` 并按 `step_index` 排序取最新值；没有 `Step(run_id,step_index)` 索引时会受历史 Step 数量影响。
- `i10`：先定位区域，再查该区域的 Event；Event 数量和索引决定影响程度。
- `i11`：先找最新 Step，再按该 step 聚合 AgentState；Step 定位和 AgentState 索引都会影响耗时。

即使多余数据属于完全不同的标签，也可能通过页缓存容量、磁盘 I/O、垃圾回收和后台写入间接影响延迟。若现有仿真仍在写 Neo4j，索引维护和写事务也会与查询竞争资源。

### 推荐方案

建议保留两套测量口径。

#### 1. 现有库：用于真实场景验证

它回答的是：

> 在当前实际数据规模、当前后台服务和当前缓存状态下，LLM 前置查询需要多久？

适合：

- 验证查询能否正确返回真实数据；
- 观察实际运行期间的端到端延迟；
- 做容量评估和压力验收。

该结果具有现实性，但可重复性较弱。每次测试应记录：节点/关系数量、索引、run_id、并发线程、连接池、是否有写入、预热方式、P50/P95/P99 和吞吐。

#### 2. 独立实例：用于查询优化和严格对比

它回答的是：

> 在数据和环境保持不变时，修改查询或索引究竟带来了多少变化？

适合：

- 比较有/无索引；
- 比较旧版/新版 Cypher；
- 分析 i1 优化是否影响 i0/i3；
- 形成论文、报告或回归基准。

建议使用独立 Docker 容器和独立 volume，导入一份固定快照。不要清理或复用现有的第二个容器，除非已经确认它没有承担其他任务、数据可以覆盖。

### 数据规模如何选择

独立实例至少准备两档：

1. **小型正确性数据集**：用于快速验证查询结果与参数。
2. **目标规模性能数据集**：节点数、各标签比例、每架 drone 的关系数量、step 数量和 event 数量接近实际部署。

如果生产目标是百万节点，使用几百节点的独立库只能证明代码能运行，不能代表百万节点下的耗时。

### 测试前应检查的内容

查看索引：

```cypher
SHOW INDEXES
YIELD name, state, type, labelsOrTypes, properties
RETURN name, state, type, labelsOrTypes, properties
ORDER BY name;
```

查看某条查询是否使用索引，可在查询前加 `EXPLAIN`；正式诊断少量样本可用 `PROFILE`。重点观察是否出现：

- `NodeIndexSeek` / `NodeIndexSeekByRange`：通常表示使用了属性索引；
- `NodeByLabelScan`：表示扫描该标签的候选节点；
- `AllNodesScan`：表示扫描全部节点，应重点检查。

如果最终部署允许新增索引，可以单独评估这些候选索引：

- `Drone(run_id, id)`；
- `Event(run_id, drone_id, time_minute)`；
- `Step(run_id, step_index)`；
- `Task(run_id, region_id)`。

是否建立应通过目标数据集上的 `EXPLAIN/PROFILE` 和读写综合测试决定；不要直接在正在运行的现有实验库中临时增删索引来做对照。

### 建议的实验矩阵

为区分数据量、索引和并发影响，可按以下顺序测量：

1. 固定快照、单线程、逐条查询，得到固有基线。
2. 固定快照，分别测试 `1/10/25/50/100` 个 worker。
3. 保持数据不变，对比索引前后执行计划和延迟。
4. 在现有库上执行同样的只读查询，作为真实环境结果。
5. 对比独立实例与现有库，判断差异来自数据规模还是共享负载。

不要只看平均耗时，应同时记录 P50、P95、P99、吞吐和失败数。当前脚本是闭环负载发生器，查询变快会提高后续请求到达率，所以正式对比还应固定请求到达率，或至少同时报告 context 吞吐。
