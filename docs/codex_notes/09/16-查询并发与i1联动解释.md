### 任务背景

用户希望理解 `scripts/lade_llm_context_queries.py` 的查询并发具体体现在哪里，以及为什么 `i1` 查询变快后，会间接影响 `i0`、`i3` 的查询耗时。

### 关键结论

- 并发发生在不同 context 之间：不同 drone、不同 repeat 组成的 job 由 `ThreadPoolExecutor` 并发执行。
- 同一个 context 内查询不并发，而是在同一个 Neo4j session 中按选定顺序逐条执行；默认 `core` 顺序是 `i0 → i1 → i3 → i4 → i5 → i6 → i9`。
- 这是闭环负载模型：线程完成一个 context 后，马上领取下一个 job；没有固定发包速率或间隔。
- `i1` 变快不会修改 `i0`、`i3` 的执行计划或结果，也不存在查询结果依赖；它改变的是后续请求到达 Neo4j 的节奏。
- `i1` 变快后，同一线程更早执行 `i3`，也更早结束 context 并开始下一轮 `i0`，使 `i0/i3` 请求更密集、更容易发生服务端和客户端排队。
- 脚本记录的是客户端端到端墙钟时间，包含数据库排队、Bolt 往返、驱动解码和结果遍历，不只是 Cypher 算子自身的 CPU 时间。

### 并发具体体现在哪里

`run_context_benchmark()` 先构造 job：

```python
jobs = [
    (drone_id, repeat_index * len(drone_ids) + drone_index)
    for repeat_index in range(args.repeat)
    for drone_index, drone_id in enumerate(drone_ids)
]
```

假设有 100 个 drone、`repeat=20`，就会生成 2000 个 context job。

线程数由下面的代码决定：

```python
max_workers = args.max_workers or len(drone_ids)
```

如果没有显式传 `--max-workers`，100 个 drone 默认就是最多 100 个工作线程。随后所有 job 被提交到线程池：

```python
with ThreadPoolExecutor(max_workers=max_workers) as executor:
    futures = [
        executor.submit(execute_context, driver, queries, args, drone_id, context_index)
        for drone_id, context_index in jobs
    ]
```

因此并发结构是：

```text
worker 1: context A: i0 -> i1 -> i3 -> ... -> 下一份 context: i0 -> i1 -> i3
worker 2: context B: i0 -> i1 -> i3 -> ... -> 下一份 context: i0 -> i1 -> i3
worker 3: context C: i0 -> i1 -> i3 -> ... -> 下一份 context: i0 -> i1 -> i3
...
```

横向的多个 worker 是并发的；每一行内部的查询是串行的。

`execute_context()` 中这一段证明单个 context 是串行执行：

```python
with driver.session(**session_kwargs) as session:
    for query_index, query in enumerate(queries):
        rows = [row_to_dict(row) for row in session.run(query.cypher, **params)]
```

所有线程共享同一个 Neo4j driver。driver 内部使用连接池，各 session/查询最终还会共享 Neo4j 服务端的 CPU、工作线程、内存和页缓存等资源。

### 为什么 i1 变快会影响 i3

在默认查询顺序中，`i3` 排在 `i1` 后面。

假设原来 `i1` 需要 5 秒：

```text
i0 完成 -> i1 占用线程 5 秒 -> i3 才发给 Neo4j
```

100 个 worker 因各自开始和完成时间不同，`i3` 请求会被慢 `i1` 阻挡和摊开。若 `i1` 优化到 50 毫秒：

```text
i0 完成 -> i1 只用 50 ms -> 大量 worker 很快进入 i3
```

于是同一时段到达数据库的 `i3` 更多，服务端排队和资源竞争可能增加。即使 `i3` 的 Cypher、参数、执行计划完全没有变化，其端到端响应时间也可能上升。

这类似收费站前的一段慢路突然拓宽：后面的收费站没有变慢，但车辆到达更集中，排队反而可能加长。

### 为什么 i1 变快也会影响排在前面的 i0

需要区分“当前 context 的 i0”和“后续 context 的 i0”。

`i1` 不可能反向改变同一个 context 中已经执行完的 `i0`。真正受影响的是下一轮 job 的 `i0`：

```text
原来：i0 -> 慢 i1 -> i3 -> ... -> 很久以后才开始下一轮 i0
优化：i0 -> 快 i1 -> i3 -> ... -> 很快就开始下一轮 i0
```

当 `repeat > 1` 或 job 数大于 worker 数时，worker 完成当前 context 后会立刻领取下一份 context。`i1` 以及其他慢查询变快，会缩短整个循环周期，于是单位时间内发出的 `i0` 数量显著增加。

仓库已有实验中，整批 2000 个 context 的完成时间从约 441.25 秒下降到 33.24 秒，即 context 完成率从约 4.53 个/秒提高到 60.17 个/秒。每个 context 都包含一次 `i0` 和一次 `i3`，因此二者的到达率也同步提高约 13.3 倍。这里变化的是负载强度，并不是它们自身多读取了数据。

还有一个细节：即使 `repeat=1`，较早完成 `i0` 的线程已经开始执行 `i1` 时，其他线程的较慢 `i0` 可能仍未结束，所以不同查询仍可能在数据库里短暂重叠。但如果 job 数等于 worker 数且没有下一轮，`i1` 变快通常不能解释已经完成的多数 `i0`；此时应检查冷启动、连接、缓存、后台负载和实验条件差异。

### 为什么查询日志中的 elapsed_ms 会变化

脚本的计时范围是：

```python
query_start = time.perf_counter()
rows = [row_to_dict(row) for row in session.run(query.cypher, **params)]
elapsed_ms = (time.perf_counter() - query_start) * 1000
```

这个时间近似为：

```text
客户端/驱动等待
+ Bolt 网络往返
+ Neo4j 排队
+ Cypher 执行
+ 返回数据传输
+ Python 驱动解码和 row_to_dict 转换
```

因此它是端到端响应时间，不是纯粹的 Neo4j 算子执行时间。100 个线程同时密集请求时，即便是 `RETURN 1` 这种不读图数据的查询，也可能因为调度、协议和结果消费链路而明显变慢。

已有只读对照也支持这一点：保持索引不变，i0 在 1/10/100 线程下平均约为 `0.849/9.875/80.195 ms`，i3 约为 `2.578/16.008/173.188 ms`。这说明并发度和请求密度本身足以显著改变测得延迟。

### 应如何正确理解因果关系

不准确的说法是：

> i1 变快，导致 i0 和 i3 的查询逻辑变慢。

更准确的说法是：

> i1 变快，缩短了闭环工作线程的循环周期，提高了后续 i3 和下一轮 i0 的请求到达率；共享资源上的排队加重，使 i0/i3 的端到端观测延迟发生变化。

所以“单条查询执行成本”和“混合并发场景下的响应时间”是两个不同指标。

### 如何做不互相干扰的对照

若要判断 i1 优化是否真的影响 i0/i3，应固定负载模型：

1. 分别单线程运行 i0、i1、i3，测固有基线。
2. 分别以固定并发运行单一查询，不混合模板。
3. 混合测试时固定每秒请求数，而不是让线程完成后立即发下一条。
4. 固定 `max_workers`、连接池、数据库快照、预热过程和后台写入负载。
5. 同时报告吞吐和 P50/P95 延迟，不能只比较平均值。

若使用当前脚本，可以先通过 `--max-workers 1` 看串行基线，再逐步测试 `10/25/50/100`，观察进入排队区的位置。
