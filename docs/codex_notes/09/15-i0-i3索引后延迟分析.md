### 底层访问过程

#### i0：Drone 当前属性

源码：`scripts/lade_llm_context_queries.py:33`。

```cypher
MATCH (d:Drone {run_id: $run_id, id: $drone_id})
RETURN ...
LIMIT 1
```

实际算子顺序：

```text
NodeByLabelScan(d:Drone)
  → Filter(run_id、id)
  → Limit 1
  → CacheProperties
  → Projection
  → ProduceResults
```

Neo4j 是属性图，不能机械地理解成 JOIN 几张关系表。此处访问 Drone 标签对应的节点及节点属性，没有遍历关系。标签 LOOKUP 索引用于找到 Drone 标签节点，和按 `(run_id,id)` 定位实体的属性索引不同。

`run_id` 是 Drone 的属性，条件 `d.run_id=$run_id` 不会自动去查 Run 节点，也不会访问该 run 的所有 AgentState。标签扫描范围可以包含其他 run 的 Drone，然后由 Filter 筛选；LIMIT 1 允许找到首个合格结果后停止继续请求上游行。当前 drone-1 的 PROFILE 实际扫描了 56 行，不代表所有 drone 都是这个扫描量。

CacheProperties 是本次执行中复用已读取属性的算子，不是新建业务表，不是整个查询结果缓存，也不表示已经使用了 AgentState 属性索引。

#### i3：Drone 关联的未完成任务

源码：`scripts/lade_llm_context_queries.py:99`。

```cypher
MATCH (d:Drone {run_id: $run_id, id: $drone_id})
      -[rel:ASSIGNED|CARRYING]->(t:Task {run_id: $run_id})
WHERE coalesce(t.status, "") <> "completed"
WITH t,
     collect(DISTINCT type(rel)) AS relation_types,
     min(coalesce(rel.time_minute, rel.pickup_time_minute, t.release_minute))
       AS relation_time_minute
RETURN ...
ORDER BY t.deadline_minute ASC, relation_time_minute ASC
LIMIT $limit
```

实际过程和本次 PROFILE 的中间行数：

| 阶段 | 算子 | 本次输出行数 | 含义 |
| --- | --- | ---: | --- |
| 找 Drone | NodeByLabelScan | 757 | 扫描 Drone 标签节点 |
| 筛选实体 | Filter | 1 | run_id、id 匹配 |
| 展开关系 | Expand(All) | 265 | 遍历该 Drone 出向 ASSIGNED/CARRYING |
| 筛选任务 | Filter | 157 | Task 标签、run_id、非 completed |
| 按任务聚合 | EagerAggregation | 151 | 合并相同 Task 的多条关系，收集类型并取最早时间 |
| 排序取前若干项 | Top | 10 | 按 deadline 和关系时间选前 10 |

因此 i3 读取两类节点 Drone/Task、两类关系 ASSIGNED/CARRYING，以及相关属性。它没有扫描百万 AgentState，也没有访问 Event、Region 或 Step。Expand(All) 中的 All 不代表全图遍历，而是该算子的展开方式。

LIMIT 10 限制最终返回行数，不保证只读取 10 个任务。聚合和 Top 需要处理上游候选；当前未使用排序索引直接产生所需顺序。与 i0 不同，i3 的最终 LIMIT 不能简单地让前端 Drone 扫描命中一个就立即结束全部查询。

已完成任务的历史关系仍可能先被遍历，之后才通过 Task.status 排除。模板也没有检查 CARRYING.active；因此候选集合不能直接当成无人机当前内存 queue。上述 151 个候选是当前图谱与模板共同得到的结果，其业务一致性需要另行检查，不是本次索引新增的行为。

DB Hits 表示数据库访问操作计数，不等于节点数量、SQL 表扫描次数或磁盘物理读次数。本次输出中的缓存指标全零不能据此解释为真实磁盘读取绝对为零。参见 [Neo4j 执行计划说明](https://neo4j.com/docs/cypher-manual/25/planning-and-tuning/execution-plans/)。

### 为什么混合压测会出现这种变化

#### 1. 当前耗时口径是客户端端到端延迟

`execute_context()` 在第 560 行开始计时，第 562 行执行 `session.run()` 并遍历全部返回记录，转换为 Python 字典，随后结束计时。

可以按阶段理解为：连接获取/协议交互、服务端排队与执行、结果传输、Python 驱动解码和字典转换。在这些阶段发生的线程等待也在墙钟耗时内。这不是单独的算子 CPU 时间。

每个 context 创建 session，内部顺序执行查询。i0 是第一个查询，可能更容易承担新连接或会话首次使用的开销；但每次 run 都可能从连接池借用连接，不能把所有连接等待只归到 i0。日志中的 database=null 说明两次都没有显式指定数据库，可在后续实验指定 `--database neo4j` 减少数据库选择的不确定性，不能宣称本次每个 i0 必然额外查一次默认数据库。参见 [Neo4j Python 驱动性能说明](https://neo4j.com/docs/python-manual/current/performance/)。

context 写 JSONL 发生在该 context 返回之后，未直接加进已完成的单条查询计时；但更频繁的日志序列化和写盘会与其他仍运行的工作线程竞争资源，并且会计入总 wall time。线程池尚未开始执行 context 的任务排队，不直接计入该 context 内的单条 query_start 计时。

#### 2. 其他查询变快，整个循环周转更频繁

每个工作任务按既定顺序执行 i0 到 i11，结束后处理下一个 context。索引使原来约 5 秒的 i6/i7 降到约 60–70 ms，整批 24000 查询由 441.25 秒压缩为 33.24 秒。

同样每类 2000 次请求，i0 和 i3 各自的平均处理频率由 4.53 次/秒变成 60.17 次/秒。大扫描减少不等于客户端请求、事务和解码压力也减少；更密集的请求完成会改变瓶颈位置。图查询仍未优化的 i3，以及本来很短、对固定等待开销敏感的 i0，都可能因此获得更高的混合负载响应时间。

这是最符合现有证据的解释方向，但处理频率提高本身不能证明 CPU 或连接池已饱和；缺少当时线程、连接池、CPU 和服务端等待指标，不能定量归因。

#### 3. 不只是第一次冷启动变慢

剔除 context_index<100 的首批请求后，i0 平均仍从 7.247 增至 67.486 ms，i3 从 13.757 增至 178.199 ms。首批之外仍存在回退，因此不能简单归因于第一次编译或首次建连接。

i2 两次各失败 2000 次，错误均为原模板使用不受支持的 BETWEEN 语法。其失败响应平均也从 15.223 增至 76.671 ms；它未执行正常的图扫描，说明变化也发生在查询执行之外或之前的响应处理环节。i2 恰在 i3 前面，错误处理会影响后续请求节奏，但现有日志不能证明 i3 每次都重连。

#### 4. 比较仍存在时间与负载混杂

两次压测相隔一周。相同 run、参数、输出不代表整个数据库规模、邻接关系数量、其他 run 写入、缓存和机器负载相同。9 月 14 日建立索引时已有记录确认仿真写入仍在运行，但不能推定两个压测时段的写入强度完全一样。索引维护仅在写入相关索引属性时产生额外写开销，不会让 i0/i3 为每次读查询遍历三棵 AgentState 索引。
